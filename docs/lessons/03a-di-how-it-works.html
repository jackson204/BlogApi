📎 補充：「登記簿」是什麼？（builder.Services 到底是什麼東西）

一句話：builder.Services 是一張清單，每一筆寫著「有人要這個型別時 → 這樣做出來」。這一課叫它登記簿，正式名稱是 DI 容器。

builder.Services（型別 IServiceCollection）可以想成這樣的清單：

要的型別                             做法
IConfiguration                       …（專案範本已經登記好的）
IDbContextOptionsConfiguration<…>    new 設定程序物件(你的 lambda)      ← 下面三筆是 AddDbContext 加的
DbContextOptions<BlogDbContext>      CreateDbContextOptions()
BlogDbContext                        new BlogDbContext(…)
  • AddDbContext、AddControllers 這些 Add… 方法，做的事都一樣：往清單加幾筆。
  • builder.Build() 把清單整理成可以查的容器（型別 IServiceProvider）。
  • 之後誰需要某個型別，就跟容器要（GetService），容器查清單、照做法做一個出來。

重點：加筆的時候，做法不會執行。寫食譜不等於煮菜。

① 程式啟動：AddDbContext 只登記，不建立

這一步在做什麼：程式啟動，Program.cs 由上往下執行，跑到 AddDbContext 這一行。EF Core 在這裡只做兩件事：檢查你的 BlogDbContext 有沒有「收參數的建構子」；然後往登記簿加幾筆「要什麼 → 怎麼做」。你的 lambda 沒有執行，BlogDbContext 也一個都沒 new。所以 3-5 圖裡的 ③ GetConnectionString、② UseSqlServer 這時候都還沒跑（見 3-5 的「讀的順序 ≠ 執行的順序」）。

✏️ 你寫的：Program.cs

builder.Services.AddDbContext<BlogDbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("BlogDb")));
📎 補充：「檢查建構子」是怎麼檢查的？（反射）

C# 程式在執行的時候可以「查看」一個型別長什麼樣子：有哪些建構子、每個建構子收幾個參數、參數是什麼型別，甚至可以直接呼叫它。這個能力叫反射（Reflection）。

// 回傳 BlogDbContext 所有建構子的清單；每一筆可以再問它收哪些參數
typeof(BlogDbContext).GetConstructors()

登記簿（DI 容器）整條流程都靠它：① 用它看你的建構子要什麼，③ 用它呼叫你的建構子。你不用自己寫反射，知道「框架是這樣知道我的建構子要什麼」就夠了。

📎 補充：為什麼有三個同名的 AddDbContext？（多載）

C# 允許同一個名字的方法有好幾個版本，只要參數不一樣；呼叫時由你傳的參數決定用哪一個，這叫多載（overload）。AddDbContext 有好幾個版本，你呼叫的是「一個型別參數、收 Action<DbContextOptionsBuilder>」的那個；它會轉交給另一個版本，最後才到真正做事的版本。

你呼叫的 AddDbContext 自己不做事，它把參數原封不動交給另一個 AddDbContext（多載），那一個再交給真正做事的 AddDbContext，一共經過三個方法。

中間那一個有一行要注意：真正做事的 AddDbContext 要的 lambda 型別是 Action<IServiceProvider, DbContextOptionsBuilder>（收兩個參數），你寫的是 Action<DbContextOptionsBuilder>（只收一個），型別對不上。所以它另外寫了一個新的 lambda (_, b) => optionsAction(b)：

  • 收兩個參數：_ 和 b。_ 是 C# 的寫法，代表「這個參數我不用」
  • 執行時只做一件事：呼叫你的 lambda（optionsAction），把 b（設定單）傳給它

從這裡開始，往下傳的都是這個新 lambda，不是你原本那個。

// 第 1154–1163 行
private static void CheckContextConstructors<TContext>()
    where TContext : DbContext
{
    // 用反射列出建構子
    var declaredConstructors = typeof(TContext).GetTypeInfo().DeclaredConstructors.ToList();
    // 只有一個建構子、而且它不收參數 → 丟例外
    if (declaredConstructors.Count == 1
        && declaredConstructors[0].GetParameters().Length == 0)
    {
        throw new ArgumentException(CoreStrings.DbContextMissingConstructor(typeof(TContext).ShortDisplayName()));
    }
}

③-1 請求進來：建立 PostsController

這一步在做什麼：瀏覽器打 GET /api/posts，ASP.NET Core 查路由，知道要交給 PostsController 處理。要呼叫它的方法，得先有一個 PostsController 物件；但你沒寫 new PostsController(…)，而且它的建構子還要一個 BlogDbContext。於是框架跟登記簿要一個 BlogDbContext，登記簿查到做法是「new 一個」，再看建構子：又要一個 DbContextOptions<BlogDbContext>，再查登記簿……這是一條需求鏈：Controller 要 DbContext，DbContext 要 options。框架從鏈的最尾端開始做：先做 options，再 new BlogDbContext，最後 new PostsController。

📎 補充：「這個請求專用的 scope」是什麼？

登記簿的每一筆，除了「怎麼做」，還寫了「做好的東西可以用多久」。AddDbContext 登記的是 Scoped：

  • 每個請求進來，框架開一個 scope，可以想成這個請求專用的小籃子
  • 這個請求第一次要 BlogDbContext：做一個，放進籃子
  • 同一個請求再要：直接給籃子裡那一個，不再做
  • 請求結束：整個籃子丟掉，裡面的 BlogDbContext 也丟掉

為什麼要這樣設計、還有哪幾種「用多久」，是下一課 03b 的主題。這裡只要知道：一個請求一個 BlogDbContext。

③-2 a～c：做出 options（設定單）

這一步在做什麼：EF Core 準備一張空白設定單（a），交給你的 lambda 在上面寫「用 SQL Server、連線字串是…」（b），再把填好的單變成成品（c）。lambda 是 Action，沒有回傳值，它不是「去拿」連線字串回來，而是在 EF Core 遞給它的那張單上寫字。

🍽️ 比喻：去餐廳點餐：服務生（EF Core）遞給你空白點餐單（a）→ 你勾選要什麼（b，你的 lambda）→ 廚房照單做出餐點（c）→ 送到你桌上（d，你的建構子收下）。

✏️ 你寫的：Program.cs（b 執行的就是這段）

options => options.UseSqlServer(builder.Configuration.GetConnectionString("BlogDb"))

lambda 就是「沒有名字的方法」。為了看清楚 b 在做什麼，先把它改寫成一般方法的樣子。一般方法一定要有名字，這裡我取一個叫 ConfigureBlogDb；這個名字是為了說明方便取的，你的 lambda 本來就沒有名字，叫什麼都不影響它做的事：

// ConfigureBlogDb 是為了說明取的名字；大括號裡面就是你 lambda 的那一行
void ConfigureBlogDb(DbContextOptionsBuilder options)   // 參數名稱叫 options
{
    options.UseSqlServer(…);
}

簡化版：EF Core 內部在做的事（每行對應小地圖的字母）

// a. 空白設定單
DbContextOptionsBuilder<BlogDbContext> builder = new DbContextOptionsBuilder<BlogDbContext>();

// b. 執行你的 lambda（填單）
ConfigureBlogDb(builder);

// c. 從 builder 拿出成品
DbContextOptions<BlogDbContext> options = builder.Options;

// d. 呼叫你的建構子
BlogDbContext db = new BlogDbContext(options);

看 b：呼叫 ConfigureBlogDb(builder) 時，方法的參數 options 收到的就是 builder。所以方法裡的 options.UseSqlServer(…)，其實是在 builder 這張設定單上寫字。options 只是方法裡面用的名字，指向的就是外面的 builder：兩個名字，同一張單。記憶體裡長這樣：

變數裡裝的是「指向物件的箭頭」（參考）。呼叫時複製的是箭頭，物件只有一個，所以方法裡改了，外面看得到

為什麼 ConfigureBlogDb 沒有回傳值也可以？就是圖裡的 ③：它改的是 builder 這個物件本身，不是算出一個新東西交回來。UseSqlServer 做的事是把 builder 裡面的 _options 欄位換成「多了 SQL Server 這筆設定」的版本（原始碼在下面 c 的摺疊區）；方法結束後，外面的 builder 已經不一樣了。

UseSqlServer 會在單上寫兩筆：SqlServerOptionsExtension（你寫的 SQL Server 設定）和 CoreOptionsExtension（順便加的 EF Core 共用設定）。

📎 補充：CoreOptionsExtension 是什麼？為什麼 UseSqlServer 會順便加它

設定單上的每一筆（EF Core 叫 extension）各管一塊：SqlServerOptionsExtension 管 SQL Server 專屬的設定（連線字串等）；CoreOptionsExtension 管 EF Core 本體、不分資料庫的設定：log 怎麼印、要不要在 log 裡顯示參數值、哪些警告要當成錯誤直接丟例外、3-8 真實版本的 UseApplicationServiceProvider 寫的也是這一筆。

UseSqlServer 會加它，是因為 SQL Server 這個 provider 要求「某幾種警告要直接丟例外」（例如 PendingModelChangesWarning：model 改了卻沒做 migration），而「哪些警告要丟例外」這個設定住在 CoreOptionsExtension 裡。所以 UseSqlServer 寫完自己那一筆之後，把 CoreOptionsExtension 找出來（單上沒有就 new 一個），寫入警告設定，再放回單上：

🔎 框架原始碼：SqlServerDbContextOptionsBuilderExtensions.cs（GitHub 第 61–72 行、第 747–759 行、第 803–816 行）

// 第 61–72 行：你的 lambda 呼叫的 UseSqlServer
public static DbContextOptionsBuilder UseSqlServer(
    this DbContextOptionsBuilder optionsBuilder,
    string? connectionString,
    Action<SqlServerDbContextOptionsBuilder>? sqlServerOptionsAction = null)
{

// 第 803–816 行：找出（或 new）CoreOptionsExtension，寫入「哪些警告要丟例外」，放回單上
private static void ConfigureWarnings(DbContextOptionsBuilder optionsBuilder)
{
    var coreOptionsExtension
        = optionsBuilder.Options.FindExtension<CoreOptionsExtension>()
        ?? new CoreOptionsExtension();

    coreOptionsExtension = RelationalOptionsExtension.WithDefaultWarningConfiguration(coreOptionsExtension);

    coreOptionsExtension = coreOptionsExtension.WithWarningsConfiguration(
        coreOptionsExtension.WarningsConfiguration.TryWithExplicit(
            SqlServerEventId.ConflictingValueGenerationStrategiesWarning, WarningBehavior.Throw));

    ((IDbContextOptionsBuilderInfrastructure)optionsBuilder).AddOrUpdateExtension(coreOptionsExtension);
}

// 第 1137–1152 行
private static DbContextOptions<TContext> CreateDbContextOptions<TContext>(
    IServiceProvider applicationServiceProvider)
    where TContext : DbContext
{
    // a. 空白設定單
    var builder = new DbContextOptionsBuilder<TContext>(
        new DbContextOptions<TContext>(new Dictionary<Type, IDbContextOptionsExtension>()));

    // EF Core 自己先寫的 1 筆
    builder.UseApplicationServiceProvider(applicationServiceProvider);

    foreach (var configuration in applicationServiceProvider.GetServices<IDbContextOptionsConfiguration<TContext>>())
    {
        // b. 呼叫 Configure，把設定單傳進去
        configuration.Configure(applicationServiceProvider, builder);
    }

    // c. 填好的單 → 成品
    return builder.Options;
}
