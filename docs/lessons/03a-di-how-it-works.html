DI 是什麼

DI 是 Dependency Injection 的縮寫，中文叫依賴注入。名字拆開來看：

詞意思在部落格 API 裡
依賴（Dependency）一個類別要完成工作，需要用到的另一個東西PostsController 要查文章，需要 BlogDbContext。BlogDbContext 就是它的依賴
注入（Injection）那個東西不是自己建立的，而是別人做好交進來的PostsController 的建構子寫 BlogDbContext db，有人把做好的傳進來

合起來一句話：一個類別需要的東西，不要自己 new，寫在建構子的參數上，由外面做好傳進來。

它要解決什麼問題

物件要用之前得先建立。問題是「誰來建立、建立時要知道哪些事、用完誰負責丟」。自己 new 的話，這三件事都落在使用它的那個類別身上；DI 把這三件事從使用者身上拿走，集中到一個地方處理。

三個角色

角色是什麼在部落格 API 裡
被需要的東西（服務）提供功能的類別BlogDbContext
需要它的人（使用者）在建構子上寫出自己要什麼PostsController
負責建立與遞送的人（容器）記得每樣東西怎麼做，有人要就做好送過去，用完負責丟ASP.NET Core 內建的 DI 容器，也就是 builder.Services 背後的東西

用了之後能達到什麼效果

效果意思這一課哪裡看得到
使用者不用知道怎麼建立Controller 不用知道連線字串、不用知道 BlogDbContext 的建構子要什麼第 2 步
建立的做法只寫一次改連線字串、換資料庫，只改一個地方第 3 步
一長串的建立由容器代勞A 要 B、B 要 C、C 要 D，不用自己一層一層 new第 3 步延伸
用多久、什麼時候丟，有人管每個請求一個、請求結束自動丟，不會忘記關連線第 4 步
可以換成別的實作正式環境用真的資料庫，測試時換成假的，使用它的類別不用改所以 DI 帶來什麼

public class MiniContainer
{
    private readonly Dictionary<Type, Func<object>> _recipes = new();

    // 登記：只把「做法」存起來，不執行
    public void Register<T>(Func<T> how) where T : class
    {
        _recipes[typeof(T)] = how;
    }

    // 要：查到做法，這時才執行
    public T Get<T>() where T : class
    {
        return (T)_recipes[typeof(T)]();
    }
}

public class AutoContainer
{
    private readonly Dictionary<Type, Func<object>> _recipes = new();

    public void Register<T>(Func<T> how) where T : class
    {
        _recipes[typeof(T)] = how;
    }

    public T Get<T>() where T : class => (T)Get(typeof(T));

    private object Get(Type type)
    {
        // 有登記做法就照做
        if (_recipes.TryGetValue(type, out var how))
        {
            return how();
        }

        // 沒登記：看它的建構子要哪些東西，一個一個去要，再呼叫建構子
        var constructor = type.GetConstructors().Single();
        var arguments = constructor.GetParameters()
            .Select(parameter => Get(parameter.ParameterType))
            .ToArray();
        Console.WriteLine($"  [自動] {type.Name} 的建構子要 ({string.Join(", ", constructor.GetParameters().Select(p => p.ParameterType.Name))})");
        return constructor.Invoke(arguments);
    }
}

先認識替身：BlogDb

接下來每一步都在問同樣三個問題：什麼時候建立、建立了幾個、什麼時候丟掉。真正的 BlogDbContext 建立和丟掉時不會印任何東西，而且要連上資料庫才能用，沒辦法用來觀察。

所以這幾步用一個替身 BlogDb 代替它：不連資料庫，只在建立和丟掉時各印一行字。它已經在完整檔案裡，不用另外建。

public class BlogDb : IDisposable
{
    private static int _count;
    public int Id { get; }

    public BlogDb(string connectionString)
    {
        Id = ++_count;
        Console.WriteLine($"  [建立] BlogDb #{Id}");
    }

    public static void Reset() => _count = 0;

    public List<string> Titles() => ["Hello", "第二篇"];

    public void Dispose() => Console.WriteLine($"  [丟掉] BlogDb #{Id}");
}
這一行做什麼對應真正的 BlogDbContext
private static int _count;所有 BlogDb 共用的計數器，記目前做到第幾個（static 見類別與物件）沒有，這是為了觀察加的
public int Id { get; }這一個是第幾個被建立的。輸出裡的 #1、#2 就是它沒有，同上
public BlogDb(string connectionString)建立時一定要給連線字串。這裡收了不會真的去連，只是讓「誰要建立它，誰就得知道連線字串」這件事成立。建立時印 [建立]建構子要收連線設定（DbContextOptions）
Reset()把計數歸零。完整檔案每一步開始前都會呼叫，讓每一步都從 #1 算起沒有
Titles()假裝查資料庫，回傳兩個寫死的標題db.Posts.ToListAsync() 這類查詢
: IDisposable 與 Dispose()用完之後要呼叫的收尾方法，這裡印 [丟掉]在這裡把資料庫連線還回去

怎麼讀輸出：

  • [建立] BlogDb #1：有一個 BlogDb 被 new 出來了。出現 #2 代表又做了第二個
  • [丟掉] BlogDb #1：那一個的 Dispose() 被呼叫了，連線還回去了
  • 只有 [建立]、沒有對應的 [丟掉]：沒有人負責收尾，真正的程式裡這代表連線沒還

程式裡會看到 using var db = new BlogDb(…); 或 using (var db = …) { … }：意思是「離開這個範圍時，自動幫我呼叫 db.Dispose()」。

剩下的問題：外面那一段越來越長

程式長大之後，Controller 不直接用 BlogDb，而是用 PostService；PostService 需要 BlogDb 和 Clock；Controller 自己也要 Clock。外面就變成這樣：

{

  • 要自己記得建立的順序：先有 BlogDb 才能做 PostService，才能做 Controller
  • 在 Web API 裡更麻煩：Controller 是框架在請求進來時建立的，你根本沒有機會寫這一行

第 3 步：自己寫一本登記簿

把「每樣東西怎麼做」集中記在一個地方，要的時候去查。這個「記做法的地方」就是容器。先自己寫一個最小的版本，只有兩個方法：

public class MiniContainer
{
    private readonly Dictionary<Type, Func<object>> _recipes = new();

    // 登記：只把「做法」存起來，不執行
    public void Register<T>(Func<T> how) where T : class
    {
        _recipes[typeof(T)] = how;

    // 要：查到做法，這時才執行

        return (T)_recipes[typeof(T)]();

它就是一個 Dictionary：key 是型別，value 是「怎麼做出這個型別」的一段程式（Func，見方法簽章那一頁）。

📎 補充：為什麼有三個同名的 AddDbContext？（多載）

C# 允許同一個名字的方法有好幾個版本，只要參數不一樣；呼叫時由你傳的參數決定用哪一個，這叫多載（overload）。AddDbContext 有好幾個版本，你呼叫的是「一個型別參數、收 Action<DbContextOptionsBuilder>」的那個；它會轉交給另一個版本，最後才到真正做事的版本。

你呼叫的 AddDbContext 自己不做事，它把參數原封不動交給另一個 AddDbContext（多載），那一個再交給真正做事的 AddDbContext，一共經過三個方法。

中間那一個有一行要注意：真正做事的 AddDbContext 要的 lambda 型別是 Action<IServiceProvider, DbContextOptionsBuilder>（收兩個參數），你寫的是 Action<DbContextOptionsBuilder>（只收一個），型別對不上。所以它另外寫了一個新的 lambda (_, b) => optionsAction(b)：

  • 收兩個參數：_ 和 b。_ 是 C# 的寫法，代表「這個參數我不用」
  • 執行時只做一件事：呼叫你的 lambda（optionsAction），把 b（設定單）傳給它

從這裡開始，往下傳的都是這個新 lambda，不是你原本那個。

📎 補充：CoreOptionsExtension 是什麼？為什麼 UseSqlServer 會順便加它

這一步在做什麼：回應送出去之後，框架執行 ③-1 開 scope 時登記的那件事：丟掉這個請求的 scope。scope 裡的每個物件都會被 Dispose（意思是「用完了，把握著的資源還回去」；對 BlogDbContext 來說，就是把資料庫連線還回去），BlogDbContext 也在裡面。下一個請求進來，回到 ③-1 再建一個新的。

這一步你不用寫任何程式。
