HTTP 請求與回應（瀏覽器和伺服器之間傳了什麼）

在瀏覽器輸入網址按下 Enter，到畫面出現內容，中間是瀏覽器送出一個請求、伺服器送回一個回應。這頁講請求怎麼找到伺服器、請求和回應各長什麼樣、header 和動詞的作用，以及瀏覽器和其他工具送請求時的差別。寫 Web API 就是在寫「收到請求之後回應什麼」，所以先把這一來一回看清楚。

1. 一問一答

HTTP 是用戶端和伺服器之間的對話規則：用戶端送出一個請求（request），伺服器送回一個回應（response）。永遠是用戶端先問，伺服器才答；伺服器不會主動去找用戶端。

角色是什麼例子
用戶端（client）發出請求的程式瀏覽器、Postman、curl、手機 App、另一個伺服器上的程式
伺服器（server）一直開著、等請求進來再回應的程式網站、Web API

從按下 Enter 到拿到回應，中間有六個步驟：

前三步在找伺服器，第四步才送出請求。下面每一節講其中一段

2. 先起一個小網站，把收到的請求印出來

後面每一節的輸出都來自這個小網站。它把收到的請求整理成文字，原樣回傳，所以可以直接看到「用戶端到底送了什麼」。不用開專案，一個 .cs 檔就能執行（.NET 10）。

echo-lab.cs

// 第一行：告訴 SDK 這是 Web 專案，不然沒有 WebApplication 這些型別
#:sdk Microsoft.NET.Sdk.Web
#:property PublishAot=false

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

// 每個請求進來，先在終端機印一行，再交給下面的路徑處理
app.Use(async (context, next) =>
{
    Console.WriteLine($"收到請求：{context.Request.Method} {context.Request.Path}{context.Request.QueryString}");
    await next();
});

// /echo 開頭的網址，不管哪個動詞：把收到的東西整理成文字回傳
app.Map("/echo/{**rest}", async context =>
{
    var request = context.Request;

    var lines = new List<string>();
    lines.Add($"動詞：{request.Method}");
    lines.Add($"路徑：{request.Path}");
    lines.Add($"query string：{request.QueryString}");
    lines.Add("header：");
    foreach (var header in request.Headers)
    {
        lines.Add($"  {header.Key}: {header.Value}");
    }

    using var reader = new StreamReader(request.Body);
    var body = await reader.ReadToEndAsync();
    lines.Add($"body：{(body == "" ? "（沒有）" : body)}");

    context.Response.ContentType = "text/plain; charset=utf-8";
    await context.Response.WriteAsync(string.Join("\n", lines));
});

// 這條路徑要求 body 是 JSON，第 6 節用它看 Content-Type 的作用
app.MapPost("/items", (Item item) => $"收到 Item，Name = {item.Name}");

app.Run("http://localhost:5062");

public record Item(string Name);
# 放在任何「沒有 .csproj」的資料夾。按 Ctrl+C 停止
dotnet run echo-lab.cs

程式裡的每一行現在不用全部看懂，知道它做兩件事就夠了：每個請求在終端機印一行，/echo 開頭的網址把請求的內容回傳。

跑起來之後有兩種方式送請求：

  • 瀏覽器：網址列輸入 http://localhost:5062/echo/hello?name=amy
  • 終端機：另開一個視窗，用 curl。Windows 的 PowerShell 裡要打 curl.exe
curl.exe "http://localhost:5062/echo/hello?name=amy"

用 curl 送的結果（實測）：

動詞：GET
路徑：/echo/hello
query string：?name=amy
header：
  Accept: */*
  Host: localhost:5062
  User-Agent: curl/8.7.1
body：（沒有）

下面的輸出都是用 curl 實際送出來的。瀏覽器送的請求 header 會多很多，內容依瀏覽器而定，請自己打開看一次。

3. 請求送到哪裡：主機、IP、port

送出請求之前，用戶端要先知道連到哪一台機器的哪一個程式。網址裡的主機回答「哪一台機器」，port 回答「機器上的哪一個程式」。

名詞是什麼例子
IP 位址網路上每台機器的編號，連線實際用的是它127.0.0.1
主機名稱給人看的名字，連線前要先換成 IP 位址localhost、example.com
DNS把主機名稱換成 IP 位址的查詢服務查 example.com 得到一個 IP 位址
port同一台機器上用來區分程式的號碼，0 到 65535。一個 port 同時只能有一個程式在聽5062

localhost 是一個特別的主機名稱，固定代表這台電腦自己，對應的 IP 位址是 127.0.0.1。所以這兩個網址連到同一個地方（實測）：

http://localhost:5062/echo     → 200
http://127.0.0.1:5062/echo     → 200

網址沒寫 port 時，用協定的預設值：http 是 80，https 是 443。平常上網的網址看不到 port，就是因為用了預設值。開發時伺服器通常聽別的 port，所以網址要寫出來。

連不上，和 404 不一樣

✗ 連不上：請求根本沒有送出去

curl.exe http://localhost:5999/echo

curl: (7) Failed to connect to localhost
port 5999 ... Couldn't connect to server

5999 這個 port 沒有程式在聽。停在圖裡的第 ③ 步，沒有請求、沒有回應，也沒有任何狀態碼。要檢查的是：伺服器有沒有啟動、port 有沒有打錯。

✓ 404：連上了，伺服器有回應

curl.exe -i http://localhost:5062/favicon.ico

HTTP/1.1 404 Not Found

伺服器收到請求，回答「我沒有這個路徑」。走完了六個步驟。要檢查的是：路徑有沒有打錯。

4. 請求長什麼樣

一個 HTTP 請求是一段文字，分三塊：第一行、header、body。curl 加上 -v 會把實際送出去的文字印出來，> 開頭的是請求。

curl.exe -v http://localhost:5062/echo/hello

> GET /echo/hello HTTP/1.1        ← 第一行：動詞、路徑、協定版本
> Host: localhost:5062            ← header，一行一個，格式是「名稱: 值」
> User-Agent: curl/8.7.1
> Accept: */*
>                                 ← 空一行，代表 header 結束。這個請求沒有 body
哪一塊說什麼
動詞（method）要做哪一種事：GET 拿資料、POST 新增、PUT 修改、DELETE 刪除
路徑（加上 query string）對哪個東西做。網址裡主機和 port 後面的那一段，細節見「網址與 query string」
header這個請求的附加說明：我是誰、我送的內容是什麼格式、我想要什麼格式的回應
body要送給伺服器的內容。GET、DELETE 通常沒有，POST、PUT 通常有

帶 body 的請求。這次對 /echo/items 送 POST，body 是一段 JSON（實測）：

動詞：POST
路徑：/echo/items
query string：
header：
  Accept: */*
  Host: localhost:5062
  User-Agent: curl/8.7.1
  Content-Type: application/json
  Content-Length: 17
body：{"name":"cherry"}

多了兩個 header：Content-Type 說 body 是 JSON，Content-Length 說 body 有 17 個位元組。

瀏覽器的網址列只能送 GET。要送 POST、PUT、DELETE，得用網頁裡的表單或 JavaScript，或改用 Postman、curl 這類可以自己選動詞的工具。

5. 回應長什麼樣

回應的結構和請求一樣是三塊，只有第一行不同：請求的第一行是「要做什麼」，回應的第一行是「結果如何」。curl -v 印出來 < 開頭的是回應。

< HTTP/1.1 200 OK                             ← 第一行：協定版本、狀態碼、說明文字
< Content-Type: text/plain; charset=utf-8     ← header
< Date: Sat, 14 Nov 2026 06:48:58 GMT
< Server: Kestrel
< Transfer-Encoding: chunked
<                                             ← 空一行，後面是 body
動詞：GET
路徑：/echo/hello
…
哪一塊說什麼
狀態碼三位數字，這次請求的結果是哪一種。細節見「HTTP 狀態碼」
header這個回應的附加說明：內容是什麼格式、什麼時候產生的、是哪種伺服器
body回傳的內容：網頁是 HTML，Web API 通常是 JSON。可以沒有

瀏覽器拿到回應之後，看 Content-Type 決定怎麼處理 body：HTML 就畫成網頁，圖片就顯示圖片，JSON 或純文字就直接把文字顯示出來。

6. header：請求和回應的附加說明

header 是一行一個的「名稱: 值」，名稱不分大小寫。種類很多，寫 Web API 常遇到的是這幾個：

header出現在意思
Host請求我要找的主機和 port。同一台機器上可以有很多個網站，伺服器靠它分辨
Content-Type請求、回應body 是什麼格式。JSON 是 application/json
Accept請求我希望回應是什麼格式。*/* 是都可以
User-Agent請求我是哪一種用戶端
Authorization請求我的身分證明，例如登入後拿到的 Token
Cookie／Set-Cookie請求／回應伺服器請瀏覽器記住的小資料，之後每個請求自動帶上。見「Cookie」
Location回應請去這個網址。和 201、301、302 這些狀態碼一起出現
Cache-Control請求、回應這份回應可以留著重複用多久。見「HTTP 快取」

Content-Type 決定伺服器怎麼讀 body

body 只是一串位元組，伺服器要靠 Content-Type 才知道該當成什麼來讀。小網站的 /items 要求 body 是 JSON。同一段內容，只換 Content-Type（實測）：

✗ 說 body 是純文字

POST /items
Content-Type: text/plain

{"name":"cherry"}

→ HTTP/1.1 415 Unsupported Media Type

內容明明是 JSON 的樣子，但請求自己說它是純文字，伺服器就不當 JSON 讀，回 415：這個格式我不收。

✓ 說 body 是 JSON

POST /items
Content-Type: application/json

{"name":"cherry"}

→ HTTP/1.1 200 OK
收到 Item，Name = cherry

伺服器照 JSON 讀，取出 name。

用工具送 JSON 卻收到 415，先檢查 Content-Type。Postman 在 Body 分頁把格式選成 JSON，就會自動加上這個 header。

7. 動詞：重送一次會不會出事

動詞除了表達「要做哪一種事」，還約定了兩個性質。它們決定請求失敗或沒回應時，能不能直接再送一次。

動詞用途會改伺服器上的資料嗎同一個請求送兩次
GET拿資料不會結果一樣，可以放心重送
PUT把某一筆改成指定的內容會結果一樣：第二次還是改成同樣的內容
DELETE刪除某一筆會結果一樣：那一筆最後都是不存在（第二次可能回 404）
POST新增會可能多出一筆

「不會改資料」叫安全（safe），「送幾次結果都一樣」叫冪等（idempotent）。這是約定，伺服器的程式要照著寫才成立：

  • 瀏覽器、快取、搜尋引擎的爬蟲都假設 GET 是安全的，會自己重送、預先讀取。所以不要用 GET 做刪除或修改，例如 GET /items/1/delete
  • 在送出 POST 的頁面按重新整理，瀏覽器會先問「要重新送出表單嗎」，就是因為 POST 重送可能多一筆

8. 伺服器不記得你是誰

HTTP 是無狀態的：每個請求各自獨立，伺服器回應完就結束了。下一個請求進來，伺服器不知道它和上一個是不是同一個人送的。

對小網站連送兩次同樣的請求，終端機印出兩行一模一樣的紀錄，沒有任何東西把它們連在一起：

收到請求：GET /echo/hello
收到請求：GET /echo/hello

這帶來兩件事：

  • 伺服器需要的資訊，每個請求都要自己帶。上一個請求說過的事，這個請求要再說一次
  • 「登入之後就一直是登入狀態」不是 HTTP 本身有的功能。做法是登入時伺服器發一個識別，之後用戶端每個請求都帶上它：放在 Cookie header 或 Authorization header。見「Cookie」

9. 瀏覽器比其他工具多做的事

curl 和 Postman 是你叫它送什麼，它就送什麼。瀏覽器在背後多做了不少事，同一個網址用瀏覽器和用工具打，看到的可能不一樣。

瀏覽器會做的事看得到的現象
自己多送請求打開一個網頁，HTML 裡提到的圖片、CSS、JavaScript 各送一個請求；另外通常還會要網站圖示 /favicon.ico。伺服器的紀錄裡會多出不是你打的網址
自動帶上 headerUser-Agent、Accept、Accept-Language，以及這個網站之前發的 Cookie
看到 3xx 自動跟著去網址列直接變成新的網址，看不到中間那個 301／302
把回應留著重複用（快取）改了伺服器的內容，重新整理卻還是舊的
限制網頁裡的 JavaScript 跨站讀資料Postman 打得通的 API，網頁裡的 JavaScript 卻被擋

用開發人員工具看每一個請求

瀏覽器按 F12 打開開發人員工具，切到 Network（網路）分頁，再重新整理頁面。這個頁面送出的每個請求各佔一列，點進去可以看到請求和回應的第一行、header、body。之後 API 不如預期時，先來這裡看實際送了什麼、回了什麼。

Postman 打得通，網頁卻被擋

瀏覽器有一條規則：網頁裡的 JavaScript 向另一個來源送請求時，伺服器要在回應的 header 裡明確表示允許，瀏覽器才把回應交給 JavaScript。來源是指「協定＋主機＋port」，三個有一個不同就算另一個來源，所以 http://localhost:3000 的網頁呼叫 http://localhost:5062 的 API 也算。

這個機制叫 CORS。它是瀏覽器在擋，不是伺服器在擋，所以 curl、Postman 不受影響。前端網頁和後端 API 分開放在不同網址時，一定會遇到；解法是在後端設定允許哪些來源。

10. HTTP 和 HTTPS

HTTPS 是加密過的 HTTP。請求和回應的內容、格式完全一樣，只是傳送前先加密，中間經過的網路設備看不到內容，也改不了。

HTTPHTTPS
網址開頭http://https://
預設 port80443
傳送的內容明文，中途的人看得到，包含密碼和 Cookie加密
伺服器要準備什麼不用一張憑證，證明「我真的是這個網域的伺服器」

什麼時候用哪一個：

  • 放上網路給別人用的網站和 API，一律用 HTTPS
  • 在自己電腦上開發，用 HTTP 連 localhost 就可以，請求沒有離開這台電腦。這頁的小網站就是這樣
  • 開發時也想用 HTTPS，需要一張開發用的憑證。瀏覽器不認得這張憑證時會顯示「連線不安全」的警告，以 .NET 為例，執行一次 dotnet dev-certs https --trust 讓這台電腦信任它
