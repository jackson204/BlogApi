補充：HTTP 快取（瀏覽器與 CDN 怎麼決定要不要重新要資料）

code review 時被問：「這支是 POST，為什麼還掛 [NoCache]？」要答得出來，得先知道快取發生在哪幾層、誰說了算、POST 和 GET 差在哪。

📌 什麼時候會用到這頁

  • 看到 [ResponseCache]、[NoCache] 這類屬性，不確定它到底擋了什麼
  • 改了資料，畫面卻還是舊的，不知道是哪一層留著舊的那一份

這頁講的是 HTTP 規則本身：回應的 header 怎麼告訴瀏覽器和中間的機器「可不可以存」。伺服器自己把結果存起來重用（OutputCache、IMemoryCache、Redis）是另一件事，留給主線的「深入｜伺服器端快取」。最後有一個小實驗，親眼看哪些請求真的進到伺服器。

1. 一個真實的問題：POST 掛 NoCache 有用嗎

部落格有一支「搜尋我的草稿」的 API。因為搜尋條件多，用 POST 把條件放在 body 裡。寫的人想到「這是登入後才看得到的個人資料，不能被快取」，就照旁邊的 endpoint 加了一行：

[Authorize]
[HttpPost("drafts/search")]
[ResponseCache(NoStore = true, Location = ResponseCacheLocation.None)]   // ← 這一行有必要嗎？
public async Task<List<DraftResponse>> SearchDrafts(DraftSearchRequest request)
{
    // …
}

很多專案會把那一行包成自己的 [NoCache] 屬性，看起來像一個「關掉快取」的開關。它是不是真的關掉了什麼，要拆成三個小問題：

  1. 這一行實際做了什麼？（第 6 節）
  2. 它是寫給誰看的？那個「誰」原本會不會快取這個回應？（第 2、3 節）
  3. 請求是 POST，有沒有差？（第 5 節）

2. 快取發生在哪幾層

「快取」就是把回應存一份，下次同樣的請求來，直接拿存的那份，不再往後問。一個請求從瀏覽器到資料庫，路上有好幾個地方都可以存：

flowchart LR B["① 瀏覽器
只服務這一個人"] --> C["② 中間的機器
CDN、反向代理
很多人共用"] C --> A["③ 你的 API
自己存結果重用"] A --> D[("資料庫")]
越靠左擋下來，後面的機器越省事；但越靠左，你越難叫它把舊的那一份丟掉
哪一層存的東西給誰用誰決定存不存想清掉怎麼辦
① 瀏覽器快取只有這台瀏覽器的這個人。規格裡叫 private cache回應的 header（Cache-Control）你清不到，只能等它過期，或改網址
② CDN、反向代理所有經過它的人。規格裡叫 shared cache回應的 header，加上那台機器自己的設定到 CDN 後台清（purge），或等過期
③ 你的 API 自己存所有打到這台 API 的人你的程式（OutputCache、IMemoryCache、Redis），不看 header你的程式自己清

這頁只講 ① 和 ②。它們有一個共同點：不是你的程式在存，你只能透過回應的 header 告訴它們規則。分不清是哪一層在存，是多數混淆的來源。

💡 共用的那一層最危險。瀏覽器存錯，頂多是這個人看到舊資料；CDN 存錯，可能把 A 的個人資料回給 B。所以規則裡有一個專門的詞 private，意思是「只有瀏覽器可以存，中間共用的機器不行」。

3. 誰說了算：Cache-Control

詞做什麼目的是什麼
Cache-Control回應裡的一個 header，用幾個關鍵字告訴瀏覽器和中間的機器：這份回應能不能存、誰能存、存多久、用之前要不要先問讓「不是你的程式」的那幾層照你的規則做事
Cache-Control: private, max-age=60
               ───┬───  ─────┬────
          只有瀏覽器可以存   60 秒內直接用存的那份
關鍵字意思常見誤會
max-age=6060 秒內是「新鮮的」，可以直接用存的那份，不必問伺服器這 60 秒內你改了資料，對方看到的還是舊的，而且你叫不動它
no-store完全不准存。每次都要重新向伺服器要這才是一般人說的「不要快取」
no-cache可以存，但每次用之前要先問伺服器「我手上這版還能用嗎」（第 4 節）名字像「不快取」，其實不是。最常被搞混的一個
private只有瀏覽器可以存，CDN 這種共用的機器不行不是「加密」或「需要登入」的意思
public共用的機器也可以存個人資料掛上這個會出事
s-maxage=60只給共用的機器看的 max-age，可以和瀏覽器的時間分開設

沒有 Cache-Control 會怎樣

不是「就不快取」。規格允許瀏覽器在沒有明確指示時自己估一個時間，前提是回應帶了 Last-Modified 這類線索。靜態檔案通常有這個 header，所以圖片、CSS 常常沒設也被存起來。API 回的 JSON 多半沒有這些線索，實務上每次都會重新要，第 8 節的實驗裡 /plain 就是這種情況。

📎 補充：帶 Authorization 的請求，共用的機器本來就不該存

規格對共用快取多了一條保護：請求如果帶 Authorization header，回應預設不可以被共用的機器存下來，除非回應明確說可以（public、s-maxage、must-revalidate）。所以用 Bearer token 的 API，就算什麼 header 都沒加，守規矩的 CDN 也不會把 A 的回應拿去給 B。

這條規則只管 Authorization header。用 cookie 登入的網站沒有這層保護，個人資料的回應要自己加 private 或 no-store。cookie 是什麼見 Cookie 那頁第 2 節。

4. 存了但要先問：ETag 與 304

no-cache 說「用之前要先問」，問的方法是：伺服器給每一版內容一個版本編號，瀏覽器下次帶著編號來問。

詞做什麼目的是什麼
ETag回應的 header，值是這版內容的編號，例如 ETag: "v1"。內容變了，編號就要跟著變讓瀏覽器能問「我手上是 v1，還能用嗎」
If-None-Match請求的 header，瀏覽器把手上的編號放在這裡帶回去同上，這是「問」的那一半
304 Not Modified伺服器的回答：「沒變，用你手上那份」。這個回應沒有 body省下傳輸內容的流量。注意伺服器還是被打到了
sequenceDiagram participant B as 瀏覽器 participant S as 你的 API B->>S: GET /etag S-->>B: 200 + 內容 + ETag "v1" + Cache-Control no-cache Note over B: 把內容和編號 v1 一起存起來 B->>S: GET /etag + If-None-Match "v1" S-->>B: 304 Not Modified，沒有內容 Note over B: 拿出存著的那份當作這次的回應
第二次請求伺服器還是有收到，只是不用再把內容傳一次

🔍 實測：第一次拿到內容和編號；第二次帶著編號問，回來的是沒有內容的 304：

GET /etag
HTTP/1.1 200 OK
Content-Length: 61
Content-Type: text/plain; charset=utf-8
Cache-Control: no-cache
ETag: "v1"

etag：伺服器第 1 次處理，這次有把內容送出去

GET /etag　　（這次 header 裡有 If-None-Match: "v1"）
HTTP/1.1 304 Not Modified
Cache-Control: no-cache
ETag: "v1"

所以「快取」省的東西有兩種，別混在一起：

  • max-age 省的是整個請求：新鮮期內瀏覽器根本不發請求，伺服器完全不知道。
  • ETag + 304 省的是傳輸內容：請求照發，伺服器照樣要判斷有沒有變，只是不用回傳 body。

5. GET 和 POST 差在哪

快取的前提是「同樣的請求，可以拿同一份回應」。這個前提對不同的 HTTP 動詞成立的程度不一樣：

動詞意思瀏覽器和 CDN 會不會快取回應
GET、HEAD只是「讀」，打幾次結果都該一樣，不會改到伺服器的東西會，照 Cache-Control 的規則
POST「請伺服器做一件事」，每一次都可能改到東西（發文、下單）實務上不會。就算回應寫了 max-age 也一樣（第 8 節實測）
PUT、DELETE修改、刪除不會。而且成功之後，同一個網址原本存著的 GET 回應會被作廢

POST 不快取的道理很直接：使用者按了兩次「送出」，第二次如果被快取擋掉、沒進伺服器，那這次操作就憑空消失了。就算這支 POST 其實只是在「查詢」，瀏覽器和 CDN 也不知道，它們只看動詞。

📎 補充：規格其實留了一個很窄的例外

HTTP 的快取規格（RFC 9111）沒有把話說死：POST 的回應如果帶了明確的新鮮期，理論上可以拿來回答後續對同一個網址的 GET。但主流瀏覽器和 CDN 都沒有這樣做，所以寫 API 時可以直接當成「POST 不會被瀏覽器和 CDN 快取」。

反過來的副作用倒是要注意：用 POST 做查詢，等於放棄了 ① ② 兩層的快取。資料很少變、很多人查同一份的 API（例如文章列表），用 GET 才吃得到這個好處。

6. ASP.NET Core 的 [ResponseCache] 做了什麼

名字裡有 Cache，但這個屬性本身不存任何東西。它只做一件事：在回應上寫 Cache-Control header。

正式語法

寫法實際寫出的 header意思
[ResponseCache(Duration = 60)]Cache-Control: public,max-age=60瀏覽器和共用的機器都可以存 60 秒。預設是 public
[ResponseCache(Duration = 60, Location = ResponseCacheLocation.Client)]Cache-Control: private,max-age=60只有瀏覽器可以存
[ResponseCache(NoStore = true, Location = ResponseCacheLocation.None)]Cache-Control: no-store,no-cache
Pragma: no-cache		完全不准存。很多專案的 [NoCache] 就是把這一行包起來

第一列和第三列的 header 是第 8 節的程式實際跑出來的（.NET SDK 10.0.303）；第二列是照官方文件寫的，這頁沒有實測。官方文件：ResponseCacheAttribute、Response caching in ASP.NET Core。

GET /attr-nostore
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Cache-Control: no-store,no-cache
Pragma: no-cache

GET /attr-60
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Cache-Control: public,max-age=60

💡 三個名字很像的東西，做的事不同

東西存在哪一層做什麼
[ResponseCache] 屬性不存，只影響 ① ②寫 Cache-Control header
UseResponseCaching() middleware③ 你的 API照 header 的規則，在伺服器存一份。只處理 GET 和 HEAD
UseOutputCache() middleware③ 你的 API照你程式裡的設定存，不看 header。預設也只處理 GET 和 HEAD

後兩個怎麼用，留給主線的「深入｜伺服器端快取」。這裡只要記得：屬性是寫字條給別人看，middleware 才是自己動手存。

7. 回到問題

把第 1 節的三個小問題走一遍：

問題答案依據
那一行實際做了什麼？在回應加上 Cache-Control: no-store,no-cache 和 Pragma: no-cache，沒有別的第 6 節
寫給誰看？對方原本會快取嗎？寫給 ① 瀏覽器和 ② 中間的機器。至於 ③，就算專案開了 OutputCache 或 ResponseCaching，它們也只處理 GET 和 HEAD第 2、6 節
請求是 POST，有差嗎？有。瀏覽器和 CDN 本來就不快取 POST 的回應，有沒有那個 header 結果都一樣第 5 節、第 8 節實測

📌 結論：掛在 POST 上，那一行不會改變任何行為，只是回應多了兩個 header。拿掉它程式比較誠實；留著當作「這是個人資料」的保險也沒有壞處，但別以為是它在保護你。

換成 GET 就不一樣了。回個人資料的 GET，如果登入是靠 cookie，或回應可能經過 CDN，那一行（或 private）就是真的在擋事情。

下次看到這類屬性，可以照同一個順序問：它寫了什麼 header → 哪一層會讀 → 那一層對這個動詞本來怎麼做。

8. 小實驗：數伺服器被打了幾次

快取有沒有生效，看回應內容看不出來，要看伺服器有沒有真的被打到。這個實驗讓每個 endpoint 各自數「我處理了第幾次」：被快取擋掉的請求不會進來，數字就不會加。

一樣用 .NET 10 的單檔程式，寫法見 Cookie 那頁第 6 節。

⚠️ port 別選 5060。瀏覽器有一份「不安全連接埠」清單，5060、5061、6000、6666 等都在裡面，打開會直接顯示 ERR_UNSAFE_PORT，但 curl 打得到，很容易以為是程式壞了。這頁用 5070。

實驗：五個 endpoint，各打兩次

需求：

  • GET /plain：不加任何 header
  • GET /cached：加 Cache-Control: max-age=10
  • GET /no-store：加 Cache-Control: no-store
  • GET /etag：加 ETag: "v1" 和 Cache-Control: no-cache；請求帶的 If-None-Match 等於 "v1" 時回 304
  • POST /post：加 Cache-Control: max-age=10
  • 每個 endpoint 回傳「伺服器第 N 次處理」
  • GET /：回一個網頁，上面有按鈕，按了就用 fetch 打對應的 endpoint，把結果印在頁面上

🧪 先猜再跑：每個 endpoint 連打兩次，第二次的數字會是 1 還是 2？把五個答案寫下來，再用瀏覽器打開 http://localhost:5070/ 驗證。F12 → Network 分頁同時開著，看每個請求的 Size 欄。

💡 提示

需求用什麼
加回應 headercontext.Response.Headers.CacheControl = "max-age=10";、context.Response.Headers.ETag = "\"v1\"";
讀請求 headercontext.Request.Headers.IfNoneMatch

curl 看 headercurl -i http://localhost:5070/cached；帶編號問：curl -i -H 'If-None-Match: "v1"' http://localhost:5070/etag

✅ 驗收：瀏覽器裡 /cached 第二次還是「第 1 次處理」，其餘三個會進伺服器的（/plain、/no-store、/post）第二次是「第 2 次處理」；/etag 第二次在 Network 分頁看到 304

參考答案（寫完再打開）

cache-lab.cs

#:sdk Microsoft.NET.Sdk.Web

WebApplicationBuilder builder = WebApplication.CreateBuilder(args);
WebApplication app = builder.Build();

// 每個 endpoint 各自數「伺服器真的處理了幾次」。被快取擋掉的請求不會進來，數字就不會加
int plain = 0, cached = 0, noStore = 0, etag = 0, post = 0;

// 什麼 header 都不加
app.MapGet("/plain", () => $"plain：伺服器第 {++plain} 次處理");

// 10 秒內可以直接用存起來的那一份
app.MapGet("/cached", (HttpContext context) =>
{
    context.Response.Headers.CacheControl = "max-age=10";
    return $"cached：伺服器第 {++cached} 次處理";
});

// 完全不准存
app.MapGet("/no-store", (HttpContext context) =>
{
    context.Response.Headers.CacheControl = "no-store";
    return $"no-store：伺服器第 {++noStore} 次處理";
});

// 可以存，但每次用之前要先問伺服器「我手上這版還能用嗎」
app.MapGet("/etag", (HttpContext context) =>
{
    etag++;
    const string version = "\"v1\"";
    context.Response.Headers.ETag = version;
    context.Response.Headers.CacheControl = "no-cache";
    if (context.Request.Headers.IfNoneMatch == version)
    {
        return Results.StatusCode(StatusCodes.Status304NotModified);
    }

    return Results.Text($"etag：伺服器第 {etag} 次處理，這次有把內容送出去");
});

// POST：就算回應說「可以存 10 秒」
app.MapPost("/post", (HttpContext context) =>
{
    context.Response.Headers.CacheControl = "max-age=10";
    return $"post：伺服器第 {++post} 次處理";
});

app.MapGet("/", () => Results.Content(Page.Html, "text/html; charset=utf-8"));

app.Run("http://localhost:5070");

public static class Page
{
    public const string Html = """
        <!doctype html>
        <meta charset="utf-8">
        <title>cache lab</title>
        <button onclick="hit('GET', '/plain')">GET /plain</button>
        <button onclick="hit('GET', '/cached')">GET /cached</button>
        <button onclick="hit('GET', '/no-store')">GET /no-store</button>
        <button onclick="hit('GET', '/etag')">GET /etag</button>
        <button onclick="hit('POST', '/post')">POST /post</button>
        <button onclick="twice()">每個各打兩次</button>
        <pre id="out"></pre>
        <script>
        async function hit(method, url) {
          const response = await fetch(url, { method });
          const text = await response.text();
          document.getElementById('out').textContent += method + ' ' + url + ' → ' + response.status + ' ' + text + '\n';
        }
        async function twice() {
          for (const [method, url] of [['GET', '/plain'], ['GET', '/cached'], ['GET', '/no-store'], ['GET', '/etag'], ['POST', '/post']]) {
            await hit(method, url);
            await hit(method, url);
          }
        }
        </script>
        """;
}

curl 不會快取任何東西，所以用 curl 連打 /cached 數字每次都會加。它適合用來看 header，不適合用來看快取有沒有生效：

curl -i http://localhost:5070/cached
# HTTP/1.1 200 OK
# Content-Type: text/plain; charset=utf-8
# Server: Kestrel
# Cache-Control: max-age=10
#
# cached：伺服器第 1 次處理

curl -i -X POST http://localhost:5070/post
# HTTP/1.1 200 OK
# Content-Type: text/plain; charset=utf-8
# Server: Kestrel
# Cache-Control: max-age=10
#
# post：伺服器第 1 次處理

以上輸出是 .NET SDK 10.0.303 加 Edge 實際跑出來的。第 6 節那兩個 [ResponseCache] 的 header，是在同一個程式裡另外加一個 Controller 量到的；想自己看的話，加上 builder.Services.AddControllers()、app.MapControllers()，再寫一個掛著該屬性的 action。

📎 補充：前端自己也有一層快取

這頁講的是瀏覽器照 HTTP 規則做的快取。前端程式自己還可能再疊一層，跟 Cache-Control 無關：

  • 資料抓取套件（TanStack Query、SWR 之類）會把 API 的結果存在記憶體裡，照自己的設定決定多久後重抓。畫面是舊的、Network 分頁卻沒有請求，有可能是它。
  • Service Worker 可以攔下頁面發出的請求，自己決定回什麼，連 POST 都攔得到。它是前端寫的程式，不受這頁的規則限制。

排查「為什麼還是舊的」時，順序是：前端套件 → Service Worker → 瀏覽器 HTTP 快取 → CDN → 你的 API。這兩樣這頁沒有實測。

延伸問題

  1. 文章列表 GET /api/posts 回應加了 Cache-Control: max-age=300。作者發了新文章，自己重新整理列表卻看不到。是哪一層留著舊的？你有辦法叫它丟掉嗎？改用 no-cache 加 ETag 會變成怎樣？
  2. 「我的草稿」是個人資料。如果它是 GET /api/me/drafts，而且登入是靠 cookie，回應應該帶什麼 Cache-Control？private 和 no-store 各自擋掉了什麼？
  3. 有人為了「反正不會被快取」把所有查詢都寫成 POST。這樣做放棄了什麼？哪種查詢適合 GET、哪種不得不用 POST？
