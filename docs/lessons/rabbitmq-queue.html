1. 為什麼慢工作不能做在請求裡

📋 情境：新文章發布後要寄通知給 2,000 位訂閱者。寄一封信大約 50 毫秒，2,000 封就是 100 秒。主管按下「發布」，轉圈圈轉 100 秒，然後 timeout。

直接在 Create 裡寄信，會有三個問題：

  1. 使用者在等：文章早就寫進資料庫了，但要等信全部寄完才回 201
  2. 別人掛了你跟著掛：郵件伺服器當機，發文就失敗，可是發文跟寄信本來是兩件事
  3. 尖峰塞車：同時 10 個人發文，就有 10 個請求各自寄 2,000 封信，API 被自己拖垮

解法是把「要做什麼」和「什麼時候做、誰來做」分開。API 只留一張紙條「文章 5 建立了」，另一個程式再去拿紙條做事：

sequenceDiagram participant F as 前端 participant A as API participant Q as RabbitMQ 佇列 participant W as Worker participant M as 郵件伺服器 F->>A: POST /api/posts A->>A: 寫進資料庫 A->>Q: 訊息：文章 5 建立了 A-->>F: 201 Created（幾十毫秒） Note over Q: 紙條先放著 Q->>W: 送出訊息 W->>M: 寄 2,000 封信（100 秒） W-->>Q: ack：做完了
前端只等「寫進資料庫 + 丟一張紙條」；寄信在另一個程式裡慢慢做，掛了也不影響發文

這和 async/await 不一樣。await 只是「等的時候不占用執行緒」，請求還是要等到事情做完才回應；佇列是「這個請求根本不做這件事」，做事的是另一個程式，可以晚一點、可以在另一台機器、可以開三個一起做。

2. 原理：Producer、Queue、Consumer，還有 ack 和 durable

三個角色

角色在 BlogApi 裡做什麼
Producer（生產者）API 的 PostsController.Create把訊息送進佇列，送完就走
Broker（RabbitMQ 本身）Docker 裡的 blog-rabbitmq獨立的程式，負責保管訊息、分配給 consumer、追蹤誰做完了
Consumer（消費者）Worker 專案的 PostCreatedConsumer向 broker 訂閱佇列，收到就處理，處理完回報

訊息本身只是一串 bytes，RabbitMQ 不管內容。我們放 JSON，兩邊用同一個 record 序列化和反序列化。

exchange 這個字先講一點點

Producer 其實不是直接送進佇列，是送給一個叫 exchange 的東西，由它依 routing key 決定丟進哪個佇列。這頁只用 default exchange（名字是空字串）：它的規則是「routing key 等於佇列名稱」，所以 routingKey: "post-created" 就是直接送進 post-created 佇列。其他種類的 exchange（一封訊息廣播給多個佇列、照樣式分流）在延伸問題。

ack：broker 怎麼知道你做完了

訂閱時有一個選擇 autoAck：

意思Worker 處理到一半當掉
autoAck: true訊息一送到 consumer 就算完成訊息丟了
autoAck: falseconsumer 處理完要自己回報 BasicAck；沒回報的訊息 broker 會留著連線斷掉時訊息回到佇列，下一個 consumer 再收到一次，而且 Redelivered = true

所以用 autoAck: false 的代價是：同一封訊息可能收到兩次（做到一半當掉，重啟後再來一次）。這叫 at-least-once。你的處理要能承受重做，叫冪等：寄信前先查「這篇文章的通知寄過了沒」，寄過就跳過。

處理失敗時不 ack，改回 BasicNack，而且要決定 requeue：true 是退回佇列馬上重送，false 是不要了（有 dead-letter 設定時會被轉送到別的佇列）。題 6 會看到 true 有多可怕。

prefetch：一次拿幾封

預設 broker 會把佇列裡的訊息一股腦塞給 consumer。BasicQos(prefetchCount: 1) 是「我手上還有沒 ack 的訊息時，不要再給我」。開兩個 Worker 時，這讓忙的那個不會囤貨，閒的那個拿得到（實驗 C）。

durable 和 persistent：broker 重啟後還在嗎

兩個開關，缺一不可：

開關設在哪意思
durable: true宣告佇列時佇列本身撐得過 broker 重啟。RabbitMQ 4 開始，非 durable 的佇列預設不准建（題 5 有錯誤原文）
Persistent = true每一封訊息的 properties訊息寫到磁碟。沒設的話佇列還在、訊息沒了（題 5 實測）

連線和 channel

  • Connection：一條 TCP 連線，建立很貴（要握手、驗證）。整個程式開一條、一直用
  • Channel：連線裡面的邏輯通道，很便宜，但不能跨執行緒共用。API 每次發布開一個、用完關掉；Worker 開一個一直收

Management UI 看什麼

http://localhost:15672（帳號密碼都是 guest）。Queues 頁面三個數字：

欄位意思
Ready在佇列裡等著被拿走的訊息數
Unacked已經送給 consumer、還沒收到 ack 的訊息數
Total兩個加起來

點進某個佇列，最下面有 Get messages（偷看內容和 headers）和 Delete queue（題 5、6、7 改宣告參數前都要先刪）。數字每 5 秒才更新一次，剛送完馬上看會是舊的。

3. 用法：RabbitMQ.Client 7 的寫法

RabbitMQ.Client 7 全部是 async，方法都有 Async 結尾，網路上 6.x 的範例（CreateModel()、BasicPublish()）已經不能用，看到要換成下面這些：

要做什麼寫法
建連線var factory = new ConnectionFactory { HostName = "localhost" };
var connection = await factory.CreateConnectionAsync();
開 channelawait using var channel = await connection.CreateChannelAsync();
宣告佇列await channel.QueueDeclareAsync("post-created", durable: true, exclusive: false, autoDelete: false, arguments: null);
宣告是「確保存在」，重複宣告沒關係，但參數要一樣（實驗 D）
發訊息var props = new BasicProperties { Persistent = true, ContentType = "application/json" };
await channel.BasicPublishAsync(exchange: "", routingKey: "post-created", mandatory: false, basicProperties: props, body: bytes);
一次拿一封await channel.BasicQosAsync(prefetchSize: 0, prefetchCount: 1, global: false);
訂閱var consumer = new AsyncEventingBasicConsumer(channel);
consumer.ReceivedAsync += async (sender, ea) => { … };
await channel.BasicConsumeAsync("post-created", autoAck: false, consumer);
回報做完await channel.BasicAckAsync(ea.DeliveryTag, multiple: false);
回報失敗await channel.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: false);
訊息內容ea.Body.Span 是 bytes；JsonSerializer.Deserialize<PostCreatedMessage>(ea.Body.Span)
佇列參數（題 6、7）arguments: new Dictionary<string, object?> { ["x-dead-letter-exchange"] = "", ["x-dead-letter-routing-key"] = "post-created.dead" }

訊息類別兩邊各放一份一模一樣的，JSON 的屬性名稱對得上就能互通：

public record PostCreatedMessage(int PostId, string Title, DateTime CreatedAt);

只放 Worker 需要的欄位，不要把整個 Post Entity 丟進去：Entity 之後會長出導覽屬性（02a），序列化會出事，而且訊息越大 broker 越慢。

BlogApi/Messaging/PostEventPublisher.cs

using System.Text.Json;
using RabbitMQ.Client;
using RabbitMQ.Client.Exceptions;

namespace BlogApi.Messaging;

// 註冊成 singleton：整個程式共用一條連線。連線是第一次發布時才建立的
public class PostEventPublisher : IAsyncDisposable
{
    private readonly ConnectionFactory _factory = new() { HostName = "localhost" };
    private readonly ILogger<PostEventPublisher> _logger;
    private readonly SemaphoreSlim _connectLock = new(1, 1);
    private IConnection? _connection;

    public PostEventPublisher(ILogger<PostEventPublisher> logger)
    {
        _logger = logger;
    }

    public async Task PublishPostCreatedAsync(PostCreatedMessage message)
    {
        try
        {
            var connection = await GetConnectionAsync();

            // channel 便宜，而且不能跨執行緒共用，所以每次發布開一個、用完關掉
            await using var channel = await connection.CreateChannelAsync();
            await channel.QueueDeclareAsync("post-created", durable: true, exclusive: false, autoDelete: false, arguments: null);

            var body = JsonSerializer.SerializeToUtf8Bytes(message);
            var props = new BasicProperties
            {
                Persistent = true,
                ContentType = "application/json"
            };

            // exchange 留空字串 = default exchange，routing key 就是佇列名稱
            await channel.BasicPublishAsync(
                exchange: "",
                routingKey: "post-created",
                mandatory: false,
                basicProperties: props,
                body: body);

            _logger.LogInformation("已送出 PostCreated：文章 {PostId}", message.PostId);
        }
        catch (BrokerUnreachableException ex)
        {
            // 連不上 RabbitMQ 不讓發文失敗，但要留下痕跡
            _logger.LogWarning(ex, "RabbitMQ 連不上，文章 {PostId} 的通知沒有送出", message.PostId);
        }
    }

    private async Task<IConnection> GetConnectionAsync()
    {
        if (_connection is { IsOpen: true })
        {
            return _connection;
        }

        // 兩個請求同時第一次發文時，只讓一個去建連線
        await _connectLock.WaitAsync();
        try
        {
            if (_connection is { IsOpen: true })
            {
                return _connection;
            }

            _connection = await _factory.CreateConnectionAsync();
            return _connection;
        }
        finally
        {
            _connectLock.Release();
        }
    }

    public async ValueTask DisposeAsync()
    {
        if (_connection is not null)
        {
            await _connection.DisposeAsync();
        }
    }
}

BlogApi.Worker/PostCreatedConsumer.cs

using System.Text.Json;
using RabbitMQ.Client;
using RabbitMQ.Client.Events;

namespace BlogApi.Worker;

// 括號裡的 logger 是 C# 12 的「主要建構子」寫法，範本的 Worker.cs 就是這樣寫的，等於宣告欄位加一個建構子
public class PostCreatedConsumer(ILogger<PostCreatedConsumer> logger) : BackgroundService
{
    private IConnection? _connection;
    private IChannel? _channel;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var factory = new ConnectionFactory { HostName = "localhost" };
        _connection = await factory.CreateConnectionAsync(stoppingToken);
        _channel = await _connection.CreateChannelAsync(cancellationToken: stoppingToken);

        // 和 API 宣告一模一樣的佇列。誰先啟動都沒關係，先到的建、後到的確認
        await _channel.QueueDeclareAsync("post-created", durable: true, exclusive: false, autoDelete: false,
            arguments: null, cancellationToken: stoppingToken);

        // 一次只拿一封，處理完（ack）才拿下一封
        await _channel.BasicQosAsync(prefetchSize: 0, prefetchCount: 1, global: false, stoppingToken);

        var consumer = new AsyncEventingBasicConsumer(_channel);
        consumer.ReceivedAsync += async (sender, ea) =>
        {
            var message = JsonSerializer.Deserialize<PostCreatedMessage>(ea.Body.Span)!;
            logger.LogInformation("收到：文章 {PostId}「{Title}」Redelivered={Redelivered}",
                message.PostId, message.Title, ea.Redelivered);

            await Task.Delay(2000, stoppingToken); // 模擬寄通知的慢工作
            logger.LogInformation("寄通知完成：文章 {PostId}", message.PostId);

            // 回報做完，broker 才會把這封從佇列拿掉
            await _channel.BasicAckAsync(ea.DeliveryTag, multiple: false);
        };

        await _channel.BasicConsumeAsync("post-created", autoAck: false, consumer, stoppingToken);
        logger.LogInformation("開始等待訊息");

        // 一直等到程式被要求停止
        await Task.Delay(Timeout.Infinite, stoppingToken);
    }

    public override void Dispose()
    {
        _channel?.Dispose();
        _connection?.Dispose();
        base.Dispose();
    }
}

題 4：ack 的意義：做到一半當掉會怎樣

需求：把 Worker 的 Task.Delay 暫時改成 10 秒（比較來得及按）。發一篇文章，看到 Worker 印「收到」之後、「寄通知完成」之前，停掉 Worker（Ctrl+C 或直接關掉視窗都一樣）。先猜：訊息還在嗎？再啟動 Worker 一次，看印出什麼。

✅ 驗收：Worker 停掉後 UI 的 Ready 又變回 1；重新啟動後再次收到同一篇，Redelivered=True

參考答案（寫完再打開）

Worker 停掉後，UI 的 post-created：Ready = 1、Unacked = 0。沒 ack 的訊息在連線斷掉時被 broker 收回去了。重新啟動：

17:12:08 info: BlogApi.Worker.PostCreatedConsumer[0]
      收到：文章 5「Docker 入門」Redelivered=True

同一封訊息、第二次收到，Redelivered 從 False 變 True。這就是 at-least-once：寧可多做一次，不要漏做。所以寄通知的程式要能承受「同一篇寄兩次」：

  • 最簡單：寄之前先查「文章 5 的通知寄過了嗎」（例如一張 Notifications 表記 PostId），寄過就直接 ack
  • Redelivered 只能告訴你「這封以前送過」，不能告訴你「以前做到哪」，所以不能拿它當依據

反過來想：如果當初用 autoAck: true，訊息在送到 Worker 的瞬間就算完成，Ctrl+C 之後它就消失了，通知永遠不會寄出。

做完把 Delay 改回 2 秒。

題 5：durable 和 persistent 的意義：broker 重啟會怎樣

需求，分三段：

  1. 照題 2 的設定（durable + Persistent）發一篇，Worker 不要開，docker restart blog-rabbitmq，等 UI 回來看 Ready
  2. API 的 Persistent = false，再做一次。這只改訊息的屬性，佇列不用動

第 1 段：5 秒內 Worker 收到同一封 10,246 次。requeue: true 是「退回佇列、馬上重送」，寄信伺服器壞了的話它就會一直壞，這封訊息在 broker 和 Worker 之間彈跳到天荒地老，而且其他正常的訊息都排在它後面。requeue: true 只適合「這台 Worker 暫時不能做，換一台做」的情況，不適合「這封訊息本身有問題」。

BlogApi/Messaging/RabbitMqTopology.cs（Worker 專案放一份一樣的，namespace 改掉）

using RabbitMQ.Client;

namespace BlogApi.Messaging;

// 佇列的宣告集中在這裡。Worker 專案放一份一模一樣的，兩邊宣告的參數才會一致
public static class RabbitMqTopology
{
    public const string PostCreatedQueue = "post-created";
    public const string DeadQueue = "post-created.dead";

    public static async Task DeclareAsync(IChannel channel)
    {
        // dead 佇列：沒有參數。要先宣告，因為 dead-letter 的目的地不存在時 broker 會直接把訊息丟掉
        await channel.QueueDeclareAsync(DeadQueue, durable: true, exclusive: false, autoDelete: false, arguments: null);

        await channel.QueueDeclareAsync(PostCreatedQueue, durable: true, exclusive: false, autoDelete: false,
            arguments: new Dictionary<string, object?>

                ["x-dead-letter-exchange"] = "",
                ["x-dead-letter-routing-key"] = DeadQueue
            });
    }
}

題 7：自動重試：等 5 秒再試，三次都失敗才放棄

寄信伺服器通常只是暫時抽筋，等幾秒再試就好了。RabbitMQ 沒有內建「延遲重送」，但可以用兩個現成的功能拼出來：訊息 TTL（放太久自動過期）和 dead-letter（過期的訊息轉送到別處）。

flowchart LR A["post-created
主佇列"] -- "nack(requeue:false)
dead-letter 到" --> R["post-created.retry
x-message-ttl = 5000"] R -- "5 秒後過期
dead-letter 回" --> A A -- "第 3 次還失敗
Worker 自己發到" --> D["post-created.dead"]
失敗的訊息先去 retry 佇列躺 5 秒，過期後自動回到主佇列再試；試滿三次 Worker 把它送進 dead 佇列

需求：

  1. RabbitMqTopology 改成三個佇列：post-created.dead 沒參數；post-created.retry 有 x-message-ttl = 5000 而且 dead-letter 回 post-created；post-created 的 dead-letter 改指到 post-created.retry。兩個專案都要改
  2. Worker 的 catch：讀 x-death 裡 queue 是 post-created、reason 是 rejected 那筆的 count。小於 3 就 BasicNackAsync(requeue: false)（會進 retry）；大於等於 3 就自己 BasicPublishAsync 到 dead 佇列、然後 BasicAckAsync 把原本那封收掉
  3. 先在 UI 刪掉 post-created，重啟 API 和 Worker，發一篇「這篇會炸」，看 Worker 視窗 20 秒

💡 提示：x-death 的型別很醜：ea.BasicProperties.Headers["x-death"] 是 List<object?>，每個元素是 Dictionary<string, object?>，字串值是 byte[]，count 是 long。寫一個小方法把它讀出來。

✅ 驗收：Worker 視窗每 5 秒收到一次，共 4 次（第一次加三次重試），最後一條 warn「放進 dead 佇列」；UI 的 post-created.dead Ready = 1

BlogApi/Messaging/RabbitMqTopology.cs（Worker 一樣改）

public static class RabbitMqTopology
{
    public const string PostCreatedQueue = "post-created";
    public const string RetryQueue = "post-created.retry";
    public const string DeadQueue = "post-created.dead";

    public static async Task DeclareAsync(IChannel channel)
    {
        await channel.QueueDeclareAsync(DeadQueue, durable: true, exclusive: false, autoDelete: false, arguments: null);

        // retry 佇列：訊息放 5 秒就過期，過期後轉回主佇列
        await channel.QueueDeclareAsync(RetryQueue, durable: true, exclusive: false, autoDelete: false,
            arguments: new Dictionary<string, object?>
            {
                ["x-message-ttl"] = 5000,
                ["x-dead-letter-exchange"] = "",
                ["x-dead-letter-routing-key"] = PostCreatedQueue
            });

        // 主佇列：被 nack(requeue:false) 的訊息轉送到 retry 佇列
        await channel.QueueDeclareAsync(PostCreatedQueue, durable: true, exclusive: false, autoDelete: false,
            arguments: new Dictionary<string, object?>
            {
                ["x-dead-letter-exchange"] = "",
                ["x-dead-letter-routing-key"] = RetryQueue
            });
    }
}

BlogApi.Worker/PostCreatedConsumer.cs（catch 和新方法）

catch (InvalidOperationException ex)
{
    logger.LogError(ex, "處理文章 {PostId} 失敗", message.PostId);

    if (DeathCount(ea) >= 3)
    {
        // 試過三次了，自己送到 dead 佇列，然後 ack 把原本那封收掉。
        // 把原本的 properties（含 x-death 履歷）一起帶過去，之後查案才知道它死過幾次
        await _channel.BasicPublishAsync(exchange: "", routingKey: RabbitMqTopology.DeadQueue,
            mandatory: false, basicProperties: new BasicProperties(ea.BasicProperties), body: ea.Body);
        await _channel.BasicAckAsync(ea.DeliveryTag, multiple: false);
        logger.LogWarning("文章 {PostId} 重試 3 次都失敗，放進 dead 佇列", message.PostId);
    }
    else
    {
        // 進 retry 佇列，5 秒後會回來
        await _channel.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: false);
    }
}

// x-death 是一個陣列，每個元素是一次死亡紀錄；找主佇列、原因是 rejected 的那筆，count 就是被退回幾次
private static long DeathCount(BasicDeliverEventArgs ea)
{
    if (ea.BasicProperties.Headers is null ||
        !ea.BasicProperties.Headers.TryGetValue("x-death", out var raw) ||
        raw is not List<object?> deaths)
    {
        return 0;
    }

    foreach (var item in deaths)
    {
        if (item is Dictionary<string, object?> death &&
            death.TryGetValue("queue", out var q) && q is byte[] qb &&
            Encoding.UTF8.GetString(qb) == RabbitMqTopology.PostCreatedQueue &&
            death.TryGetValue("reason", out var r) && r is byte[] rb &&
            Encoding.UTF8.GetString(rb) == "rejected" &&
            death.TryGetValue("count", out var c) && c is long count)
        {
            return count;
        }
    }

    return 0;
}

5. 故意弄壞：四個實驗

每個先猜結果，再動手，最後打開答案。做完記得改回來。

實驗 A：RabbitMQ 沒開就發文

docker stop blog-rabbitmq，重啟 API，POST 一篇。猜：API 起得來嗎？發文會回什麼？

答案

API 照常啟動、POST 照樣 201，文章在資料庫裡。只有 Run 視窗多一條 Warning：

warn: BlogApi.Messaging.PostEventPublisher[0]
      RabbitMQ 連不上，文章 8 的通知沒有送出
      RabbitMQ.Client.Exceptions.BrokerUnreachableException: None of the specified endpoints were reachable
       ---> System.AggregateException: One or more errors occurred. (Connection failed, host 127.0.0.1:5672)
       ---> RabbitMQ.Client.Exceptions.ConnectFailureException: Connection failed, host 127.0.0.1:5672

這是題 2 刻意的設計：連線在第一次發布時才建、連不上就 catch。代價是這封訊息丟了，文章 8 的通知永遠不會寄。要不要接受這個代價，是產品決定，不是技術決定：

  • 通知可以漏：現在這樣就好，log 有留痕跡
  • 通知不能漏：把「要發的訊息」先寫進資料庫的一張表（跟文章同一個交易），另一個背景工作再把表裡的東西送進 RabbitMQ。這叫 outbox pattern，在延伸問題

做完 docker start blog-rabbitmq。

實驗 B：autoAck: false 但忘了 ack

把 Worker 的 BasicAckAsync 那行註解掉，啟動 Worker，連發兩篇正常的文章。猜：Worker 收到幾封？UI 的 Ready 和 Unacked 各是多少？

答案

Worker 只收到第一封，印完「寄通知完成」就再也沒動靜。UI：Ready = 1、Unacked = 1。

因為 prefetch 是 1：手上有一封沒 ack 的，broker 就不給下一封。忘了 ack 等於 Worker 把自己卡死，而且沒有任何錯誤。把 Worker 停掉，Ready 變回 2（那封沒 ack 的被收回去了）。

沒設 prefetch 的話症狀不一樣：Worker 會一直收，Unacked 一直漲，直到 Worker 記憶體爆掉。兩種都是「處理完一定要 ack 或 nack」沒做到。

實驗 C：開兩個 Worker

開兩個終端機各跑一個 Worker（dotnet run --project BlogApi.Worker 兩次），連發四篇文章。猜：誰收到哪幾封？

答案 
Worker 1：收到：文章 24    收到：文章 26
Worker 2：收到：文章 25    收到：文章 27

輪流分配（round-robin）。同一個佇列可以有很多 consumer，每封訊息只會給其中一個。這就是「放大」的方法：寄信太慢，多開幾個 Worker 就好，API 一行都不用改。

prefetch 1 在這裡的作用：如果 Worker 1 拿到一封要做 100 秒的，接下來的訊息會全部給 Worker 2，而不是平均分配然後卡在 Worker 1 後面排隊。

實驗 D：宣告的參數和既有佇列不一樣

重做一次題 6 的第 2 段，但這次跳過「先刪佇列」那一步：佇列還是題 2 建的那個（沒有參數），程式碼已經改成有 dead-letter 參數的宣告，直接啟動 API 發文。猜：會怎樣？

答案

發文回 500，Run 視窗：

RabbitMQ.Client.Exceptions.OperationInterruptedException: The AMQP operation was interrupted: AMQP close-reason, initiated by Peer, code=406, text='PRECONDITION_FAILED - inequivalent arg 'x-dead-letter-exchange' for queue 'post-created' in vhost '/': received the value '' of type 'longstr' but current is none', classId=50, methodId=10

佇列一旦建好，參數就不能改；再宣告一次必須一模一樣，不然 broker 會關掉你的 channel。received the value '' … but current is none 在講：你這次送來 x-dead-letter-exchange = ""，但現有的佇列沒有這個參數。反過來（佇列有參數、程式碼沒有）也一樣會炸，只是訊息裡的 received 和 current 對調。

這就是題 5、6、7 一直要你「先刪佇列」的原因。正式環境不能隨便刪佇列（裡面有訊息），所以 RabbitMQ 建議佇列參數用 policy（在 broker 端設定）而不是寫死在程式裡，policy 可以改、程式碼宣告不行。這頁用程式碼宣告是為了讓你看到參數長什麼樣。

7. 延伸問題

  1. MassTransit 是什麼？在 RabbitMQ.Client 上面再包一層：你寫 IConsumer<PostCreated> 類別和 Publish(message)，它幫你宣告 exchange 和佇列、序列化、重試、dead-letter（它叫 _error 佇列）。公司用它的話，這頁的每個概念都還在，只是名字換了。
  2. 一封訊息要給好幾個 Worker（寄信的、推播的、算統計的）？這頁的佇列是「一封只給一個 consumer」。要廣播就要 fanout exchange：producer 送給 exchange，exchange 複製到綁定的每個佇列，每個佇列各自有 consumer。要照條件分流是 topic exchange。
  3. 發文成功但訊息沒送出（實驗 A）怎麼保證不漏？outbox pattern：訊息先寫進資料庫的 OutboxMessages 表，和文章同一個 SaveChangesAsync；背景工作每秒掃一次表、送進 RabbitMQ、標記已送。資料庫成功就一定會送到，代價是晚幾秒。
  4. Kafka、Azure Service Bus 和 RabbitMQ 差在哪？Service Bus 是雲端代管的同一類東西，概念幾乎一樣。Kafka 不是佇列是「日誌」：訊息不會因為被消費而消失，consumer 自己記讀到哪，適合大量事件流和重播。
  5. 兩邊各放一份 PostCreatedMessage 很醜？開一個 class library 專案 BlogApi.Contracts，兩邊都參考它。訊息格式要改時只改一處，但改了之後兩邊要一起部署，這是另一個課題。
  6. Worker 做完想通知瀏覽器「通知已寄出」？Worker 不是 Web 程式，碰不到瀏覽器。要經過 API（Worker 呼叫 API 的端點，API 再用 SignalR 推）或 SignalR 的 backplane。SignalR 在下一頁。
