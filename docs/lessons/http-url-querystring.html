網址與 query string（一條網址怎麼讀）

https://example.com/api/posts/5?keyword=docker&page=2 這串字怎麼讀？哪幾段用來找到伺服器、哪幾段真的送給伺服器、? 後面那串的規則是什麼、值裡有空白或中文怎麼辦？這頁不用寫程式，最後有一個現成的小網站可以親眼看每種寫法。

1. 一條網址拆成幾段

先看一條完整的網址。瀏覽器網址列看到的是整條，但伺服器收到的只有其中兩段。

https://example.com:5107/api/posts/5?keyword=docker&page=2#top
\___/   \_________/ \__/\__________/ \___________________/ \_/
 [1]        [2]      [3]     [4]              [5]          [6]
段名稱這一段在說什麼誰會用到它
[1]協定（scheme）https用哪一套規則溝通：http，或加密的 https瀏覽器決定怎麼建立連線
[2]主機（host）example.com要連到哪一台電腦瀏覽器查 DNS、建立連線；伺服器從 Host header 看到它
[3]port 5107那台電腦上的哪一個門。省略時 https 是 443、http 是 80瀏覽器
[4]路徑（path）/api/posts/5對哪個資源：第 5 篇文章伺服器用它決定這個請求要執行哪一段程式
[5]query string keyword=docker&page=2附加條件：怎麼篩、怎麼排、第幾頁伺服器的程式拿來當作條件
[6]fragment top頁面裡的某個位置，例如跳到某個標題只有瀏覽器用，不會送給伺服器

真正送到伺服器的是哪幾段

瀏覽器送出請求時，會把網址拆開放進 HTTP 請求的不同位置：

GET /api/posts/5?keyword=docker&page=2 HTTP/1.1
Host: example.com:5107

顏色和上面的六段一樣。協定和fragment沒有出現在請求裡。

  • 第一行「動詞 路徑?query string」：路徑和 query string 連在一起送
  • 主機和 port 變成 Host header
  • 協定決定連線要不要加密，不會出現在請求內容裡
  • fragment 不會送出。不是伺服器丟掉的，而是瀏覽器（或 curl）在送出前就把它拿掉了

實測。對第 4 節的小網站用 curl -v 送請求，它會把實際送出的請求行印出來（> 開頭的那幾行）：

curl -v -s "http://localhost:5060/echo?x=1#top"
# > GET /echo?x=1 HTTP/1.1
# > Host: localhost:5060
#
# 伺服器印回來的：
# Path        : /echo
# QueryString : ?x=1

2. query string 的格式：?、名稱=值、&

query string 從路徑後面的第一個 ? 開始，到網址結尾（或 # 之前）。裡面是一組或多組「名稱=值」，組和組之間用 & 連接。下表每一列的右欄，是伺服器把 query string 拆開後實際得到的東西，用第 4 節的小網站測的：

規則寫法伺服器拆出來的（實測）
一組就是「名稱=值」，多組用 & 連接?keyword=docker&page=2keyword → ["docker"]
page → ["2"]
名稱和值都是文字。2 拆出來是字串 "2"，要當成數字用，是伺服器的程式收到之後才做的事?page=2page → ["2"]
同一個名稱可以出現很多次，會變成多個值?tag=a&tag=btag → ["a", "b"]，count=2
值可以是空的，名稱還是會被拆出來?keyword=keyword → [""]，count=1
名稱的大小寫原樣保留。要不要分大小寫，由伺服器的程式決定?Keyword=dockerKeyword → ["docker"]
「沒有 query string」和「只有問號」是兩回事/echo
/echo?		QueryString 是空字串
QueryString 是 ?，但一組都拆不出來

路徑和 query string 的分工

兩段都在同一行裡送出，但回答的問題不同：

路徑query string
回答的問題對哪個資源用什麼條件：篩選、排序、分頁
能不能省略不行。少一段就是另一條路徑，伺服器不認得就回 404可以。沒帶就是「不加這個條件」
誰決定它長什麼樣寫 API 的人事先定好有哪些路徑寫 API 的人事先定好認得哪些名稱
例子/api/posts/5：第 5 篇?keyword=docker：標題含 docker
?page=2：第 2 頁

為什麼搜尋不寫成 /api/posts/docker

把要搜尋的字直接接在路徑後面，看起來也能用。先照路徑的讀法，把三條網址各讀一次：

/api/posts/5                     文章裡，編號 5 的那一篇
/api/posts/docker                文章裡，叫 docker 的那一篇？
/api/posts?keyword=docker        文章裡，標題含 docker 的那些

綠色是路徑，橘色是 query string。搜尋放在路徑裡有兩個問題：

  1. 意思不對。路徑的每一段都在指認一個東西，/api/posts/5 是第 5 篇。照同樣的讀法，/api/posts/docker 是「叫 docker 的那一篇」；但搜尋要的是「標題含 docker 的那些」，可能很多篇，也可能一篇都沒有。
  2. 和「查某一篇」撞在一起。伺服器通常已經約定 /api/posts/ 後面那一段是文章編號。送 /api/posts/docker 過去，伺服器會把 docker 當成編號來處理；它不是數字，所以得到的是錯誤（404 或 400），不是搜尋結果。

✗ 搜尋的字放在路徑

GET /api/posts/docker

被讀成「編號是 docker 的那一篇」。伺服器找不到這樣的編號，回錯誤。

✓ 搜尋的字放在 query string

GET /api/posts?keyword=docker

路徑還是「文章」，條件另外寫在後面。條件可有可無：不帶就是 /api/posts，全部的文章。

第 2 個問題什麼時候是 404、什麼時候是 400，和伺服器的程式怎麼寫有關，做完熱身再看：路徑裡的值轉不成數字時

3. 值裡有空白、中文、& 的時候

空白、&、=、?、# 在網址裡各有工作（分隔參數、分隔名稱和值、開始 query string、開始 fragment），中文則不在網址允許的字元範圍內。這些字要放進值裡，得先寫成 % 加兩位十六進位的形式（百分比編碼）。這裡只看 query string 最常遇到的幾種寫法，右欄是伺服器解開之後拿到的值：

送出的寫法伺服器拿到的值（實測）說明
?keyword=hello%20worldhello world空白的標準寫法
?keyword=hello+worldhello worldquery string 裡 + 也會被當成空白，這是表單送出時留下的慣例。值裡真的要一個加號，要寫 %2B
?keyword=a%26ba&b值裡的 & 要寫成 %26
?keyword=a&ba，另外多出一組名稱 b、值是空的沒編碼的 & 會被當成分隔符號
?keyword=%E5%85%A5%E9%96%80入門中文每個字變成 3 個 %XX（UTF-8），解碼回來還是原字

在瀏覽器網址列直接打空白或中文，瀏覽器送出前會自動換成 %XX 的寫法，不用自己算。&、#、+ 這些本來就有工作的符號不會自動換，要放進值裡得自己寫成 %26、%23、%2B。

4. 小實驗：用現成的小網站看每種寫法

前面所有實測輸出都來自這個小網站。它只有一條路徑 /echo，把收到的主機、路徑、query string，以及 query string 拆開之後的每一組「名稱 → 值」印回來。程式不用看懂，照著存檔、執行就好（.NET 10）。

url-lab.cs

#:sdk Microsoft.NET.Sdk.Web
using Microsoft.Extensions.Primitives;

WebApplicationBuilder builder = WebApplication.CreateBuilder(args);
WebApplication app = builder.Build();

// 把收到的 Host、路徑、原始 query string、拆開後的每一組名稱=值印回來
app.MapGet("/echo", (HttpContext context) =>
{
    HttpRequest request = context.Request;
    List<string> lines = new List<string>();
    lines.Add("Host        : " + request.Host);
    lines.Add("Path        : " + request.Path);
    lines.Add("QueryString : " + request.QueryString.Value);
    foreach (KeyValuePair<string, StringValues> pair in request.Query)
    {
        string values = string.Join(", ", pair.Value.Select(v => "\"" + v + "\""));
        lines.Add("  " + pair.Key + " -> [" + values + "]  count=" + pair.Value.Count);
    }
    return string.Join("\n", lines);
});

app.Run("http://localhost:5060");
# 放在任何「沒有 .csproj」的資料夾。按 Ctrl+C 停止
dotnet run url-lab.cs

跑起來之後，在瀏覽器網址列輸入 http://localhost:5060/echo?keyword=docker&page=2，或在另一個終端機用 curl（Windows 的 PowerShell 裡打 curl.exe）。把 ? 後面換成下面每一種寫法，對照第 2、3 節的表格：

curl "http://localhost:5060/echo?keyword=docker&page=2"
# Host        : localhost:5060
# Path        : /echo
# QueryString : ?keyword=docker&page=2
#   keyword -> ["docker"]  count=1
#   page -> ["2"]  count=1

curl "http://localhost:5060/echo?tag=a&tag=b"
#   tag -> ["a", "b"]  count=2

curl "http://localhost:5060/echo?keyword="
#   keyword -> [""]  count=1

curl "http://localhost:5060/echo?keyword=a&b"
#   keyword -> ["a"]  count=1
#   b -> [""]  count=1

curl "http://localhost:5060/echo?Keyword=docker"
#   Keyword -> ["docker"]  count=1

curl "http://localhost:5060/echo"
# QueryString :                  ← 空字串
curl "http://localhost:5060/echo?"
# QueryString : ?                ← 只有問號，一組都拆不出來

curl "http://localhost:5060/echo?keyword=hello%20world"
#   keyword -> ["hello world"]  count=1
curl "http://localhost:5060/echo?keyword=hello+world"
#   keyword -> ["hello world"]  count=1
curl "http://localhost:5060/echo?keyword=a%26b"
#   keyword -> ["a&b"]  count=1
curl "http://localhost:5060/echo?keyword=%E5%85%A5%E9%96%80"
#   keyword -> ["入門"]  count=1

curl -v -s "http://localhost:5060/echo?x=1#top"
# > GET /echo?x=1 HTTP/1.1          ← curl 送出去的時候 #top 已經不在了
# > Host: localhost:5060
# QueryString : ?x=1
#   x -> ["1"]  count=1

要親眼看到的四件事：

  • ?tag=a&tag=b：同一個名稱出現兩次，印出 count=2
  • ?keyword=a&b：沒編碼的 & 被當成分隔符號，多出一組名稱 b
  • ?keyword=hello+world：伺服器拿到的是 hello world
  • /echo?x=1#top：#top 不會出現在伺服器收到的 query string 裡

query string 進到程式之後，怎麼變成方法的參數、沒帶的時候參數是什麼，等做完熱身、寫過 Controller 再看：query string 怎麼變成方法參數

延伸問題

這幾題沒有標準答案，之後做專案遇到時再回來想。

  1. 篩選條件很多的時候（例如一次送 50 個 tag），網址會非常長。有些 API 因此改成 POST /search，把條件放在 body 的 JSON 裡。這樣做違反了「GET 拿資料、POST 新增」的習慣嗎？從「能不能存成書籤、分享連結」和「能不能被快取」兩個角度各想一次。
  2. 分頁有兩種寫法：?page=3&pageSize=20，或 ?after=第 40 筆的編號&limit=20。使用者翻到第 3 頁的途中，有人新增或刪除了一筆資料，兩種寫法各會發生什麼事？
  3. fragment 不會送到伺服器。早期的單頁應用（SPA）用 /#/posts/5 這種網址切換畫面，為什麼這樣設計能避免「重新整理時伺服器回 404」？現在的 History API（pushState）又是怎麼解決同一個問題的？
