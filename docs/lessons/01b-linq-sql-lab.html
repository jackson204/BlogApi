📎 補充：= null! 是什麼

專案開了 <Nullable>enable</Nullable>，Category Category { get; set; } 沒給初始值，編譯器會警告「可能是 null」。但這個屬性在查詢時由 EF Core 填（Include 之後才有值），不是我們 new 的。= null! 的意思是「我知道它一開始是 null，不用警告我」。第 2 課會再講導覽屬性什麼時候有值、什麼時候是 null。

3-4. ShopDbContext：沒有 DI，自己設定

LinqLab/Data/ShopDbContext.cs

using LinqLab.Models;
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Diagnostics;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.Logging;

namespace LinqLab.Data;

public class ShopDbContext : DbContext
{
    public DbSet<Category> Categories => Set<Category>();
    public DbSet<Product> Products => Set<Product>();
    public DbSet<Customer> Customers => Set<Customer>();
    public DbSet<Order> Orders => Set<Order>();
    public DbSet<OrderItem> OrderItems => Set<OrderItem>();

    // 這裡沒有 DI，沒有 AddDbContext 幫忙登記設定。
    // 有人 new ShopDbContext() 時，EF Core 會呼叫這個方法來問「要怎麼連資料庫」
    protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
    {
        // Web 專案的 WebApplication.CreateBuilder 會自動讀 appsettings.json，Console 專案要自己讀
        IConfiguration config = new ConfigurationBuilder()
            .AddJsonFile("appsettings.json")
            .Build();

        optionsBuilder
            .UseSqlServer(config.GetConnectionString("LinqLab"))
            // 每一句送出去的 SQL 都印到主控台
            .LogTo(Console.WriteLine, new[] { DbLoggerCategory.Database.Command.Name }, LogLevel.Information, DbContextLoggerOptions.None)
            // 連參數的值也一起印。正式環境不要開，會把個資印進 log
            .EnableSensitiveDataLogging();
    }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // decimal 要指定精度，不然 EF Core 會用預設值並發出警告
        modelBuilder.Entity<Product>().Property(p => p.Price).HasPrecision(18, 2);
        modelBuilder.Entity<OrderItem>().Property(i => i.UnitPrice).HasPrecision(18, 2);
    }
}

和 01 的 BlogDbContext 比，差別只有一個地方，但這個地方正是 DI 的意義：

BlogApi（有 DI）LinqLab（沒有 DI）
設定寫在哪Program.cs 的 AddDbContext(options => options.UseSqlServer(…))DbContext 自己的 OnConfiguring
設定怎麼進來建構子收 DbContextOptions，由 DI 傳進來沒有建構子參數；new ShopDbContext() 時 EF Core 回頭呼叫 OnConfiguring
誰 new 它DI（每個請求一個）你自己 new、自己 await using 丟掉
要換資料庫（測試時換成記憶體資料庫）改 Program.cs 一行，DbContext 不用動要改 DbContext 本身

實驗室這樣寫最省事。但 Web 專案不要把連線寫死在 OnConfiguring，第 3 課會從這個痛點出發講 DI。

LogTo 的參數做什麼
Console.WriteLine每一條 log 交給誰印。這裡印到主控台
new[] { DbLoggerCategory.Database.Command.Name }只要「資料庫指令」這一類，不要連線開關、交易等雜訊。對應 01 題 7 設定的 Microsoft.EntityFrameworkCore.Database.Command
LogLevel.Information最低等級
DbContextLoggerOptions.None不要前面的 info:、分類名稱、事件編號，只印訊息本身

using Microsoft.EntityFrameworkCore;

public static class Seed
{

        var tea = new Product { Name = "綠茶", Price = 25, Stock = 0, Category = drinks };      // 缺貨
        var coffee = new Product { Name = "咖啡", Price = 60, Stock = 20, Category = drinks };
        var chips = new Product { Name = "洋芋片", Price = 45, Stock = 50, Category = snacks };
        var chocolate = new Product { Name = "巧克力", Price = 80, Stock = 8, Category = snacks };
        var cookie = new Product { Name = "餅乾", Price = 35, Stock = 30, Category = snacks };
        var pen = new Product { Name = "原子筆", Price = 15, Stock = 200, Category = stationery };
        var notebook = new Product { Name = "筆記本", Price = 50, Stock = 40, Category = stationery };

        var ming = new Customer { Name = "小明", City = "台北", JoinedAt = new DateTime(2025, 3, 1) };
        var hua = new Customer { Name = "小華", City = "台北", JoinedAt = new DateTime(2025, 11, 20) };
        var mei = new Customer { Name = "小美", City = "台中", JoinedAt = new DateTime(2026, 1, 15) };
        var qiang = new Customer { Name = "阿強", City = "高雄", JoinedAt = new DateTime(2026, 6, 2) };
        var fang = new Customer { Name = "小芳", City = "台中", JoinedAt = new DateTime(2026, 10, 1) };   // 還沒下過單

            new() { Customer = hua, OrderedAt = new DateTime(2026, 8, 20), Status = OrderStatus.Cancelled, Items = { Item(chocolate, 1) } },
            new() { Customer = hua, OrderedAt = new DateTime(2026, 10, 15), Status = OrderStatus.Paid, Items = { Item(cola, 6), Item(cookie, 2), Item(pen, 10) } },

🤔 為什麼用 EnsureCreated，不用 01 學的 Migration？

EnsureCreatedAsync() 看資料庫在不在，不在就照目前的模型直接建表，不留任何版本紀錄。實驗室的資料庫是拋棄式的：做壞了就 EnsureDeleted 砍掉重建，不需要「從上一版升到這一版」，所以用它最省事。

它和 Migration 不能混用：EnsureCreated 建的資料庫沒有 __EFMigrationsHistory，之後想加 Migration 會對不起來。正式專案（BlogApi）用 Migration；一次性的實驗、測試用 EnsureCreated。想練習的話，把這裡改成 Migration 是這一課的選修題。

物件圖的部分值得看一下：orders 裡每筆訂單掛著 Customer 和 Items，每個 Item 又掛著 Product。SaveChangesAsync 時 EF Core 會自己排好順序：先 INSERT 客戶和商品拿到 Id，再 INSERT 訂單填入 CustomerId，最後 INSERT 明細。跑 reset 時主控台會印出這整串（五句 CREATE TABLE、四個索引、再來是一批批的 MERGE … OUTPUT INSERTED.[Id]）。

    ? Catalog.All
    : Catalog.All.Where(e => args.Contains(e.Id)).ToList();

{

這行在做什麼
args is ["reset"]C# 的清單模式：「args 剛好只有一個元素而且是 reset」
Func<ShopDbContext, Task>把「一個方法」當資料放進清單，和 C# 補充頁的 Action／Func 一樣，差別是回傳 Task（async 方法）
foreach (var (id, title, run) in selected)tuple 拆成三個變數
await run(db)呼叫那個方法，把 DbContext 傳進去

{

{

        .Select(p => p.Name)

-- 有 OrderBy。Parameters=[@p='3']
SELECT [p].[Name]
FROM [Products] AS [p]
ORDER BY [p].[Id]
OFFSET @p ROWS FETCH NEXT @p ROWS ONLY

-- 沒有 OrderBy
SELECT [p].[Name]
FROM [Products] AS [p]
ORDER BY (SELECT 1)
OFFSET @p ROWS FETCH NEXT @p ROWS ONLY

6. Level 2：關聯（8 個實驗）

這一層開始跨表。EF Core 把導覽屬性翻成 JOIN 或子查詢，你不用自己寫 ON 條件，它從外鍵知道。寫在 Level2.cs。

L2-01：Include 多對一

任務：所有訂單，連同下單的客戶（Include(o => o.Customer)）。印「訂單 1：小明（台北）」。

先猜：會是 INNER JOIN 還是 LEFT JOIN？為什麼？

LINQ 與實測 SQL（寫完再打開） 
public static async Task IncludeManyToOne(ShopDbContext db)
{
    var orders = await db.Orders
        .Include(o => o.Customer)
        .ToListAsync();

FROM [Orders] AS [o]

SELECT [o].[Id], [o].[CustomerId], [o].[OrderedAt], [o].[Status], [s].[Id], [s].[OrderId], [s].[ProductId], [s].[Quantity], [s].[UnitPrice], [s].[Id0], [s].[CategoryId], [s].[Name], [s].[Price], [s].[Stock]

{

第一個 .ToList() 送出 0 句。.ToList() 本身只是「把前面那串真的跑一遍，結果裝成清單」，它連不連資料庫，要看它的主體：從 .ToList() 往前看到最開頭，看這一串是從哪裡出發的。

第一個 .ToList()迴圈裡的 .ToListAsync()
主體（最開頭）cities，記憶體裡的陣列db.Customers，資料庫的表
主體的型別IEnumerable<…>IQueryable<string>
跑完之後清單裡裝什麼2 個還沒送出的查詢客戶名稱

  • 用型別判斷最準：主體是 IQueryable<…> 才會連資料庫；IEnumerable、List、陣列都只在記憶體裡跑。Rider 把游標移到 .ToList() 前面那個方法上就看得到型別

  • 會觸發執行的不只 ToList：First、Count、Any、foreach 都一樣，判斷方式相同。Where、Select、OrderBy、Concat、Skip、Take 只是加條件，不會觸發（L4-03）

  • 寫法是「前面那份 .Concat( 後面那份 )」。兩個都是 IQueryable 時不會真的去接資料，只是在查詢上記一筆「這兩段要接起來」，所以兩段變成一句 SQL，不是兩句

  • 沒有 OrderBy 時，接起來的順序資料庫不保證，所以這題只比筆數。要固定順序就在 Concat 後面加 OrderBy（下一題）
  • 對記憶體裡的陣列或 List 也可以用 Concat／Union，意思相同，只是在 C# 裡做：new[] { 1, 2, 3 }.Concat(new[] { 3, 4 }) 是 1、2、3、3、4，Union 是 1、2、3、4

Aggregate 是什麼：把一份清單「滾」成一個結果

它需要一個規則：「目前累積的結果」加上「下一個」要變成什麼，然後從左到右一個一個套。先用數字看：

1123
2336
36410

括號裡的兩個名字是自己取的，第一個永遠是「目前累積的結果」，第二個永遠是「下一個」。

套回這題：規則換成「接起來」

sources.Aggregate((merged, source) => merged.Concat(source)) 的規則是「目前已經接好的，再接上下一段」。三種都勾時：

  • ORDER BY 和 OFFSET … FETCH 在最外層，作用在合併之後的結果上。所以三張表的資料是混在一起排序、再取 5 筆，資料庫只回這 5 筆。如果改成每張表各自 ToListAsync() 再用 C# 合併，就會把三張表全部搬回來（L4-02 的坑）
  • N'Product' AS [Kind] 是程式裡寫死的 Kind = "Product"。資料表本身沒有「種類」欄位，所以每一段自己標上是哪一種，合併後才分得出來
  • 只勾一種時 ORDER BY 第二個鍵變成 (SELECT 1)：這時每一列的 Kind 都是同一個固定值，排不排都一樣（和 L1-09 沒有 OrderBy 時看到的是同一個寫法）
  • 為什麼排序要加第二個鍵 ThenBy(Kind)：三張表的 Id 各自編號，會有三筆 Id 都是 1。只依 Id 排的話，這三筆誰先誰後資料庫不保證，分頁時可能同一筆出現兩次、另一筆漏掉。排序鍵要能分出每一筆的先後，分頁才穩定

var merged = sources[0];

{

}

// 寫法二：寫死三段。只勾一種時 sources[1] 不存在，會出錯
var merged = sources[0].Concat(sources[1]).Concat(sources[2]);

段數固定時寫法二最直白；段數不固定就用迴圈或 Aggregate。Aggregate 是把那個迴圈濃縮成一行。

    await ByProgress(db, "不存在");
}

private static async Task ByProgress(ShopDbContext db, string progress)
{
    // 查詢前：進度（value）→ 資料庫的狀態（key）。主體是記憶體裡的對應表，不連資料庫
    var statuses = ProgressMapping
        .Where(pair => pair.Value == progress)
        .Select(pair => pair.Key)
        .ToList();
    Lab.Note($"{progress} → [{string.Join(", ", statuses)}]");

    var orders = await db.Orders
        .Where(o => statuses.Contains(o.Status))
        .OrderBy(o => o.Id)
        .Select(o => new { o.Id, o.Status })
        .ToListAsync();

    // 查詢後：資料庫的狀態（key）→ 進度（value）
    foreach (var order in orders)
    {
        Lab.Show($"訂單 {order.Id}：{order.Status} → {ProgressMapping[order.Status]}");
    }
}

查詢前查詢後
手上有的使用者選的進度（value）資料庫回來的狀態（key）
要換成資料庫的狀態（key），可能好幾個進度（value），剛好一個
寫法.Where(pair => pair.Value == progress).Select(pair => pair.Key)ProgressMapping[order.Status]
  • 第 2 步不會送 SQL。ProgressMapping 是記憶體裡的 Dictionary，對它用 Where、Select、ToList 都只在 C# 裡跑（L4-07）
  • 反查要取 key，不是 value。statuses.Contains(o.Status) 兩邊要是同一種東西：o.Status 是 OrderStatus，所以清單裡也要是 OrderStatus，也就是對應表的 key。value 是給使用者看的文字，資料庫不認得
  • 「進行中」對應兩個狀態，SQL 是 IN；「已完成」只對應一個，SQL 是 =（L4-10）
  • 選了不存在的進度：反查得到空清單，SQL 變成 WHERE 0 = 1，回 0 筆，不會出錯。要小心的是另一種寫法：如果寫成「清單不是空的才加這個條件」，不存在的進度就會變成沒有篩選、回傳全部訂單
  • 查詢後用 ProgressMapping[order.Status]。如果資料庫裡出現對應表沒列到的狀態，這裡會丟 KeyNotFoundException。新增狀態時要記得一起更新對應表
  • pair.Key、pair.Value 與其他讀法見 Dictionary；這個做法的完整說明見 enum 與資料庫第 7 節
