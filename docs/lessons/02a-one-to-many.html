1. 這一課要解決的問題

📋 情境：主管打開文章列表，問「這篇是誰寫的？」現在的 Post 只有標題和內容，答不出來。

要做到：有作者這個東西、每篇文章歸屬一位作者、列表直接顯示作者名、能查某位作者的所有文章、刪作者時不能把文章弄丟。對應的 API：

第 5 課做登入之後，authorId 會改成從登入的人身上拿，前端不用傳也不能傳。這一課還沒有登入，先讓前端傳。

2. 原理：關聯在資料庫和 EF Core 裡長什麼樣

2-1. 關聯在資料庫怎麼存：外鍵放在「多」的那一邊

先用具體的人來說。小明寫了〈Docker 入門〉和〈我的第一支 Web API〉兩篇，小華寫了〈小華的第一篇〉一篇。小明有兩篇文章，但〈Docker 入門〉這篇只有小明一位作者。一位作者有很多文章、一篇文章只有一位作者，這叫一對多。

怎麼判斷是幾對幾：站在兩邊各問一次「最多可以有幾個？」

站在哪邊問問題答案
作者 → 文章一位作者最多可以有幾篇文章？很多（小明有 2 篇）
文章 → 作者一篇文章最多可以有幾位作者？一位

一邊答「一」、一邊答「多」，就是一對多；答「多」的那邊（文章）叫「多的那一邊」。

文章編號以你的資料庫實際產生的為準；筆記用 5、6、7，是因為題 2 清掉舊文章後從 5 接著編。從這兩張表可以讀出：

  • Posts 每一列的 AuthorId 只有一個格子，只放得下一個數字，所以一篇文章只有一位作者。「一」的那個方向是欄位本身保證的
  • AuthorId 這一欄裡 1 出現了兩次，資料庫不禁止重複，所以同一位作者可以出現在很多列。「多」的那個方向就在這裡
  • 想知道小明寫了什麼：拿 Authors 的 Id = 1 到 Posts 找 AuthorId = 1 的列，找到 5 和 6。SQL 就是 WHERE AuthorId = 1
  • 想知道文章 5 是誰寫的：拿 Posts 的 AuthorId = 1 回 Authors 找 Id = 1，找到小明。SQL 就是 JOIN Authors ON Posts.AuthorId = Authors.Id
  • 小芳在 Posts 裡一列都沒有，她還是一位合法的作者。所以作者這邊是「零或多」篇文章

資料庫記這件事的方法只有一種：在「多」的那張表（Posts）加一個欄位，存「一」那邊的主鍵（Authors.Id）。這個欄位叫外鍵（Foreign Key）。畫成 ERD 如下，那條線兩端的符號標的就是上面問的兩個答案：Author 這端 || 是「恰好一」（一篇文章恰好一位作者），Post 這端 o{ 是「零或多」（一位作者可以零篇、也可以很多篇；小芳就是零篇，所以是 o{ 不是 |{）：

erDiagram Author ||--o{ Post : "寫了" Author { int Id PK string Name string Bio "可為 NULL" } Post { int Id PK string Title string Content datetime CreatedAt datetime UpdatedAt "可為 NULL" int AuthorId FK }
線的上端（Author 這頭）||＝恰好一，下端（Post 這頭）o{＝零或多。Posts 多一個 AuthorId 欄位指向 Authors.Id；Authors 這邊什麼都不用加

為什麼不是反過來、在 Authors 加一欄 PostIds 放 "5,6"？因為一個格子只能放一個值，上面 Posts 每列只有一個 AuthorId，靠的正是這一點；反過來放就是硬把兩個數字塞進一格，資料庫沒辦法幫你查、幫你算。而且文章新增時要去改作者那一列，兩張表會互相牽制。外鍵放在多的那邊，新增文章只要填一個數字，資料庫還會幫你檢查這個數字真的存在（這就是題 2 和題 6 會撞到的 FOREIGN KEY constraint）。

EF Core 靠慣例把三個零件對起來。它看的是名字，下面三個顏色各代表一件事：

public class Post
{
    public int AuthorId { get; set; }               // 外鍵屬性：名字 = 導覽屬性的名字 + Id
    public Author Author { get; set; } = null!;   // 參考導覽屬性：型別是 Author 類別，名字叫 Author
}

看到 Post 有一個 Author 型別的屬性叫 Author，又有一個 int 叫 AuthorId（導覽屬性名 + Id），就認定這是外鍵。藍色是要連到哪個類別、綠色是導覽屬性的名字、紅色是固定接在後面的 Id，三個對上，不用你多寫一個字。名字對不上時（例如導覽屬性叫 Writer、外鍵卻叫 AuthorId），要用 3-2 的 Fluent API 明講。這一課就算名字對得上也會用 Fluent API 寫一次，因為 OnDelete 只能在那裡設。

2-3. 導覽屬性什麼時候有值

查出一篇 Post，它的 Author 屬性預設是 null：導覽屬性只是「寫好的空位」，要不要填、怎麼填，看你怎麼查。下面用一個練習用的 SQLite 小資料庫（3 位作者、4 篇文章：小明 2 篇、小華 1 篇、小芳 1 篇）跑三種情境，每種都用 LogTo 數送了幾句 SQL（單檔程式實際執行過）。

情境 1 不 Include：空位留著，Author 是 null

var posts = db.Posts.ToList();
Console.WriteLine($"送了 {sqlCount} 句 SQL，第一篇的 Author 是 {(posts[0].Author is null ? "null" : posts[0].Author.Name)}");

// 輸出：
// 送了 1 句 SQL，第一篇的 Author 是 null

一句 SQL 只查 Posts，作者沒撈，post.Author 就是 null。EF Core 不會因為你寫了導覽屬性就自動多查一次。

情境 2 Include：一句 JOIN，Author 有值

var posts = db.Posts.Include(p => p.Author).ToList();
Console.WriteLine($"送了 {sqlCount} 句 SQL，第一篇的 Author 是 {posts[0].Author.Name}");

// 輸出：
// 送了 1 句 SQL，第一篇的 Author 是 小明
// SELECT "p"."Id", "p"."AuthorId", "p"."Title", "a"."Id", "a"."Name"
// FROM "Posts" AS "p"
// INNER JOIN "Authors" AS "a" ON "p"."AuthorId" = "a"."Id"

還是一句 SQL，但多了 INNER JOIN，作者的欄位一起撈回來，組成完整的 Author 物件放進 post.Author。不管幾篇文章都是 1 句。

情境 3 延遲載入：碰到 post.Author 才偷偷去查（這一課不開）

📌 這裡先看它會發幾句 SQL。另外兩件事在別的地方：

  • 它是怎麼攔到「碰 post.Author」、為什麼大家說它危險：本課 延遲載入是怎麼做到的，為什麼這一課不開
  • 實際打開它、量 N+1 慢在哪，再跟 Include、Select 投影比：第 4 課「文章列表效能優化」

這個行為預設沒有，要另外裝 Microsoft.EntityFrameworkCore.Proxies、在 options 加 UseLazyLoadingProxies()、導覽屬性標 virtual。開了之後：

var posts = db.Posts.ToList();
Console.WriteLine($"ToList 之後：{sqlCount} 句 SQL");
foreach (var post in posts)
{
    var name = post.Author.Name;      // 碰到 Author 才偷偷去查
    Console.WriteLine($"  {post.Title} → {name}，到目前為止 {sqlCount} 句 SQL");
}

// 輸出：
// ToList 之後：1 句 SQL
//   Docker 入門 → 小明，到目前為止 2 句 SQL
//   我的第一支 Web API → 小明，到目前為止 2 句 SQL      ← 小明已經查過，記憶體裡有，不用再查
//   小華的第一篇 → 小華，到目前為止 3 句 SQL
//   小芳的第一篇 → 小芳，到目前為止 4 句 SQL
// 最後一句（查作者的）：
// SELECT "a"."Id", "a"."Name"
// FROM "Authors" AS "a"
// WHERE "a"."Id" = @p
// LIMIT 1

每碰到一位還沒查過的作者，就多送一句 WHERE "a"."Id" = @p。4 篇文章 3 位作者送了 1 + 3 句；列表 100 篇、100 位作者就是 1 + 100 句，這叫 N+1，正是效能問題的來源，第 4 課會示範它有多慢。所以這一課不開它。

還有一種常用的做法不填導覽屬性，直接拿欄位：Select 投影 _db.Posts.Select(p => new { p.Title, p.Author.Name })，也是一句 JOIN，但只拿你點名的欄位。回 API 只需要作者名時，主要用這個。

在 Where 或 Select 裡用到導覽屬性（p.Author.Name），EF Core 自己會 JOIN，不需要 Include。Include 是「把整個關聯物件載回來放在 post.Author」才需要。

延遲載入是怎麼做到的，為什麼這一課不開

一句話：導覽屬性平常是空的，第一次碰它的那一刻，EF Core 才偷偷發一句 SQL 把它填起來。

怎麼攔到「碰它」這個動作：C# 讀一個屬性本來不會發生任何事，所以 EF Core 得把那個屬性換掉。開了 UseLazyLoadingProxies() 之後，查詢回來的不是你寫的 Post，而是 EF Core 在執行時動態產生的子類別（proxy），它 override 了標成 virtual 的 Author 屬性：你一讀，它先看載過了沒，沒有就拿手上的 AuthorId 發一句 SQL 填進去，再回給你。這也是導覽屬性一定要 virtual 的原因：不是 virtual 就 override 不了，攔不到（單檔程式實際執行過）：

var post = db.Posts.First();
Console.WriteLine($"你寫的類別：{typeof(Post).Name}，實際拿到的：{post.GetType().Name}，父類別：{post.GetType().BaseType!.Name}");

// 輸出：
// 你寫的類別：Post，實際拿到的：PostProxy，父類別：Post

為什麼大家說它危險：

  • N+1 看不見：情境 3 迴圈裡那行 post.Author.Name 怎麼看都像在讀記憶體，實際上每一輪都可能打一次資料庫，程式碼上沒有任何痕跡
  • 序列化會觸發它：直接回傳 Entity 時，System.Text.Json 把每個屬性都走一遍，走到 Author 就載、走到 Author.Posts 又載，整張關聯圖一路拉進來（再加上 2-4 的循環參照，更慘）
  • DbContext 關掉之後再碰就炸：Controller 方法結束、請求的 scope 釋放之後，還拿著那個 post 去碰 Author，proxy 會用已經 Dispose 的 context 發 SQL。實際跑一次：先用一個 using 區塊查出 post，離開區塊後再讀 post.Author.Name：

那它什麼時候有用：真的「大多數時候用不到關聯、偶爾才碰一下」的情境，例如桌面程式點開某一筆明細才看關聯。Web API 幾乎都是「這個請求要什麼，一開始就知道」，所以這一課的做法是：要整個物件用 Include，只要幾個欄位用 Select 投影，延遲載入不開。第 4 課會把它打開跑一次，看它慢在哪。

2-4. 直接回傳 Entity 會爆：循環參照

01 的延伸問題 3 問過：加上作者之後，直接回傳 Post 會怎樣？現在可以回答了。Include(p => p.Author) 撈回來之後，EF Core 會做一件貼心的事叫 fix-up：把 post.Author 指向作者物件，同時把那篇文章塞進 author.Posts。於是：

flowchart LR P1["Post #5"] -- ".Author" --> A["Author #1"] A -- ".Posts[0]" --> P1 A -- ".Posts[1]" --> P2["Post #6"] P2 -- ".Author" --> A
物件之間互相指來指去是正常的，記憶體裡沒問題；問題出在要把它寫成 JSON 的時候

用程式碼看同一件事。不用資料庫，自己把 fix-up 做完的樣子接起來：一位作者、兩篇文章，post.Author 指向作者，author.Posts 裝著那兩篇（單檔程式實際執行過）：

var author = new Author { Id = 1, Name = "小明" };
var post5 = new Post { Id = 5, Title = "Docker 入門", AuthorId = 1, Author = author };
var post6 = new Post { Id = 6, Title = "我的第一支 Web API", AuthorId = 1, Author = author };
author.Posts.Add(post5);
author.Posts.Add(post6);

// 記憶體裡繞一圈回到自己，完全沒問題
Console.WriteLine($"post5.Author.Name = {post5.Author.Name}");
Console.WriteLine($"post5.Author.Posts.Count = {post5.Author.Posts.Count}");
Console.WriteLine($"post5.Author.Posts[0] 就是 post5 自己嗎：{ReferenceEquals(post5.Author.Posts[0], post5)}");
Console.WriteLine($"post5.Author.Posts[0].Author.Posts[0].Author.Posts[0].Title = {post5.Author.Posts[0].Author.Posts[0].Author.Posts[0].Title}");

// 輸出：
// post5.Author.Name = 小明
// post5.Author.Posts.Count = 2
// post5.Author.Posts[0] 就是 post5 自己嗎：True
// post5.Author.Posts[0].Author.Posts[0].Author.Posts[0].Title = Docker 入門

第三行是重點：post5.Author.Posts[0] 不是另一份複本，就是 post5 自己（同一個物件）。所以最後一行 .Author.Posts[0] 可以無限接下去，每接一次就繞回原點，C# 完全不介意。

    {

or if the object depth is larger than the maximum allowed depth of 32. Consider using ReferenceHandler.Preserve

三種解法：

單一：Author Author= null!自己 new 一個空的 Author 等於捏造一位不存在的作者，所以留給 EF Core 填

第 2 步（Restrict）：RestrictAuthorDelete 的 Up() 是把外鍵拆掉重建：

    name: "FK_Posts_Authors_AuthorId",

public async Task<IActionResult> Delete(int id)
{

    }

從 SQL 看出來的重點

  • 必填外鍵 → INNER JOIN：int AuthorId 保證每篇文章都對得到作者，不需要 LEFT JOIN。改成 int? 就會變 LEFT JOIN（想看兩種 JOIN 的實際 SQL，01b 的 L2-01 和 L2-02 有）
  • 投影 vs Include 的差別只在 SELECT 清單：JOIN 一樣，差在拿幾個欄位。列表頁用投影，省流量也避開循環參照
  • a.Posts.Count 是子查詢，不是 N+1：一句 SQL 算完所有作者的文章數。寫成「先撈作者，再 foreach 裡 CountAsync」就是 2-3 第 (3) 段那種 N+1：每位作者多送一句 SQL
  • Cascade 刪除在 SQL 裡看不到：EF Core 只送一句 DELETE FROM [Authors]，文章是資料庫自己連帶刪的。這就是它可怕的地方

導覽屬性的優缺點

優點缺點
不用自己寫 JOIN，p.Author.Name 就有忘了 Include 或投影，post.Author 是 null，執行時才爆 NullReferenceException
