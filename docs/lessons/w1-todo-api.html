1. 這一課要做出什麼

這一課做出一個待辦事項 API，可以查清單、新增、修改、刪除。資料先不放資料庫：部落格的第一課要同時學 Web API 和資料庫，東西太多，所以這裡先把 Web API 這一半單獨學會。建立專案、寫 Controller、決定網址和狀態碼這幾件事，到部落格專案照樣用。

前端（這一課用 Postman 代替）送請求過來，後端要提供這六支 API：

功能HTTP網址成功時回傳哪一題
全部待辦事項GET/api/todos200 + 陣列題 3
只看已完成／未完成GET/api/todos?isDone=true200 + 陣列題 4
單一筆GET/api/todos/{id}200 + 物件題 4
新增POST/api/todos201 + 新增的那一筆題 5
修改PUT/api/todos/{id}204，沒有內容題 7
刪除DELETE/api/todos/{id}204，沒有內容題 7

動手之前，先看「後端 API」到底在整件事裡的哪個位置：

左邊發問、右邊回答。這一課要寫的是右邊那個專案。①②④ 框架會幫你做，你要寫的只有藍色的 ③

請求和回應裡每一塊是什麼、請求怎麼找到伺服器，在「起步」的第一篇：HTTP 請求與回應。還沒讀過的話，建議先讀完起步三篇再往下。

名詞是什麼這一課對應到
用戶端（Client）發出請求的程式瀏覽器、Postman
伺服器（Server）一直開著、等請求進來再回應的程式你的 TodoApi 專案，dotnet run 之後就是一台伺服器
HTTP 請求（Request）用戶端送過來的那一段文字，第一行是「動詞 路徑」GET /api/todos
HTTP 回應（Response）伺服器送回去的那一段文字，第一行有狀態碼，後面是內容200 OK + 待辦事項的 JSON

在瀏覽器網址列輸入網址按 Enter，瀏覽器送出的就是一個 GET 請求，所以查詢類的 API 可以直接用瀏覽器看。但網址列只能送 GET，新增、修改、刪除要用的 POST、PUT、DELETE 送不出來，所以題 2 之後改用 Postman 當用戶端，它每一種動詞都能送。

狀態碼：伺服器用三位數字回報結果

伺服器每次回應，第一行都有一個三位數字，叫狀態碼，告訴用戶端這次請求的結果。上面那張圖裡回應的 HTTP/1.1 200 OK，200 就是狀態碼。Postman 送出請求後，回應區最先顯示的也是它。

第一位數字代表大類。這一課會遇到兩類：2xx 是成功；4xx 是用戶端送來的請求有問題，例如網址打錯、資料沒填。

狀態碼意思這一課什麼時候會看到
200 OK成功，回應裡有資料查詢
201 Created成功，而且新增了一筆新增
204 No Content成功，沒有資料要回修改、刪除
400 Bad Request送來的資料不對新增時沒填標題
404 Not Found找不到網址不存在，或查一筆不存在的編號
405 Method Not Allowed網址有，但不接受這個動詞對只接受 GET 的網址送 POST

做題目時每送一個請求，先看狀態碼是不是預期的那一個，再看內容。看到 404 不代表伺服器壞了：伺服器有回應，只是它說「沒有這個網址」。伺服器真的沒啟動時，Postman 顯示的是連不上，沒有任何狀態碼。

狀態碼的完整分類和其他常用的幾個：HTTP 狀態碼

不接資料庫，那資料存在哪裡？

資料放在 Controller 的一個 List<TodoItem> 裡，新增、查詢都是在操作這個清單，所以不用安裝資料庫也有地方放資料，可以先專心學 API。代價是程式一關資料就消失，下一個專案才要換成資料庫。

那個清單在程式的記憶體裡，就是 Controller 裡的一個變數：

List<TodoItem> Todos = new()
{
    new TodoItem { Id = 1, Title = "買牛奶", IsDone = false },
    new TodoItem { Id = 2, Title = "裝 .NET SDK", IsDone = true }
};

List<TodoItem> 是一個可以一直往裡面加東西的清單。整個「資料庫」就是這個清單：

什麼時候記憶體裡發生什麼
程式啟動作業系統分一塊記憶體給這個程式。上面那一行執行時，清單在這塊記憶體裡建立出來，裡面有寫死的兩筆
新增（POST）Todos.Add(…)：往清單裡多放一個物件
查詢（GET）從清單裡找出來回傳
修改、刪除改清單裡那個物件的屬性，或把它從清單拿掉
程式關掉那塊記憶體還給作業系統，清單連同裡面的資料一起消失。下次啟動又是寫死的那兩筆

從頭到尾沒有任何東西寫到硬碟，所以不用安裝資料庫，也不用 Docker。代價就是資料留不住。三種放資料的地方比一比：

資料放在程式關掉之後特性哪裡用
記憶體（變數、List）消失不用安裝任何東西，讀寫不經過硬碟和網路這一課
檔案（例如一個 .json 檔）還在要自己處理讀檔寫檔；兩個請求同時寫容易寫壞；資料一多，要找「已完成的那幾筆」得整個檔案讀進來這份筆記不用
資料庫（SQL Server）還在專門處理「很多人同時讀寫」和「依條件查詢」，但要另外安裝、另外學怎麼連線部落格專案，從 00 開始

對 Controller 來說，這一課的 List 就是資料庫的替身。到了部落格，Todos.Add(…) 會換成「寫進資料表」，Todos.Where(…) 會換成「查詢資料表」，但網址、JSON、狀態碼這些 API 的外觀完全不變。所以現在先用最簡單的 List 把 API 這一半學會，資料庫那一半留給下一個專案。

資料會不見這件事，題 6 會親眼看一次。

2. 動手做

題 1：用指令建立方案和專案，跑起最小的 Web 程式

用指令建立方案和專案，跑起一個只有四行的最小 Web 程式。

需求：

  • 建立資料夾 TodoApi，在裡面建立一個方案（solution），名稱 TodoApi
  • 在方案資料夾裡建立一個「空的 ASP.NET Core」專案（project），名稱也叫 TodoApi，並把它加入方案。這一課從頭到尾都用這一個專案
  • 執行專案，用瀏覽器打開，看到 Hello World!
  • 自己加一條路徑：打開 /hello/Jack 會看到 Hello Jack!，Jack 換成別的名字也可以

動手前先認識「方案」和「專案」，以及會用到的指令：

  • 專案是一個可以編譯、執行的程式（.csproj）；方案是一份「有哪些專案」的清單（.slnx 或 .sln），本身沒有程式碼
  • 指令打在 Windows 的 PowerShell，用 cmd（命令提示字元）也可以，指令一樣。先 cd 到你平常放專案的資料夾再開始
指令做什麼
dotnet new sln -n 方案名稱在目前的資料夾建立一個空的方案
dotnet new web -n 專案名稱 -f net10.0建立一個「空的 ASP.NET Core」專案。web 是範本名稱，-f 指定 .NET 版本
dotnet sln add 專案資料夾/專案名稱.csproj把專案登記到方案的清單裡
dotnet run --project 專案資料夾編譯並執行那個專案。按 Ctrl+C 停止
dotnet build只編譯、不執行。在方案資料夾執行會編譯清單上的全部專案
  • 加一條路徑的寫法：app.MapGet("路徑", () => 要回傳的東西);。路徑裡的 {name} 是佔位符，寫成 (string name) => … 就能拿到網址上那一段

✅ 驗收：瀏覽器打開 / 看到 Hello World!，打開 /hello/你的名字 看到 Hello 你的名字!

最小的 Web 程式：範本的 Program.cs 只有四行

TodoApi/Program.cs（範本產生的四行，註解是另外加的）

// 準備：讀設定檔，做出一個 builder
var builder = WebApplication.CreateBuilder(args);

// 定案：做出 app，它就是這個網站本身
var app = builder.Build();

// 排路徑：有人用 GET 打 / 時，執行後面那段程式，把回傳值送回去
app.MapGet("/", () => "Hello World!");

// 開門：開始聽 port，程式會停在這一行，直到按 Ctrl+C
app.Run();

() => "Hello World!" 是一段「沒有名字的方法」，叫 lambda：() 裡是參數（這裡沒有），=> 後面是回傳值。MapGet 把它收起來，等有請求打到 / 才執行。lambda 的寫法見「看懂方法簽章」。

加一條路徑

TodoApi/Program.cs（加一行）

var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/", () => "Hello World!");
app.MapGet("/hello/{name}", (string name) => $"Hello {name}!");

app.Run();

改完要停掉（Ctrl+C）再 dotnet run 一次。實測：

GET  /             → 200 Hello World!
GET  /hello/Jack   → 200 Hello Jack!
GET  /nothing      → 404          沒有任何一行 MapGet 認領這個路徑
POST /             → 405          路徑有，但只登記了 GET

$"Hello {name}!" 是字串插值：把變數 name 的值填進字串裡。

題 2：寫第一個 Controller，把四行的程式改成 Controller 版

在題 1 的專案裡寫第一個 Controller，並在 Program.cs 親手加上讓 Controller 生效的兩行。後面每一題都在這個專案裡寫。

需求：

  • 在 TodoApi 專案裡建立 Controllers 資料夾，裡面建立 HelloController.cs
  • GET /api/hello 回傳文字 Hello from Controller!
  • 用 Postman 呼叫，看到 200 和那段文字

分三步做。每一步改完都重新 dotnet run，用 Postman 送 GET /api/hello，記下看到什麼：

  1. 只寫 HelloController.cs，Program.cs 不動
  2. 在 Program.cs 的 app.Run(); 前面加一行 app.MapControllers();
  3. 在 Program.cs 的 var app = builder.Build(); 前面加一行 builder.Services.AddControllers();

Controller 的基本形狀。以一個回傳 pong 的 PingController 為例，顏色相同的地方是同一件事：

using Microsoft.AspNetCore.Mvc;

[ApiController]
[Route("api/[controller]")]
public class PingController : ControllerBase
{
    [HttpGet]
    public string Get()
    {
        return "pong";
    }
}

這樣寫出來的 API 是 GET /api/ping，回應內容是 pong。

  • 路徑：[controller] 會自動換成類別名去掉結尾的 Controller，所以 PingController 的路徑是 /api/ping。檔案放在 Controllers 資料夾，類別名稱用 Controller 結尾
  • 動詞：方法上面寫 [HttpGet]，代表有人用 GET 打這個路徑時，呼叫這個方法。方法 return 的東西就是回應的內容
  • 每個 Controller 都有的兩樣：[ApiController] 標明這個類別是 Web API 的 Controller，框架會替它自動做幾件事；繼承 ControllerBase，類別裡就有回應請求常用的方法可以呼叫
  • 方括號 […] 是貼在類別或方法上的標記，叫 attribute。它自己不做事，是框架在程式啟動時讀這些標記，決定哪個網址交給哪個方法
  • Postman 是專門用來送 HTTP 請求的程式：新增一個請求，左邊下拉選單選動詞（GET、POST…），旁邊填網址，按 Send 送出，下方會顯示狀態碼和回應內容

✅ 驗收：第 3 步做完，Postman 回傳 200 和 Hello from Controller!；說得出第 1 步和第 2 步各自為什麼不行

第 1 步：只寫 Controller，Program.cs 不動（實測）

GET /            → 200 Hello World!      題 1 的 MapGet 照常運作

第 2 步：加上 app.MapControllers()（實測）

程式一啟動就丟例外，跑不起來：

Please add all the required services by calling 'IServiceCollection.AddControllers' inside the call to 'ConfigureServices(...)' in the application startup code.

  2. 這一行呼叫了 MapControllers

第 3 步：再加上 builder.Services.AddControllers()（實測）

GET /api/hello   → 200 Hello from Controller!
GET /api/Hello   → 200 Hello from Controller!      路徑不分大小寫

TodoApi/Program.cs（做完第 3 步）

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();                  // Build() 之前：登記使用 Controller 需要的功能

var app = builder.Build();

app.MapGet("/", () => "Hello World!");
app.MapGet("/hello/{name}", (string name) => $"Hello {name}!");

app.MapControllers();                               // Build() 之後：讀所有 Controller，建對照表

app.Run();
藍色那行先登記功能，綠色那行再用這些功能建對照表

builder.Services 這本登記簿，正式名稱是依賴注入（Dependency Injection，簡稱 DI）的容器。Add… 是往裡面登記「有這個功能」，框架裡要用的地方再向它拿。MapControllers() 在啟動時就是向它拿讀 Controller 的功能，拿不到就丟例外，所以第 2 步的錯誤訊息寫的是 Unable to find the required services（找不到需要的 service）。

登記簿在程式啟動的哪個階段可以寫、哪個階段定案：Program.cs 的四個階段。依賴注入想深入時再回來看「03a｜依賴注入（DI）：從 new 到 DI 容器」。

AddControllers() 和 MapControllers() 要成對

Program.cs 裡有哪一行結果原因
兩行都沒有（第 1 步）程式跑得起來，/api/hello 回 404沒有人去讀 Controller，對照表裡沒有它
只有 MapControllers()（第 2 步）程式一啟動就丟例外讀 Controller 要用的功能沒有登記
只有 AddControllers()和第 1 步一樣，回 404（實測）功能登記了，但沒有人去讀 Controller
兩行都有（第 3 步）200功能登記了，表也建了

要用 Controller，固定是這三行、照這個順序：builder.Services.AddControllers() → builder.Build() → app.MapControllers()。Add… 放到 Build() 之後會怎樣，看第 4 節：這幾行哪些可以換位置。

兩種寫法可以放在同一個專案

第 3 步做完，題 1 的 / 和 /hello/Jack 照樣回 200（實測）。題 1 那種「路徑直接寫在 Program.cs」的寫法叫 Minimal API，它不需要 AddControllers() 和 MapControllers()。兩種寫法什麼時候用：

Minimal APIController
路徑寫在哪裡Program.cs 裡的 app.MapGet(…)各個 Controller 類別的方法上
什麼時候用API 只有幾支API 支數多，要一種資料一個類別分開放
什麼時候不用支數一多，全部擠在一個檔案會很難找只有一兩支時，要多建類別和資料夾

題 3：第一支 API，GET /api/todos

寫出第一個 Controller，親眼看到方法的回傳值自動變成 JSON 送回用戶端。

需求：

  • 建立類別 TodoItem，有三個屬性：Id（int）、Title（string）、IsDone（bool）
  • 建立 TodosController，裡面放一個 List<TodoItem>，先寫死兩筆資料
  • GET /api/todos 回傳整個清單

寫 Controller 之前，先知道這幾件事：

  • TodosController 的開頭和題 2 的 HelloController 一樣：放在 Controllers 資料夾、類別上面寫 [ApiController] 和 [Route("api/[controller]")]、繼承 ControllerBase
  • [Route("api/[controller]")] 裡的 [controller] 會自動換成類別名去掉結尾的 Controller，所以 TodosController 的路徑是 /api/todos
  • 方法上面寫 [HttpGet]，代表「有人用 GET 打這個路徑時，呼叫這個方法」
  • 方法 return 什麼，框架就把它轉成 JSON 送回去，不用自己轉

✅ 驗收：GET /api/todos 回傳 200 和兩筆資料的 JSON 陣列

題 4：查單一筆，以及只看已完成的

從路徑和 ? 後面各拿一個值當參數，找不到資料時回 404。

需求：

  • GET /api/todos/1 回傳編號 1 的那一筆；編號不存在時回 404
  • GET /api/todos?isDone=true 只回傳已完成的，isDone=false 只回傳未完成的；沒帶 isDone 時和題 3 一樣回傳全部

這題要從請求的兩個地方拿值，寫法如下：

  • 從路徑拿值：方法上寫 [HttpGet("{id}")]，參數寫 int id。{id} 是佔位符，/api/todos/1 的 1 會填進參數 id
  • 從 ? 後面拿值：參數名稱沒出現在路徑裡的，框架會去網址 ? 後面找同名的。? 後面那一段叫 query string，見「網址與 query string」
  • 可以不帶的參數要宣告成可以是 null 的型別：bool? isDone。沒帶時 isDone 是 null
  • 回 404：return NotFound();
  • 在清單裡找一筆：Todos.FirstOrDefault(t => t.Id == id)，找不到會回傳 null。篩選多筆：Todos.Where(t => …).ToList()

✅ 驗收：/api/todos/1 回 200；/api/todos/99 回 404；/api/todos?isDone=true 只有一筆

    // GET api/todos
    // GET api/todos?isDone=true
    [HttpGet]
    public ActionResult<List<TodoItem>> GetAll(bool? isDone)
    {
        if (isDone is null)
        {
            return Todos;
        }

        return Todos.Where(t => t.IsDone == isDone).ToList();
    }

    // GET api/todos/1
    [HttpGet("{id}")]
    public ActionResult<TodoItem> GetById(int id)
    {
        var todo = Todos.FirstOrDefault(t => t.Id == id);
        if (todo is null)
        {
            return NotFound();
        }

        return todo;
    }

題 5：新增一筆，POST /api/todos

接收前端送來的 JSON，新增成功回 201。先寫完全不檢查的版本，看不合格的資料會怎樣，再一次加一個檢查。

需求：

  • 前端送 JSON {"title":"寫第一支 API"}，後端新增一筆待辦事項
  • 前端只能傳 title。Id 由後端決定（接著現有的編號往下排），IsDone 一律是 false
  • 成功時回 201，回應內容是新增的那一筆
  • title 必填、最多 100 字，不符合要回 400（第 3、4 步才加）

分四步做，每一步都重新執行再送請求：

  1. 不做任何檢查：寫一個只有 Title 的 record 和 Create 方法，送 {"title":"寫第一支 API"}，要回 201。
  2. 程式不改，送四個不合格的請求，記下各自回幾號，再 GET /api/todos 看清單多了什麼：
    • {}（沒有 title）
    • {"title":""}（title 是空字串）
    • {"title":" "}（title 只有空白）
    • title 是 101 個字
  3. 加上 [Required]，重送那四個請求，看哪幾個的結果變了。
  4. 再加上 [MaxLength(100)]，重送一次。另外送一個剛好 100 個字的。

接收 JSON、回 201、加檢查的寫法：

  • 從 JSON 拿值：方法參數是一個類別（或 record）時，框架會把請求 body 的 JSON 轉成那個型別的物件，JSON 的欄位名稱對得上屬性名稱就填進去
  • 「前端只能傳 title」：另外寫一個只有 Title 的 record 當參數型別，不要直接用 TodoItem。record 是一種寫起來比較短的類別：public record CreateTodoRequest(string Title);
  • 回 201：return CreatedAtAction(nameof(GetById), new { id = todo.Id }, todo);。三個參數的意思是「新資料可以用 GetById 這個方法查到、它的 id 是多少、回應內容是什麼」
  • 下一個編號：用一個 int 欄位記著，用掉一個就加 1
  • 第 3、4 步的檢查：[Required]、[MaxLength(100)] 是 attribute，寫在 record 參數的型別前面：[Required] string Title。兩個一起寫是 [Required, MaxLength(100)] string Title。檔案最上面要加 using System.ComponentModel.DataAnnotations;
  • 101 個字的 title：在 PowerShell 執行 'a' * 101 會印出 101 個 a，複製貼進 JSON

✅ 驗收（第 4 步做完）：正常的 title 回 201，回應內容是新增的那一筆；{}、空字串、只有空白、101 個字都回 400；剛好 100 個字回 201

第 1 步：看現象

第 2 步：找原因

在 TodosController 裡加一個建構子。建構子是「這個類別的物件被建立時」會執行的方法，名稱和類別一樣、沒有回傳型別：

只改 Todos 和 _nextId 這兩行的宣告，方法裡的程式不動。改完之後重做第 1 步，兩次 POST 的 id 要是 3 和 4，GET /api/todos 要看得到四筆。

第 4 步：重新啟動

修好之後，把程式停掉再 dotnet run，然後 GET /api/todos，看剛才新增的還在不在。

第 3 步要用到的 C# 規則：

  • 一個類別可以建立很多個物件。一般的欄位是每個物件各有一份，物件被丟掉，它的欄位也跟著不見
  • 欄位宣告前面加 static，這個欄位就不屬於任何一個物件，而是屬於類別本身，整個程式只有一份
  • static 寫在存取修飾詞後面：private static …

  • 第二個 POST 是另一個新物件，_nextId 又從 3 開始，清單又是寫死的兩筆
  • 接著的 GET 再換一個新物件，看到的還是寫死的兩筆

✗ 留不住：一般的欄位

private readonly List<TodoItem> Todos = new() { … };

欄位屬於每一個物件。每個請求建立一個新的 Controller，就有一份新的清單和新的 _nextId，請求結束一起丟掉。

✓ 留得住：static 欄位

private static readonly List<TodoItem> Todos = new() { … };
private static int _nextId = 3;

欄位屬於類別，整個程式只有一份。不管框架建立幾個 Controller 物件，每個請求讀寫的都是同一份清單、同一個 _nextId。

static 欄位什麼時候用：整個程式只需要一份、每個物件都要看到同一個值的東西，例如這一課的練習用清單和編號。什麼時候不用：真的專案不會用 static List 放資料，兩個請求同時新增時清單和編號都可能出錯，原因在「常見坑」。

第 4 步：重新啟動之後，回到最初寫死的那兩筆（實測）。

GET /api/todos → 200 [{"id":1,"title":"買牛奶","isDone":false},{"id":2,"title":"裝 .NET SDK","isDone":true}]

static 的清單活在程式的記憶體裡。程式一關，記憶體就還給作業系統；再啟動時，那一行 new() { … } 重新執行一次，又是寫死的兩筆。

💡 第 1 步和第 4 步合起來的結論

  • Controller 物件只活一個請求那麼久，不能把要留下來的資料放在它的一般欄位上
  • 放在 static 欄位可以活到程式關掉為止，但程式一重啟（改版、當機、主機重開）就全部消失
  • 要讓資料「明天還在」，得把它寫到程式外面去。這就是資料庫要做的事，也是下一個專案從 00｜用 Docker 跑 MSSQL 開始的原因

        }

    }

    // GET api/todos/1
    [HttpGet("{id}")]
    public ActionResult<TodoItem> GetById(int id)
    {
        var todo = Todos.FirstOrDefault(t => t.Id == id);
        if (todo is null)
        {
            return NotFound();
        }

        return todo;
    }

    // POST api/todos
    [HttpPost]
    public ActionResult<TodoItem> Create(CreateTodoRequest request)
    {
        var todo = new TodoItem
        {
            Id = _nextId,
            Title = request.Title,
            IsDone = false
        };
        _nextId++;

        Todos.Add(todo);

        return CreatedAtAction(nameof(GetById), new { id = todo.Id }, todo);
    }

    // PUT api/todos/1
    [HttpPut("{id}")]
    public IActionResult Update(int id, UpdateTodoRequest request)
    {
        var todo = Todos.FirstOrDefault(t => t.Id == id);
        if (todo is null)
        {
            return NotFound();
        }

        todo.Title = request.Title;
        todo.IsDone = request.IsDone;

        return NoContent();
    }

    // DELETE api/todos/1

    public IActionResult Delete(int id)
    {

        if (todo is null)
        {
            return NotFound();
        }

        Todos.Remove(todo);

        return NoContent();

(1) 一支 API = 動詞 + 路徑

這一段講標 (1) 的兩行 · Controllers/WeatherForecastController.cs

[Route("[controller]")]                    // 路徑：/weatherforecast
[HttpGet(Name = "GetWeatherForecast")]     // 動詞：GET

同一筆資料要能查、改、刪，光靠網址分不出要做哪一件，所以一支 API 是由動詞＋路徑一起決定的：動詞說做什麼（GET 拿、POST 新增、PUT 整筆換掉、DELETE 刪），路徑說對誰做。路徑一樣、動詞不同，就是不同的 API。

HTTP 請求的第一行就是「動詞 路徑」，例如 GET /weatherforecast。這一課的 API 用到四個動詞：

動詞做什麼例子請求要帶 body 嗎
GET拿資料，不改任何東西GET /weatherforecast、GET /api/todos（清單）、GET /api/todos/5（編號 5）不帶
POST新增一筆POST /api/todos帶：新待辦事項的 JSON
PUT整筆換掉PUT /api/todos/5帶：改完的 JSON
DELETE刪掉DELETE /api/todos/5不帶

GET /api/todos/5 和 DELETE /api/todos/5 路徑一樣，但是兩支不同的 API，各自對應 Controller 裡不同的方法。對範本實測：對 /weatherforecast 送 POST 會回 405 Method Not Allowed，意思是「這條路徑有人認領，但沒有方法接 POST」。

(2) 路由：請求怎麼找到你的方法

這一段講標 (2) 的兩行 · Program.cs 和 Controllers/WeatherForecastController.cs

app.MapControllers();        // Program.cs：程式啟動時建路由表
[Route("[controller]")]      // Controller 類別上：這個類別的路徑

請求進來時，由路由決定該呼叫哪個方法。程式啟動時把每個方法的「動詞＋路徑」登記成一張表，請求進來就查表：路徑查不到回 404，動詞不對回 405。在方法上寫 [HttpGet("{id}")] 就完成登記，不用自己判斷網址。

分兩個時間點。程式啟動時：你執行 dotnet run，Program.cs 從第一行往下跑，在開始接收請求之前，app.MapControllers() 把路由表建好，整個執行期間只做這一次。每個請求進來時：框架只查這張表。

左邊寫表、右邊查表。以做完題 7 的 TodosController 為例：對得到一列就呼叫那個方法；路徑有但動詞對不上是 405；整條路徑都不在表裡是 404

路徑怎麼算出來的：[Route("[controller]")] 裡的 [controller] 會換成類別名去掉結尾的 Controller，再接上方法的 [HttpGet("…")]：

類別[Route]方法算出來的 API
WeatherForecastController[controller][HttpGet]GET /weatherforecast
TodosController（題 3）api/[controller][HttpGet]GET /api/todos
TodosControllerapi/[controller][HttpGet("{id}")]GET /api/todos/5（{id} 是佔位符，5 會填進參數 id）
TodosControllerapi/[controller][HttpDelete("{id}")]DELETE /api/todos/5

範本的路由表只有一列（GET /weatherforecast）。對範本實測幾個網址，規則和上面的圖一樣：

GET  /                      → 404   路由表裡沒有「/」，沒有人認領
GET  /weatherforecast       → 200   命中
GET  /WeatherForecast       → 200   路徑不分大小寫
GET  /weatherforecast/5     → 404   範本的 Get() 沒有宣告 {id}，所以 /weatherforecast/5 不在表裡
POST /weatherforecast       → 405   路徑有，但沒有方法標 [HttpPost]

打開 / 看到 404 不代表伺服器壞了：伺服器有在跑，只是 / 這條路徑沒有任何方法認領。

(3) 參數從哪裡來

這一段講標 (3) 的那一行 · Controllers/WeatherForecastController.cs

(4) 為什麼繼承 ControllerBase

這一段講標 (4) 的那一行 · Controllers/WeatherForecastController.cs

public class WeatherForecastController : ControllerBase

繼承 ControllerBase 之後，類別裡就有 Ok()、NotFound()、CreatedAtAction()、NoContent() 這些回傳方法可以呼叫，回 404、201 這些結果時不用自己 new 結果物件。API 的 Controller 都繼承它。

ASP.NET Core 有兩個 Controller 父類別可以選：

ControllerBaseController
給你什麼Ok()、NotFound()、CreatedAtAction()、NoContent() 這些回傳方法；Request、Response；ModelStateControllerBase 的全部，再加 View()、ViewBag、PartialView() 這些產生 HTML 畫面用的東西
用在Web API：回 JSONMVC 網站：回 HTML 頁面

Controller 本身就是繼承 ControllerBase，再多加產生畫面的那些方法。Web API 只回 JSON、不產生畫面，所以繼承 ControllerBase 就夠了，不會多出一堆用不到的方法。

那 app.MapControllers() 啟動時掃描，是怎麼判斷「這個類別是 Controller」的？只要是 public、不是 abstract 的類別，符合下面任一條就算：

  • 類別名稱以 Controller 結尾，例如 WeatherForecastController
  • 類別本身或它繼承的類別上標了 [Controller]。ControllerBase 身上就標了這個，所以繼承它的類別，不管叫什麼名字都會被認出來

[ApiController] 加在 Controller 類別上，讓你不用在每個方法開頭自己檢查送來的資料合不合格：驗證失敗自動回 400，方法不會被呼叫；物件型別的參數自動從 body 的 JSON 拿；錯誤回應統一成 ProblemDetails 格式。每個 API 的 Controller 類別上都要加。

下面兩個 Controller 的方法內容一樣，差別只在有沒有 [ApiController]，用來實測這三件事：

public class CreateRequest

    public string? Title { get; set; }
}

[ApiController]                      // ← 有
[Route("with")]
public class WithController : ControllerBase
{

    public IActionResult Create(CreateRequest request)
    {
        // new { … } 是匿名物件，轉成 JSON 就是 {"called":true,"title":…}
        // called 用來看這個方法到底有沒有被呼叫
        return Ok(new { called = true, request.Title });

    [HttpGet("{id}")]
    public IActionResult Get(int id)

[Route("without")]                   // ← 沒有 [ApiController]

    }

    [HttpPost("body")]
    public IActionResult CreateBody([FromBody] CreateRequest request)
    {
        return Ok(new { called = true, request.Title, valid = ModelState.IsValid });
    }

    [HttpGet("{id}")]
    public IActionResult Get(int id)
    {
        return NotFound();
    }
}

① 驗證失敗自動回 400，方法不會被呼叫

送一個沒有 title 的 JSON：

POST /with           body: {}
→ 400 {"type":"https://tools.ietf.org/html/rfc9110#section-15.5.1",
       "title":"One or more validation errors occurred.","status":400,
       "errors":{"Title":["The Title field is required."]},"traceId":"…"}

POST /without/body   body: {}
→ 200 {"called":true,"title":null,"valid":false}

有 [ApiController] 的那邊，回應裡沒有 called，代表 Create() 根本沒被呼叫，框架在進方法之前就擋下來回 400 了。沒有的那邊，方法照樣被呼叫，Title 是 null，只是 ModelState.IsValid 變成 false。要擋的話，每個方法開頭都得自己寫：

if (!ModelState.IsValid)
{
    return BadRequest(ModelState);
}

② 自動推斷參數來源

這次送有 title 的 JSON：

POST /with           body: {"title":"Hi"}
→ 200 {"called":true,"title":"Hi"}

POST /without        body: {"title":"Hi"}
→ 200 {"called":true,"title":null,"valid":false}

POST /without/body   body: {"title":"Hi"}
→ 200 {"called":true,"title":"Hi","valid":true}

有 [ApiController] 時，框架照上一節的規則看到 CreateRequest 是物件型別，就去 body 的 JSON 拿。沒有的話，物件型別參數預設是從表單欄位、query string 找，不會去讀 body 的 JSON，所以 JSON 送了等於沒送，Title 是 null。要自己在參數前標 [FromBody]，像 /without/body 那樣，才拿得到。

③ 錯誤回應統一用 ProblemDetails 格式

GET /with/5      → 404 {"type":"https://tools.ietf.org/html/rfc9110#section-15.5.5",
                        "title":"Not Found","status":404,"traceId":"…"}

GET /without/5   → 404（body 是空的）

兩邊都是 return NotFound();，有 [ApiController] 的那邊會自動補上一段 JSON。這個格式叫 ProblemDetails，固定有 type、title、status 欄位；① 的 400 也是同一個格式，只是多了 errors。這樣前端不管收到哪種錯誤，都用同一套方式讀。

Program.cs 的四個階段：CreateBuilder → Build → Use／Map → Run

Program.cs 分成四段，知道順序才知道新的一行該加在哪裡，順序錯了會出事：Build() 之前登記「有什麼東西可以用」，之後排「請求怎麼走」，Run() 開始聽請求。builder.Services.Add… 一律寫在 Build() 前面；看到 Unable to resolve service 就是忘了登記。

把範本的 Program.cs 從頭看一遍，它是四個階段，順序不能換：

那一行做什麼目的是什麼
WebApplication.CreateBuilder(args)做一個 builder。它會先讀 appsettings.json、appsettings.Development.json、環境變數、命令列參數，設定好 log，並準備一本空的登記簿 builder.Services準備階段：收集設定、準備登記簿
builder.Services.AddXxx()往登記簿寫「之後有人要 X 時，怎麼做一個」。這時還沒做出任何東西決定這個程式「有哪些東西可以用」
builder.Build()登記簿定案，做出 app（型別是 WebApplication）。之後再 builder.Services.Add… 會丟例外（實測）：
InvalidOperationException: The service collection cannot be modified because it is read-only.		把「準備」和「執行」分成兩段，Build 是分界線
app.UseXxx() / app.MapXxx()排請求的管線。Use… 是每個請求都會經過的關卡（http 轉 https、檢查授權）；Map… 是終點：哪條路徑交給誰（MapControllers 就是建上面的路由表）決定請求進來之後依序經過什麼
app.Run()啟動 Kestrel 伺服器，開始聽 port，然後卡在這一行，直到 Ctrl+C 或程序被關掉。寫在 Run() 後面的程式碼要等伺服器關掉才會執行（實測）開門營業。到這裡之前，一個請求都還沒進來

這幾行哪些可以換位置

分界線是 builder.Build()：Add… 一律在它之前，Use… 和 Map… 一律在它之後。在同一邊裡面，有的可以換、有的換了結果會不同：

哪幾行能不能換原因
AddControllers() 和 AddOpenApi() 彼此可以兩行都只是往登記簿各寫一筆，誰先寫結果一樣
Add… 移到 Build() 之後不行Build() 之後登記簿不能再改，程式一啟動就丟例外（下面有實測）
Use…、Map… 移到 Build() 之前不行app 是 Build() 做出來的，在那之前還沒有 app 這個變數，編譯不會過
UseHttpsRedirection() 和 UseAuthorization() 彼此換了順序就不同請求照程式碼寫的順序，一關一關經過。這個專案沒有設定權限，對調了看不出差別；照範本的順序放就好
MapControllers() 和 Use… 之間可以請求一定先走完所有 Use… 的關卡，最後才查路由表，和 Map… 寫在第幾行無關
app.Run()要在最後程式會卡在這一行，寫在它後面的 Use…、Map… 等於沒寫

Run() 要聽哪個 port：Properties/launchSettings.json

app.Run() 沒有寫網址，要聽哪個 port、用什麼環境，是 Properties\launchSettings.json 決定的。連不上時來這裡對 applicationUrl。這個檔案只在開發機用，不會跟著發佈。

dotnet run 啟動時會讀這個檔案。題 1 建的專案裡也有這個檔案。下面是範本專案的內容，你的檔案一樣有 http、https 兩組設定，port 的數字會不同：

欄位做什麼影響到哪裡
profiles 底下的 http、https兩組啟動設定。dotnet run 沒指定時用第一個；要指定就寫 dotnet run --launch-profile https這一課的 dotnet run 都沒指定，用的是第一組 http
commandName: "Project"用「執行這個專案」的方式啟動，相當於 dotnet run一般不用動
applicationUrlRun() 要聽的網址和 port。port 數字是建專案時隨機抽的，所以每個人的不一樣終端機印的 Now listening on: http://localhost:5298；Postman 的網址要填這個 port
environmentVariables 裡的 ASPNETCORE_ENVIRONMENT啟動時設一個環境變數，值是 Developmentapp.Environment.IsDevelopment() 回 true；會多讀 appsettings.Development.json
launchBrowser啟動時要不要自動開瀏覽器API 專案通常 false
dotnetRunMessagesdotnet run 時要不要印 Building… 這類訊息只影響終端機輸出

不是用 dotnet run 啟動時（例如發佈後直接跑 dotnet TodoApi.dll，或放進 Docker），launchSettings.json 不會被讀，port 改由環境變數 ASPNETCORE_URLS 或參數 --urls http://… 決定。這一課先知道有這件事就好。

5. 常見坑

  • 用 webapi 範本建專案時忘了 --use-controllers：專案裡沒有 Controllers 資料夾，Program.cs 裡是 app.MapGet(…)。那是題 1 那種 Minimal API 的寫法。把專案資料夾刪掉、dotnet sln remove 之後重建最快
  • 改了程式但結果沒變：程式要停掉再啟動才會用新的程式碼。按 Ctrl+C 停掉，再 dotnet run 一次
  • Postman 網址的 port 和實際的不一樣：出現「連線被拒絕」（ECONNREFUSED）時，對一下網址裡的 port 和終端機印的 Now listening on
  • POST 回 415 Unsupported Media Type：請求少了 Content-Type: application/json 這個 header，框架不知道 body 是 JSON。Postman 的 Body 分頁選 raw 之後，格式要選 JSON，不是 Text
  • 路徑是 /api/todos 不是 /todos：看 Controller 上的 [Route("api/[controller]")]，前面有 api/
  • static List 只適合練習：兩個請求同時新增時，List 和 _nextId++ 都可能出錯（它們不是設計給多個執行緒同時用的）。真的專案不會這樣存資料，下一個專案就換成資料庫
