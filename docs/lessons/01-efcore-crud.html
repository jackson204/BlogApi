2-1. 從 ADO.NET 推演到 ORM

.NET 內建的資料庫存取方式叫做 ADO.NET。連 SQL Server 用的是 Microsoft.Data.SqlClient 套件（第 0 課連線字串提到的就是它）。先用它寫「文章列表」和「新增文章」，感受一下：

第 1 步：純 ADO.NET（實際連到第 0 課的容器驗證過）

public static async Task<List<Post>> GetAllAsync(string connectionString)
{
    var posts = new List<Post>();

    await using var connection = new SqlConnection(connectionString);   // 1. 建立連線
    await connection.OpenAsync();                                        // 2. 打開連線

    var sql = "SELECT Id, Title, Content, CreatedAt, UpdatedAt FROM Posts ORDER BY CreatedAt DESC";
    await using var command = new SqlCommand(sql, connection);           // 3. 準備 SQL
    await using var reader = await command.ExecuteReaderAsync();         // 4. 執行

    while (await reader.ReadAsync())                                     // 5. 一列一列讀
    {
        posts.Add(new Post                                               // 6. 一欄一欄塞回物件
        {
            Id = reader.GetInt32(0),
            Title = reader.GetString(1),
            Content = reader.GetString(2),
            CreatedAt = reader.GetDateTime(3),
            UpdatedAt = reader.IsDBNull(4) ? null : reader.GetDateTime(4)
        });
    }

    return posts;
}

public static async Task<int> InsertAsync(string connectionString, string title, string content)
{
    await using var connection = new SqlConnection(connectionString);
    await connection.OpenAsync();

    var sql = """
        INSERT INTO Posts (Title, Content, CreatedAt)
        OUTPUT INSERTED.Id
        VALUES (@title, @content, @createdAt)
        """;
    await using var command = new SqlCommand(sql, connection);
    command.Parameters.AddWithValue("@title", title);                    // 參數化，防 SQL Injection
    command.Parameters.AddWithValue("@content", content);
    command.Parameters.AddWithValue("@createdAt", DateTime.UtcNow);

    return (int)(await command.ExecuteScalarAsync())!;
}

能用，但問題很多：

痛點具體來說
重複的樣板程式每個查詢都要「開連線 → 準備 SQL → 執行 → 讀取」，五支 API 就寫五次
SQL 是字串"SELECT Titel ..." 打錯字，編譯會過，執行時才爆
手動對應欄位reader.GetString(1) 靠位置對應。SELECT 多加一個欄位，後面的編號全部要改
改表要改很多地方Posts 加一個欄位，所有相關的 SELECT、INSERT、對應程式都要找出來改
型別要自己顧驗證時發現：AddWithValue 會猜型別，把 DateTime 當成舊的 datetime（精度只有約 3 毫秒），寫進 datetime2 欄位的時間被四捨五入了
安全靠自律忘了用 @參數、改成字串相加，就有 SQL Injection 漏洞

第 2 步：自然會想「把重複的部分抽出來」。把「讀取結果、依欄位名稱塞進物件」寫成共用函式，就是 Dapper 這類「微型 ORM」做的事。SQL 還是自己寫，但對應和參數化交給它：

Dapper 寫法示意（本課程不會安裝 Dapper）

await using var connection = new SqlConnection(connectionString);
var posts = await connection.QueryAsync<Post>(
    "SELECT * FROM Posts WHERE Title LIKE @keyword",
    new { keyword = $"%{keyword}%" });

第 3 步：再往前一步，連 SQL 都不想手寫。如果工具知道「Post class 對應 Posts 表」，就能直接把 C# 的查詢翻成 SQL，還能記住哪些欄位改過、自動產生建表的 SQL。這就是完整的 ORM（Object-Relational Mapping，物件關聯對應），EF Core 就是其中一個：

var posts = await _db.Posts.Where(p => p.Title.Contains(keyword)).ToListAsync();
從 ADO.NET → Dapper → EF Core：工具幫你做的事越來越多

💡 ORM 沒有讓 SQL 消失：EF Core 底下還是用 ADO.NET（SqlClient）把 SQL 送到資料庫。所以這一課最後會觀察它產生的 SQL，確認它做的事跟你想的一樣。

2-3. ORM：class 和資料表怎麼對應？

C#（EF Core）資料庫說明
Entity class Post資料表 Posts一個 class 對應一張表
屬性 Title欄位 Title一個屬性對應一個欄位
一個 Post 物件一列資料
DbSet<Post> Posts代表整張 Posts 表對它下 LINQ，就是對這張表查詢
DbContext一次和資料庫的「工作階段」管理連線、追蹤物件變化、SaveChanges 時一次寫入
屬性名稱叫 Id主鍵 + 自動編號（IDENTITY）EF Core 的慣例，不用另外設定

慣例不夠用時：Data Annotations 和 Fluent API

EF Core 會依照慣例決定欄位型別，例如 string 預設變成 nvarchar(max)。但部落格的標題只想要最多 200 字，慣例做不到，就要自己設定。設定的寫法有兩種：

同一個規則「Title 最多 200 字」的兩種寫法，產生的資料表完全一樣
① Data Annotations② Fluent API（本課使用）
寫在哪Entity class 的屬性上方，用 [ ] 標註DbContext 覆寫 OnModelCreating 方法
從哪來.NET 內建的 System.ComponentModel.DataAnnotations 命名空間，不是 EF Core 專屬的EF Core 的 ModelBuilder
最多 200 字[MaxLength(200)].HasMaxLength(200)
能做的事常見的：長度、必填、欄位名稱、主鍵全部：上面那些，再加上索引、複合主鍵、關聯、預設值……
兩邊都寫時Fluent API 優先

本課程用 Fluent API。理由是：第 2 課的一對多、多對多關聯，有些設定只有 Fluent API 做得到。與其兩種混著用，不如一開始就統一用 Fluent API，Entity class 也能保持乾淨，只放資料。

不過 Data Annotations 還是要認得，因為題 6 的 API 輸入驗證會用到它（[Required]、[MaxLength]）。那是另一個用途，到時候再說明。

2-4. DbContext 和 DbSet 是什麼？

上面的表格裡，最重要的兩個角色是 DbContext 和 DbSet。你的程式只跟它們說話，不直接碰連線和 SQL。

DbContext 是一個「工作階段」，裡面有查詢入口（DbSet）、記帳本（ChangeTracker）、連線

DbContext：和資料庫的一次「工作階段」

  • 你寫的 BlogDbContext 繼承 EF Core 的 DbContext，所以免費得到查詢、追蹤、儲存這些能力
  • 一個請求用一個：請求開始時建立、結束時丟掉。不要把它存成 static 共用，它不是 thread-safe，多個請求同時用會出錯
  • 它負責三件事：
    1. 提供查詢入口：透過 DbSet
    2. 記帳：ChangeTracker 記住查出來或加進去的物件，以及它們被改了什麼（2-6 會詳細講）
    3. 管理連線：需要時才開連線，用完還回連線池，你不用寫 new SqlConnection

DbSet<T>：代表一張資料表

  • DbSet<Post> Posts 代表 Posts 這張表。DbContext 裡有幾個 DbSet，資料庫就有幾張表（Migration 就是看這個決定要建哪些表）
  • 它實作了 IQueryable<Post>，所以可以直接接 LINQ：_db.Posts.Where(…)
常用寫法做什麼什麼時候送出 SQL
_db.Posts.Where(…).ToListAsync()查詢多筆ToListAsync() 時
_db.Posts.FindAsync(id)用主鍵查一筆。如果這個物件已經被追蹤，直接回傳，不查資料庫呼叫時（必要時才查）
_db.Posts.Add(post)標記成「要新增」不會，要等 SaveChanges
_db.Posts.Remove(post)標記成「要刪除」不會，要等 SaveChanges
_db.SaveChangesAsync()把所有記帳內容一次寫進資料庫。注意它在 DbContext 上，不在 DbSet 上呼叫時

2-5. Migration：C# 改了，資料表怎麼跟著改？

你修改 Entity class 後，資料庫不會自己變。Migration 會比對「現在的 class」和「上一次的快照」，產生一份變更紀錄（C# 檔），再由它產生 SQL 去改資料庫。

flowchart LR A["Post.cs
BlogDbContext.cs"] -- "dotnet ef migrations add 名稱" --> B["Migrations 資料夾
xxxx_InitialCreate.cs
（變更紀錄，要 commit）"] B -- "dotnet ef database update" --> C["產生 SQL
CREATE TABLE Posts ..."] C --> D[("BlogDb
Posts 表")] C --> E[("__EFMigrationsHistory
記錄已套用到哪一版")]
Migration 就像資料庫的 git commit，每一次變更都有紀錄，可以追蹤、也可以退回

2-6. Change Tracking：為什麼要呼叫 SaveChanges？

DbContext 會追蹤透過它查出來或加進去的物件。你對物件做的事情只是在「記帳」，呼叫 SaveChangesAsync() 時才一次產生 SQL 寫進資料庫。

stateDiagram-v2 [*] --> Added: _db.Posts.Add(post) Added --> Unchanged: SaveChanges 時送出 INSERT [*] --> Unchanged: 查詢出來，例如 FindAsync Unchanged --> Modified: 修改屬性 post.Title = ... Modified --> Unchanged: SaveChanges 時送出 UPDATE Unchanged --> Deleted: _db.Posts.Remove(post) Deleted --> [*]: SaveChanges 時送出 DELETE
忘了呼叫 SaveChanges，資料就只停留在「記帳」階段，不會進資料庫

2-7. LINQ 什麼時候才真的查資料庫？

Where、OrderBy 只是在組合查詢條件，還沒送出任何 SQL。要等到呼叫 ToListAsync()、FirstOrDefaultAsync()、CountAsync() 這類「要拿結果」的方法，才會真的執行。這叫做延遲執行（deferred execution）。

flowchart LR A["_db.Posts"] --> B[".Where(...)"] --> C[".OrderByDescending(...)"] --> D[".ToListAsync()"] D == "這時候才送出 SQL" ==> E[("SQL Server")] A -.-|"到這裡都還沒查資料庫"| C

所以可以先 var query = _db.Posts.AsQueryable();，再依照條件決定要不要加 Where。最後只會送出一句組合好的 SQL。

3-3. Entity 和 DbContext

語法骨架

public class 類別名稱
{
    public int Id { get; set; }                  // 叫 Id → 自動當主鍵
    public string 欄位 { get; set; } = string.Empty;
}

public class 名稱DbContext : DbContext
{
    public 名稱DbContext(DbContextOptions<名稱DbContext> options) : base(options) { }

    public DbSet<類別名稱> 表名 => Set<類別名稱>();

    // 慣例不夠用時，在這裡用 Fluent API 補充設定
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<類別名稱>(entity =>
        {
            entity.Property(x => x.欄位).設定方法(…);
        });
    }
}
  • protected override：OnModelCreating 是父類別 DbContext 本來就有的方法，這裡覆寫它，加上自己的設定。EF Core 建立模型時會自動呼叫它
  • modelBuilder.Entity<Post>(entity => { … })：又是一個 Action（見 3-5 ①），entity 代表「Post 的設定器」
  • entity.Property(x => x.Title)：用 lambda 指定要設定哪個屬性，打錯字編譯就會發現
  • 常用設定方法：.HasMaxLength(200)、.IsRequired()、.HasColumnName("…")、.HasDefaultValueSql("…")

3-4. 連線字串：用 User Secrets，不要寫進 appsettings

⚠️ 你的 repo 是 public 的。appsettings.Development.json 會被 commit，裡面的密碼全世界都看得到。

User Secrets 把機密存在專案資料夾以外（Windows 的 %APPDATA%\Microsoft\UserSecrets\），所以不會被 commit。開發環境（Development）執行時，.NET 會自動讀它。

dotnet user-secrets init                       # 在 csproj 加上 UserSecretsId
dotnet user-secrets set "區段:鍵" "值"           # 冒號代表 JSON 的階層
dotnet user-secrets list                       # 看目前存了什麼

"ConnectionStrings:BlogDb" 等同 JSON 的 { "ConnectionStrings": { "BlogDb": "..." } }。Rider 也可以對專案按右鍵 → Tools → .NET User Secrets 直接編輯。

3-5. 註冊 DbContext

builder.Services.AddDbContext<名稱DbContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("連線字串名稱")));

要寫在 Program.cs 的 builder.Build() 之前。這行的意思是「之後有人需要 DbContext 時，用這個連線字串建立一個給它」。

① 先認識 Action 和 Func

看 AddDbContext 的簽章時，會看到參數型別是 Action<DbContextOptionsBuilder>。要看懂它，得先知道什麼是委派（delegate）。

委派就是「裝著一個方法的變數」。一般的變數裝的是值（數字、字串），委派裝的是「一段可以執行的程式」。.NET 內建兩種最常用的委派：

Action 只做事、不回傳；Func 最後一個型別是回傳值
ActionFunc
回傳值沒有（等於 void 方法）有，角括號裡最後一個型別就是回傳型別
寫法Action<參數1, 參數2, …>Func<參數1, 參數2, …, 回傳>
例子Action<string>＝收一個 string、不回傳Func<int, int, int>＝收兩個 int、回傳 int

簡單範例：先用具名方法，再改用 lambda（實際執行過）

// 1. 先用具名方法
void SayHello() => Console.WriteLine("Hello");
int Add(int a, int b) => a + b;

Action hello = SayHello;          // 把「方法」裝進變數（注意：SayHello 後面沒有括號）
Func<int, int, int> add = Add;
hello();                          // 執行變數裡的方法 → Hello
Console.WriteLine(add(1, 2));     // → 3

// 2. 改用 lambda，不用另外取名字
Action<string> greet = name => Console.WriteLine($"Hi, {name}");
Func<int, int, int> multiply = (a, b) => a * b;
Func<string, bool> isLong = title => title.Length > 5;
greet("小明");                     // → Hi, 小明
Console.WriteLine(multiply(3, 4)); // → 12
Console.WriteLine(isLong("EF Core 入門")); // → True

lambda 的讀法：參數 => 要做的事。=> 念成「goes to」，左邊是參數，右邊是內容。只有一個參數時可以省略括號，像 name => …；兩個以上要加括號，像 (a, b) => …。

進階範例：把方法當參數傳給別人，由別人決定什麼時候執行（實際執行過）

void RunLater(Action<string> action)
{
    Console.WriteLine("RunLater 開始，還沒執行 action");
    action("由 RunLater 傳進來的值");   // 由 RunLater 決定什麼時候執行、傳什麼值
}

RunLater(text => Console.WriteLine($"action 執行了：{text}"));

// 輸出：
// RunLater 開始，還沒執行 action
// action 執行了：由 RunLater 傳進來的值

這就是 AddDbContext 的模式：

  • 你傳進去的 options => options.UseSqlServer(…) 是一個 Action<DbContextOptionsBuilder>
  • options 是 EF Core 之後會傳進來的，就像上面的 text 是 RunLater 傳進來的
  • 什麼時候執行，由 EF Core 決定，見 ③

你其實早就用過 Func 了：_db.Posts.Where(p => p.Title.Contains(keyword)) 裡的 p => …，寫法就是一個「收 Post、回傳 bool」的 lambda。（細節：EF Core 實際收的型別是 Expression<Func<Post, bool>>，它會把這段 lambda 當成「資料」拆開，才能翻成 SQL；後面的課再細講。）

② 這一行是怎麼來的？學會看方法簽章

這行其實是三個方法一層包一層。括號最裡面的先執行，所以要由內往外讀：

③ 的回傳值餵給 ②，② 所在的整段 lambda 再餵給 ①

下面是這三個方法在 EF Core 10 / .NET 10 的真正簽章（用反射從套件讀出來的，只列出這一行用到的那個多載）：

③ Microsoft.Extensions.Configuration.ConfigurationExtensions

public static string? GetConnectionString(
    this IConfiguration configuration,
    string name)

② Microsoft.EntityFrameworkCore.SqlServerDbContextOptionsExtensions

簽章怎麼讀：逐一對照

看到什麼代表什麼對應到我們那一行
static + 第一個參數有 this擴充方法（extension method）。可以像「那個型別本來就有的方法」一樣，用 . 呼叫this IServiceCollection → 所以寫成 builder.Services.AddDbContext(…)，builder.Services 的型別就是 IServiceCollection
方法名稱後面的 <TContext>泛型參數，呼叫時填入型別AddDbContext<BlogDbContext>
where TContext : DbContext泛型限制：填進去的型別必須繼承 DbContextBlogDbContext : DbContext，所以可以；填 string 會編譯錯誤
Action<DbContextOptionsBuilder>委派：「一個收 DbContextOptionsBuilder、沒有回傳值的方法」。可以用 lambda 寫options => options.UseSqlServer(…)，這裡的 options 型別就是 DbContextOptionsBuilder
= null、= ServiceLifetime.Scoped選擇性參數：沒傳就用預設值我們只傳了 lambda，所以生命週期都是 Scoped（一個請求一個，第 3 課講）

回傳型別和 this 參數型別相同可以串接呼叫（Fluent API）UseSqlServer 回傳 DbContextOptionsBuilder，後面還能再接 .LogTo(…) 這類設定

③ lambda 什麼時候執行？（第 3 課預告）

① 說過：lambda 交出去之後，什麼時候執行由 EF Core 決定。那到底是什麼時候？我寫了一個小程式實測：在 lambda 裡印一行字，看它在什麼時候出現。測試程式用的 DbContext 叫 DemoDb，「scope」可以先想成「一個請求」。

左邊是實測輸出，右邊是在真正的 API 裡代表什麼。紅色的「執行了」只出現在請求第一次需要 DbContext 的時候
輸出發生什麼事在 BlogApi 裡代表
AddDbContext 呼叫完畢
BuildServiceProvider 完畢		兩行之間沒有「執行了」，代表 lambda 還沒跑Program.cs 跑完 AddDbContext 和 builder.Build()，程式啟動了，但一個 DbContext 都還沒建立
取得 DemoDb 之前
-> optionsAction 執行了
取得 DemoDb 之後		第一次要 DbContext 時，lambda 才執行，用它的設定建立 DbContext第一個請求進來，ASP.NET Core 建立 PostsController，建構子需要 BlogDbContext，這時候才建立 #1
同一個 scope 拿兩次是同一個物件？True同一個 scope 第二次要，不會再執行 lambda，直接給同一個同一個請求裡，不管幾個地方要 DbContext，拿到的都是 #1
第二個 scope 取得 DemoDb 之前
-> optionsAction 執行了		換一個 scope，lambda 再執行一次，建立新的第二個請求有自己的 DbContext #2，和 #1 互不影響

結論：AddDbContext 的意思是「登記一份做法」，不是「現在就建立 DbContext」。每個請求各自建立一個、用完就丟，這叫做 Scoped 生命週期。為什麼要這樣設計？如果全部請求共用一個會怎樣？這些是第 3 課的主題。

public class Post
{
    public int Id { get; set; }

    public string Title { get; set; } = string.Empty;

    public string Content { get; set; } = string.Empty;

    public DateTime CreatedAt { get; set; }

    public DateTime? UpdatedAt { get; set; }

BlogApi/Data/BlogDbContext.cs

using BlogApi.Models;
using Microsoft.EntityFrameworkCore;

namespace BlogApi.Data;

public class BlogDbContext : DbContext
{
    public BlogDbContext(DbContextOptions<BlogDbContext> options) : base(options)
    {
    }

    public DbSet<Post> Posts => Set<Post>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Post>(entity =>
        {
            entity.Property(p => p.Title).HasMaxLength(200);
        });
    }
}
  • Post.cs 只有屬性，沒有任何資料庫設定；「最多 200 字」集中寫在 BlogDbContext
  • = string.Empty：專案有開 Nullable，string 代表「不可以是 null」，所以要給預設值，不然編譯器會警告
  • DbSet<Post> Posts => Set<Post>();：官方文件也常見 public DbSet<Post> Posts { get; set; }，兩種都可以。用 => Set<Post>() 的好處是不會有 nullable 警告

題 6：PostsController 五支 API

需求：完成第 1 節表格裡的 5 支 API。另外：

  • 新增、修改時，前端只能傳 title 和 content。Id、CreatedAt 由後端決定，不能讓前端亂傳
  • title、content 必填，title 最多 200 字；不符合要回 400
  • 列表依 CreatedAt 新到舊排序；有傳 keyword 時只回傳標題包含關鍵字的文章
  • 找不到 id 時回 404
  • 全部使用 async 版本的方法

💡 提示：每支 API 用到什麼

APIEF Core 方法成功時回傳
GET 列表Where、OrderByDescending、ToListAsync200 + 陣列
GET 單筆FindAsync(id)200 + 物件
POSTAdd → SaveChangesAsync201 CreatedAtAction
PUTFindAsync → 改屬性 → SaveChangesAsync204 NoContent
DELETEFindAsync → Remove → SaveChangesAsync204 NoContent

「前端只能傳 title 和 content」：另外寫一個只有這兩個屬性的 record 當參數型別，不要直接用 Post。

「必填、最多 200 字，不符合回 400」：在 record 的參數上加 Data Annotations 的 [Required]、[MaxLength(200)]（using System.ComponentModel.DataAnnotations;）。[ApiController] 收到請求時會自動檢查，不符合就直接回 400，連你的方法都不會進去。

🤔 題 3 不是說用 Fluent API 嗎？為什麼這裡又用 Data Annotations？

因為管的是兩件不同的事：

  • 題 3 的 HasMaxLength(200)：管資料庫，決定欄位是 nvarchar(200)。只有 EF Core 看得懂
  • 這裡的 [MaxLength(200)]：管 API 的輸入，前端送來的資料太長就回 400。是 ASP.NET Core 在看，Fluent API 做不到這件事

如果只有資料庫限制、沒有輸入驗證，前端送 300 字的標題，要等到寫進資料庫時才出錯，前端拿到的會是 500，而不是清楚的 400。

✅ 驗收：用題 7 的 .http 檔，每支 API 都回傳正確的狀態碼

參考答案（寫完再打開）

BlogApi/Models/PostRequest.cs

using System.ComponentModel.DataAnnotations;

namespace BlogApi.Models;

// 新增、修改文章時，前端只能傳這兩個欄位
public record PostRequest(
    [Required, MaxLength(200)] string Title,
    [Required] string Content);

BlogApi/Controllers/PostsController.cs

using BlogApi.Data;
using BlogApi.Models;
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;

namespace BlogApi.Controllers;

[ApiController]
[Route("api/[controller]")]
public class PostsController : ControllerBase
{
    private readonly BlogDbContext _db;

    public PostsController(BlogDbContext db)
    {
        _db = db;
    }

    // GET api/posts?keyword=docker
    [HttpGet]
    public async Task<ActionResult<List<Post>>> GetAll(string? keyword)
    {
        var query = _db.Posts.AsQueryable();

        if (!string.IsNullOrWhiteSpace(keyword))
        {
            query = query.Where(p => p.Title.Contains(keyword));
        }

        var posts = await query
            .OrderByDescending(p => p.CreatedAt)
            .ToListAsync();

        return posts;
    }

    // GET api/posts/5
    [HttpGet("{id}")]
    public async Task<ActionResult<Post>> GetById(int id)
    {
        var post = await _db.Posts.FindAsync(id);
        if (post is null)
        {
            return NotFound();
        }

        return post;
    }

    // POST api/posts
    [HttpPost]
    public async Task<ActionResult<Post>> Create(PostRequest request)
    {
        var post = new Post
        {
            Title = request.Title,
            Content = request.Content,
            CreatedAt = DateTime.UtcNow
        };

        _db.Posts.Add(post);
        await _db.SaveChangesAsync();

        return CreatedAtAction(nameof(GetById), new { id = post.Id }, post);
    }

    // PUT api/posts/5
    [HttpPut("{id}")]
    public async Task<IActionResult> Update(int id, PostRequest request)
    {
        var post = await _db.Posts.FindAsync(id);
        if (post is null)
        {
            return NotFound();
        }

        post.Title = request.Title;
        post.Content = request.Content;
        post.UpdatedAt = DateTime.UtcNow;

        await _db.SaveChangesAsync();
        return NoContent();
    }

    // DELETE api/posts/5
    [HttpDelete("{id}")]
    public async Task<IActionResult> Delete(int id)
    {
        var post = await _db.Posts.FindAsync(id);
        if (post is null)
        {
            return NotFound();
        }

        _db.Posts.Remove(post);
        await _db.SaveChangesAsync();
        return NoContent();
    }
}
  • 為什麼不用 Post 當參數？如果前端傳 {"id": 999, "createdAt": "1999-01-01"}，這些值會被直接寫進去。這叫做 over-posting。用 PostRequest 就只收得到兩個欄位
  • PUT 為什麼沒有呼叫 Update()？FindAsync 查出來的物件已經被追蹤（Unchanged），改屬性後會自動變成 Modified，SaveChangesAsync 就會送出 UPDATE（見 2-6）
  • CreatedAt 用 DateTime.UtcNow：存 UTC 時間，前端再依照使用者的時區顯示，避免伺服器搬到其他時區時時間錯亂

5. 觀察 SQL：LINQ 對照產生的 SQL

以下是題 7 實際執行時，EF Core 10 印出的 SQL（只保留重點）：

C#產生的 SQL
_db.Posts
  .OrderByDescending(p => p.CreatedAt)
  .ToListAsync()
 
SELECT [p].[Id], [p].[Content], [p].[CreatedAt],
       [p].[Title], [p].[UpdatedAt]
FROM [Posts] AS [p]
ORDER BY [p].[CreatedAt] DESC
 
.Where(p => p.Title.Contains(keyword))
 
WHERE [p].[Title] LIKE @keyword_contains ESCAPE N'\'
-- @keyword_contains = N'%Docker%'
 
_db.Posts.FindAsync(id)
 
SELECT TOP(1) [p].[Id], [p].[Content], ...
FROM [Posts] AS [p]
WHERE [p].[Id] = @p
 
_db.Posts.Add(post);
await _db.SaveChangesAsync();
 
INSERT INTO [Posts] ([Content], [CreatedAt],
                     [Title], [UpdatedAt])
OUTPUT INSERTED.[Id]
VALUES (@p0, @p1, @p2, @p3);
 
post.Title = ...;
post.Content = ...;
post.UpdatedAt = ...;
await _db.SaveChangesAsync();
 
UPDATE [Posts] SET [Content] = @p0, [Title] = @p1,
                   [UpdatedAt] = @p2
OUTPUT 1
WHERE [Id] = @p3;
 
_db.Posts.Remove(post);
await _db.SaveChangesAsync();
 
DELETE FROM [Posts]
OUTPUT 1
WHERE [Id] = @p0;

從 SQL 看出來的重點

  • 全部都是參數化查詢（@p0、@keyword_contains），值不會直接拼進 SQL 字串，所以不會有 SQL Injection
  • OUTPUT INSERTED.[Id]：INSERT 時順便把資料庫產生的自動編號拿回來，這就是 SaveChangesAsync() 之後 post.Id 會有值的原因
  • UPDATE 只更新有改的欄位：CreatedAt 沒改，所以不在 SET 裡面。這是 Change Tracking 的功勞
  • PUT 和 DELETE 都是兩句 SQL：先 SELECT TOP(1)（FindAsync），再 UPDATE / DELETE。之後的課會介紹 ExecuteUpdateAsync / ExecuteDeleteAsync，可以一句完成
  • Contains 變成 LIKE '%...%'：前後都有 %，資料量大時用不到索引，第 4 課談效能時會再提

6. 優缺點 & 常見坑

優點

  • 用 C# 型別寫查詢，打錯欄位名稱編譯時就會發現
  • 自動參數化，預設就能防 SQL Injection
  • Migration 讓資料庫結構有版本紀錄，換電腦一個指令就能重建

缺點

  • 產生的 SQL 不一定是最佳寫法，要養成看 SQL log 的習慣
  • 多了一層抽象，出問題時要同時懂 C# 和 SQL 才好排查

常見坑
