1. 為什麼需要 log（你其實已經在用了）

📋 情境：主管說「昨天下午三點有人回報新增文章失敗」。你打開 Rider，Run 視窗是今天早上才開的，昨天的東西一行都不在。

log 要解決三件事：

  • 留下來：寫進檔案或資料庫，程式關掉、電腦重開都還在
  • 分等級：出事時只想看 Warning 以上，不想在幾千行 SQL 裡面找
  • 分來源：EF Core 的 SQL、框架的訊息、你自己寫的，各自放各自的地方

你其實已經在用 log 了。Run 視窗裡這些，全部是 .NET 內建的 ILogger 印出來的：

info: Microsoft.Hosting.Lifetime[14]
      Now listening on: http://localhost:5107
info: Microsoft.EntityFrameworkCore.Database.Command[20101]
      Executed DbCommand (18ms) [Parameters=[], CommandType='Text', CommandTimeout='30']
      SELECT [p].[Id], [p].[Content], [p].[CreatedAt], [p].[Title], [p].[UpdatedAt]
      FROM [Posts] AS [p]
片段叫什麼意思
info等級（LogLevel）Information，正常流程的訊息
Microsoft.Hosting.Lifetimecategory誰印的。慣例是「類別的全名」或命名空間
[14]EventId同一個 category 裡，這一種訊息的編號；你自己寫的 log 通常是 0
第二行起訊息內容

01 題 7 你在 appsettings.Development.json 加的這一行，就是在調 category 的門檻：

"Microsoft.EntityFrameworkCore.Database.Command": "Information"

意思是「category 是 Microsoft.EntityFrameworkCore.Database.Command 的 log，Information 以上都要印」。EF Core 一直都在送 SQL 的 log，是這個門檻原本設在 Warning，把它擋掉了。

2. .NET 的 logging 架構：ILogger、Category、LogLevel、Provider

寫 log 的程式碼、決定印到哪裡的程式碼，是分開的兩層。你的 Controller 只跟 ILogger 講話，不知道也不在乎最後是印到螢幕還是檔案：

flowchart LR C["PostsController
_logger.LogInformation(…)"] --> L1["ILogger#lt;PostsController#gt;
category = BlogApi.Controllers.PostsController"] E["EF Core"] --> L2["ILogger
category = Microsoft.EntityFrameworkCore.Database.Command"] L1 --> F["LoggerFactory"] L2 --> F F --> P1["Console Provider
（內建：Run 視窗）"] F --> P2["NLog Provider
（裝套件才有）"] P2 --> T1["File target
logs/app-日期.log"] P2 --> T2["Console target"] P2 --> T3["Database target"]
左邊是「誰在寫」，中間是「集中分發」，右邊是「寫到哪」。NLog 是一個 Provider，它自己裡面再分好幾個 target
名詞是什麼在 BlogApi 裡
ILogger<T>寫 log 的介面。<T> 只拿來決定 category 名稱（T 的全名）ILogger<PostsController> 的 category 是 BlogApi.Controllers.PostsController
category這行 log 是誰寫的，用來分流和設門檻你的 Controller、EF Core、Kestrel 各有各的名字
LogLevel六個等級（下表）找不到文章是 Warning，SaveChanges 爆掉是 Error
Provider把 log 送到某個地方的元件。一個程式可以掛好幾個內建有 Console、Debug、EventSource；NLog 是裝套件加上去的
builder.Logging.ClearProviders()把內建的 Provider 全部拔掉不拔的話，同一行會被內建 Console 印一次、NLog 的 console target 再印一次

ILogger<PostsController> 怎麼拿到？建構子多一個參數，跟 BlogDbContext 一樣，框架會自己塞進來。這套機制叫 DI，原理在第 3 課，這裡先照著用：

public PostsController(BlogDbContext db, ILogger<PostsController> logger)
{
    _db = db;
    _logger = logger;
}

六個等級，還有 NLog 叫它們什麼

.NET 的名字NLog 的名字什麼時候用BlogApi 的例子
TraceTrace每一步的變數值，量非常大幾乎不用
DebugDebug開發時想看的細節「查到 3 篇文章」
InformationInfo正常流程的里程碑「建立文章 5」、Now listening on
WarningWarn不正常，但程式處理掉了「找不到文章 999」然後回 404
ErrorError這一次請求失敗了未處理的例外、SaveChanges 失敗
CriticalFatal整個程式快掛了啟動時連不上資料庫

三個名字不一樣的要記：nlog.config 裡寫 minLevel="Info"，不是 Information。

3. NLog 的三個零件：Target、Rule、Layout

零件回答的問題例子
Target寫到哪？Console、File、Database；每個 target 有名字，rule 用名字指它
Rule誰的 log、什麼等級以上、送到哪幾個 target？「Microsoft.* 只留 Warn 以上」「其他全部 Info 以上寫到 console 和 file」
Layout一行長什麼樣？${longdate}|${level}|${logger}|${message}

這是題 1 要用的 nlog.config，先整份看過，下面逐行說：

BlogApi/nlog.config

<?xml version="1.0" encoding="utf-8" ?>
<nlog xmlns="http://www.nlog-project.org/schemas/NLog.xsd"
      xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
      throwConfigExceptions="true"
      autoReload="true"
      internalLogLevel="Warn"
      internalLogFile="${basedir}/logs/nlog-internal.log">

  <targets>
    <target xsi:type="Console" name="console" layout="${MicrosoftConsoleLayout}" />

    <target xsi:type="File" name="file"
            fileName="${basedir}/logs/app-${shortdate}.log"
            layout="${longdate}|${level:uppercase=true}|${logger}|${message:withexception=true}"
            maxArchiveFiles="7" />
  </targets>

  <rules>
    <logger name="System.*" finalMinLevel="Warn" />
    <logger name="Microsoft.*" finalMinLevel="Warn" />
    <logger name="Microsoft.Hosting.Lifetime*" finalMinLevel="Info" />
    <logger name="*" minLevel="Info" writeTo="console,file" />
  </rules>
</nlog>

最外層的四個屬性

屬性意思
throwConfigExceptions="true"設定檔寫錯時，啟動直接丟例外。預設是 false：錯了就整份設定作廢、什麼都不印，你會以為 NLog 壞了
autoReload="true"改了 nlog.config 不用重啟，NLog 會自己重讀
internalLogLevel、internalLogFileNLog 自己的 log。它寫不進檔案、連不上資料庫時，錯誤會記在這裡，不會丟到你的程式

Target：寫到哪

片段意思
xsi:type="Console" / "File"target 的種類。還有 Database、ColoredConsole、Mail 等，各自是不同的 NuGet 套件或內建
name="file"給 rule 的 writeTo 用的名字，自己取
layout="${MicrosoftConsoleLayout}"讓 console target 印出來的格式跟內建的一模一樣，Run 視窗看起來不會變
${basedir}程式執行的資料夾。開發時是 BlogApi/bin/Debug/net10.0，所以 log 會在 bin/Debug/net10.0/logs/（.gitignore 已經擋掉 logs/）
${shortdate}今天的日期 2026-11-01，所以每天一個檔：app-2026-11-01.log
maxArchiveFiles="7"最多留 7 個舊檔，再舊的自動刪

Layout：一行長什麼樣

${…} 叫 layout renderer，每個是一個欄位。用上面的 layout，一行長這樣：

2026-11-01 15:43:07.3968|INFO|BlogApi.Controllers.PostsController|建立文章 5：Docker 入門
renderer印出來
${longdate}2026-11-01 15:43:07.3968，本機時間
${level:uppercase=true}INFO、WARN、ERROR
${logger}category：BlogApi.Controllers.PostsController
${message:withexception=true}訊息；有例外時接著印 | 和例外的 ToString（含 stack trace）
${exception:format=tostring}只印例外，沒例外時是空字串
${aspnet-request-url}這行 log 是在處理哪個 URL 時寫的（NLog.Web.AspNetCore 提供）
${configsetting:item=ConnectionStrings.BlogDb}讀 appsettings 的值，例如連線字串

Rule：誰的 log、什麼等級、送去哪

四條 rule 由上往下逐條比對，每一行 log 都會走一遍：

屬性意思
name="Microsoft.*"比對 category，* 是萬用字元。Microsoft.EntityFrameworkCore.Database.Command、Microsoft.AspNetCore.Routing.EndpointMiddleware 都符合
minLevel="Info"這個等級以上才算符合
writeTo="console,file"送到哪些 target，逗號分隔
final="true"符合這條之後，後面的 rule 不再看
finalMinLevel="Warn"Warn 以下的直接丟掉、不往下走；Warn 以上的繼續往下找 rule。等於「這個來源只留 Warn 以上」。後面還有符合的 finalMinLevel 時，以後面那條為準

所以上面四條的意思是：

  1. System.* 和 Microsoft.* 的 Info、Debug 丟掉（EF Core 的 SQL 就在這裡被丟掉了）
  2. 但 Microsoft.Hosting.Lifetime* 的 Info 留著，因為 Now listening on 這幾行你會想看
  3. 剩下的（你的 Controller、Warn 以上的框架訊息）Info 以上寫到 console 和 file

為什麼第 2 條能救回第 1 條丟掉的東西？因為 finalMinLevel 的規矩是最後一條符合的贏：Microsoft.Hosting.Lifetime 的 log 同時符合 Microsoft.* 和 Microsoft.Hosting.Lifetime*，門檻取後面那條的 Info。所以具體的要放在籠統的後面；兩條對調，Now listening on 就從檔案裡消失（實測過）。writeTo 那種「寫出去」的 rule 則相反：放太前面，log 先被寫出去了，後面的 rule 再怎麼擋都來不及。

4. 寫 log 的正確姿勢

Message template：範本固定，值另外給

// ✅ 範本是固定字串，大括號是「名稱」，值用後面的參數依序填
_logger.LogInformation("建立文章 {PostId}：{Title}", post.Id, post.Title);

// ❌ 字串插值：範本每次都不一樣
_logger.LogInformation($"建立文章 {post.Id}：{post.Title}");

兩種寫法在 log 檔裡看起來一模一樣，都是 建立文章 5：Docker 入門。差別在 ✅ 多帶了兩個「屬性」：PostId = 5、Title = Docker 入門。log 寫成 JSON 時它們會變成獨立欄位，之後可以用 PostId 搜尋；❌ 只剩一串字。

兩個規矩：

  • 大括號裡是名稱，不是運算式。{post.Id} 不行，要寫 {PostId} 然後把 post.Id 當參數傳
  • Rider 會在 ❌ 那行畫提示 CA2254。建置時預設不會出警告，因為這條規則的嚴重性是「建議」，所以別靠建置抓它

例外要當第一個參數

catch (InvalidOperationException ex)
{
    _logger.LogError(ex, "讀取文章 {PostId} 失敗", id);   // ✅ 例外物件放第一個
    _logger.LogError(ex.Message);                           // ❌ 只剩一句話
}

兩種寫法在檔案裡的差別（同一個例外）：

2026-11-01 15:49:11.2867|ERROR|BlogApi.Controllers.PostsController|測試用例外
2026-11-01 15:49:11.3313|ERROR|BlogApi.Controllers.PostsController|讀取文章 997 失敗|System.InvalidOperationException: 測試用例外
   at BlogApi.Controllers.PostsController.GetById(Int32 id) in C:\Users\s9740\RiderProjects\BlogApi\BlogApi\Controllers\PostsController.cs:line 53

第一種出事時你只知道「有個測試用例外」，不知道從哪一行丟出來的。第二種有 stack trace，直接指到檔案和行號。

等級怎麼選

  • 程式處理掉了就是 Warning（找不到文章、驗證沒過）；處理不掉才是 Error（例外沒接住、資料庫寫不進去）
  • Information 寫里程碑：建立、刪除、登入。不要在迴圈裡面寫，一次請求幾千行沒人看
  • 想看細節用 Debug，然後用 rule 在正式環境關掉，不要用完刪程式碼

5. 練習：題 1～5

題 1：接上 NLog

需求：

  1. 安裝套件 NLog.Web.AspNetCore（6.2.2）。它會一起帶進 NLog 和 NLog.Extensions.Logging
  2. 專案根目錄（和 Program.cs 同一層）新增 nlog.config，內容就是第 3 節那份
  3. Program.cs 在 CreateBuilder 之後加兩行：拔掉內建 Provider、掛上 NLog
  4. 啟動，打一次 GET /api/posts

💡 提示：Web 專案不用設 Copy to Output，Web SDK 預設會把 *.config 和 *.json 複製到 bin（Console 專案才要自己設）。掛 NLog 的方法在 NLog.Web 命名空間，記得 using。

✅ 驗收：BlogApi/bin/Debug/net10.0/logs/app-日期.log 出現，第一行是 …|INFO|Microsoft.Hosting.Lifetime|Now listening on: http://localhost:5107；Run 視窗長得跟以前一樣。但 EF Core 的 SQL 不見了。先想想為什麼，題 3 處理

參考答案（寫完再打開） 
dotnet add package NLog.Web.AspNetCore --version 6.2.2

BlogApi/Program.cs（只列出改動）

using BlogApi.Data;
using Microsoft.EntityFrameworkCore;
using NLog.Web;

var builder = WebApplication.CreateBuilder(args);

// 拔掉內建的 Console、Debug 等 Provider，不然同一行會印兩次
builder.Logging.ClearProviders();
// 掛上 NLog，它會自己去找 nlog.config
builder.Host.UseNLog();

builder.Services.AddControllers();
// … 其他不變

2026-11-01 15:41:11.1776|INFO|Microsoft.Hosting.Lifetime|Application started. Press Ctrl+C to shut down.

SQL 為什麼不見了：EF Core 的 SQL 是 Information、category 是 Microsoft.EntityFrameworkCore.Database.Command，被 <logger name="Microsoft.*" finalMinLevel="Warn" /> 丟掉了。你在 appsettings.Development.json 設的 "Microsoft.EntityFrameworkCore.Database.Command": "Information" 現在沒有作用：掛上 NLog 之後，等級門檻由 nlog.config 決定，appsettings 的 Logging:LogLevel 整段都不再參與。

題 2：Controller 寫 log

需求：

  1. PostsController 的建構子多收一個 ILogger<PostsController>，存成欄位 _logger
  2. Create 成功後寫一行 Information：文章編號和標題
  3. GetById、Delete 找不到文章時寫一行 Warning，帶編號；Delete 成功寫一行 Information
  4. 全部用 message template，不用 $"…"

✅ 驗收：POST 一篇、GET /api/posts/999、DELETE /api/posts/999 之後，log 檔多出三行，category 都是 BlogApi.Controllers.PostsController，等級分別是 INFO、WARN、WARN

參考答案（寫完再打開）

BlogApi/Controllers/PostsController.cs（只列出改動）

private readonly BlogDbContext _db;
private readonly ILogger<PostsController> _logger;

public PostsController(BlogDbContext db, ILogger<PostsController> logger)
{
    _db = db;
    _logger = logger;
}

// GetById 裡
if (post is null)
{
    _logger.LogWarning("找不到文章 {PostId}", id);
    return NotFound();
}

// Create 裡，SaveChangesAsync 之後（這時 post.Id 才有值）
_logger.LogInformation("建立文章 {PostId}：{Title}", post.Id, post.Title);
return CreatedAtAction(nameof(GetById), new { id = post.Id }, post);

// Delete 裡
if (post is null)
{
    _logger.LogWarning("要刪除的文章 {PostId} 不存在", id);
    return NotFound();
}

_db.Posts.Remove(post);
await _db.SaveChangesAsync();
_logger.LogInformation("刪除文章 {PostId}", id);
return NoContent();

log 檔會多這幾行：

2026-11-01 15:43:07.3968|INFO|BlogApi.Controllers.PostsController|建立文章 5：Docker 入門
2026-11-01 15:43:07.4830|WARN|BlogApi.Controllers.PostsController|找不到文章 999
2026-11-01 15:43:07.5287|WARN|BlogApi.Controllers.PostsController|要刪除的文章 999 不存在

ILogger 不用 using，它在 Microsoft.Extensions.Logging，專案的 implicit usings 已經包含。

這些 log 行之後一直留著。02a 的參考答案改寫 PostsController 時沒有把它們寫出來，你自己保留就好。

題 3：把 SQL 找回來，分到自己的檔案

需求：

  1. 新增一個 File target，名字 sqlfile，檔名 logs/sql-日期.log，layout 只要時間和訊息
  2. 新增一條 rule：category Microsoft.EntityFrameworkCore.Database.Command 的 Info 以上寫到 sqlfile，而且寫完就停（不要再被其他 rule 處理）
  3. 想清楚這條 rule 要放在 Microsoft.* 那條的上面還是下面

✅ 驗收：打一次 GET /api/posts，logs/sql-日期.log 出現 Executed DbCommand 和 SELECT；app-日期.log 裡沒有 SQL

參考答案（寫完再打開）

BlogApi/nlog.config（只列出改動）

<targets>
  …
  <target xsi:type="File" name="sqlfile"
          fileName="${basedir}/logs/sql-${shortdate}.log"
          layout="${longdate}|${message}"
          maxArchiveFiles="7" />
</targets>

<rules>
  <!-- 要放在 Microsoft.* 那條的上面，不然先被它丟掉 -->
  <logger name="Microsoft.EntityFrameworkCore.Database.Command" minLevel="Info" writeTo="sqlfile" final="true" />
  <logger name="System.*" finalMinLevel="Warn" />
  <logger name="Microsoft.*" finalMinLevel="Warn" />
  <logger name="Microsoft.Hosting.Lifetime*" finalMinLevel="Info" />
  <logger name="*" minLevel="Info" writeTo="console,file" />
</rules>

sql-2026-11-01.log：

2026-11-01 15:45:17.0029|Executed DbCommand (18ms) [Parameters=[], CommandType='Text', CommandTimeout='30']
SELECT [p].[Id], [p].[Content], [p].[CreatedAt], [p].[Title], [p].[UpdatedAt]
FROM [Posts] AS [p]
ORDER BY [p].[CreatedAt] DESC
2026-11-01 15:45:17.2105|Executed DbCommand (12ms) [Parameters=[@p0='?' (Size = 4000), @p1='?' (DbType = DateTime2), @p2='?' (Size = 200), @p3='?' (DbType = DateTime2)], CommandType='Text', CommandTimeout='30']

順序為什麼重要：rule 由上往下比對，Microsoft.* 那條會把 Info 丟掉並停止。EF 的 rule 放在它上面，SQL 先被寫進 sqlfile，final="true" 讓它不再往下走，所以也不會進 app-日期.log。

SQL 現在不在 Run 視窗了。想兩邊都有，writeTo="sqlfile,console" 就好。自己決定，開發時看 Run 視窗很方便，但檔案留得住。

題 4：例外會怎麼被記錄

需求：

  1. 在 GetById 最前面暫時加：if (id == 999) throw new InvalidOperationException("測試用例外");
  2. 打 GET /api/posts/999，看回應，再看 app-日期.log：這條 Error 是誰寫的？有沒有 stack trace？
  3. 再加一段 try { … } catch (InvalidOperationException ex) { … }，裡面用兩種寫法各記一次（LogError(ex, "…") 和 LogError(ex.Message)），比較檔案裡的差別
  4. 看完把這些測試碼全部拿掉

✅ 驗收：回應 500；log 檔有一條 ERROR，category 是 Microsoft.AspNetCore.Diagnostics.DeveloperExceptionPageMiddleware，後面接完整 stack trace

參考答案（寫完再打開）

你沒有寫任何 log，但 app-日期.log 自己多了這一塊：

三件事：

  • 寫這條的是 Development 環境的 DeveloperExceptionPageMiddleware：例外一路往外丟、沒人接，它接住、記 Error、回 500 和 stack trace。正式環境沒有它，第 5 課會做自己的錯誤處理

6. 故意弄壞：四個實驗

每個先猜結果，再動手，最後打開答案。做完記得改回來。

實驗 A：找不到設定檔

把 bin/Debug/net10.0/nlog.config 刪掉（專案根目錄那份留著），從 Rider 啟動。猜：log 還會寫嗎？

答案

一切正常。NLog 找設定檔不只看 ${basedir}，也會看 log 第 4 行印的那個 Content root path，也就是專案資料夾；那裡的 nlog.config 被找到了。而且下次建置又會把它複製回 bin。

要看到真正壞掉的樣子，把整個 bin/Debug/net10.0 複製到別的資料夾、刪掉裡面的 nlog.config，在那個資料夾開終端機跑 dotnet BlogApi.dll：

  • 終端機完全安靜，連 Now listening on 都沒有
  • 沒有 logs 資料夾
  • 沒有任何錯誤，API 照樣能打

因為 ClearProviders() 把內建 Console 拔了，NLog 又沒有設定檔，等於沒有任何 target。找不到設定檔，NLog 不會報錯。這就是正式環境 publish 之後「怎麼都沒 log」最常見的原因，第一件事是確認 nlog.config 有沒有在程式旁邊。Web 專案的 SDK 會自動複製；Console 專案（例如 01b 的 LinqLab）要自己在 csproj 加：

<ItemGroup>
  <Content Include="nlog.config" CopyToOutputDirectory="PreserveNewest" />
</ItemGroup>

實驗 B：用字串插值寫 log

把題 2 的 Create 改成 _logger.LogInformation($"建立文章 {post.Id}：{post.Title}");。猜：Rider 會說什麼？建置會過嗎？log 檔會不一樣嗎？

答案
  • Rider 在那行畫提示，規則 CA2254。訊息（中文版）：記錄訊息範本不應在與 'LoggerExtensions.LogInformation(ILogger, string?, params object?[])' 通話期間改變，意思是「範本每次呼叫都不同」
  • 建置照樣過、沒有警告：這條規則預設嚴重性是「建議」。想讓它變警告，專案根目錄加 .editorconfig 寫 dotnet_diagnostic.CA2254.severity = warning
  • app-日期.log 那一行長得一模一樣

那差在哪？差在這行 log 身上帶的「屬性」。題 7 把 log 寫成 JSON 時會看到：message template 的那行多了 "PostId":5,"Title":"Docker 入門"，插值的那行什麼都沒有。

實驗 C：appsettings 的 LogLevel 還有用嗎？

把 appsettings.Development.json 的 "Default": "Information" 改成 "Warning"，重啟，POST 一篇文章。猜：題 2 那行 INFO「建立文章」還會寫進檔案嗎？

答案

還會。Default 管的就是你自己的 category（BlogApi.*），改成 Warning 照理說 Information 應該被擋，結果檔案裡還是有：

2026-11-01 15:45:23.6677|INFO|BlogApi.Controllers.PostsController|建立文章 6：Docker 入門

因為 UseNLog() 會把 Microsoft 那一層的等級過濾拿掉，讓 nlog.config 的 rule 成為唯一的門檻（控制這件事的選項叫 RemoveLoggerFactoryFilter，實測不設它就是這個行為）。所以掛上 NLog 之後：

  • appsettings 裡 Logging:LogLevel 整段不再有作用，包括 01 題 7 加的那行 EF Core 設定
  • 要調等級，改 nlog.config 的 minLevel / finalMinLevel

改回 Information，免得之後自己忘了這件事。

實驗 D：rule 的順序

把 <logger name="*" …> 那條搬到 <rules> 的第一條，其他不動。重啟，打 GET /api/posts 和 POST 一篇。猜：app-日期.log 會多什麼？

原本 7 行的 log 檔變成 42 行，Run 視窗也被洗版。多出來的是誰：

題 6：每一行 log 帶上是哪個請求

log 檔一多，「找不到文章 999」是哪個 URL 打出來的看不出來。NLog.Web.AspNetCore 提供一組 ${aspnet-…} renderer，能在 layout 裡放目前請求的資訊。

需求：file target 的 layout 在 ${logger} 後面加一欄：HTTP 方法和 URL。再加上 ${aspnet-response-statuscode} 試試，看它在 Controller 裡寫 log 的那一刻印出什麼。

✅ 驗收：打 POST、GET /api/posts/1000（404），log 檔每行多了 POST http://localhost/api/posts 這種欄位

參考答案（寫完再打開） 
layout="${longdate}|${level:uppercase=true}|${logger}|${aspnet-request-method} ${aspnet-request-url} ${aspnet-response-statuscode}|${message:withexception=true}"
2026-11-01 16:23:13.6043|INFO|Microsoft.Hosting.Lifetime|  |Now listening on: http://localhost:5107
2026-11-01 16:23:15.3330|INFO|BlogApi.Controllers.PostsController|POST http://localhost/api/posts 200|建立文章 5：Docker 入門
2026-11-01 16:23:15.3812|ERROR|Microsoft.AspNetCore.Diagnostics.DeveloperExceptionPageMiddleware|GET http://localhost/api/posts/999 200|An unhandled exception has occurred while executing the request.|System.InvalidOperationException: 測試用例外
2026-11-01 16:23:15.4719|WARN|BlogApi.Controllers.PostsController|GET http://localhost/api/posts/1000 200|找不到文章 1000

第三行的 ERROR 是題 4 的 throw 還在時打 999 留下的，故意留著給你看狀態碼。三個觀察：

  • 啟動時的那幾行不在任何請求裡，所以這欄是空的
  • ${aspnet-request-url} 預設不含 port（http://localhost/api/posts）。要 port 寫 ${aspnet-request-url:IncludePort=true}
  • ${aspnet-response-statuscode} 三行都印 200，連丟例外（最後回 500）和找不到（最後回 404）的都是 200。因為 log 寫下去的那一刻回應還沒決定，狀態碼還是預設值。這個 renderer 只有在回應結束之後寫的 log 裡才準，例如框架自己的 Request finished 那行。想記「每個請求回了什麼狀態碼」，用 ASP.NET Core 內建的 app.UseHttpLogging()，不要靠 Controller 裡的 log

題 7：JSON layout，一行一個 JSON

文字 log 給人看；要讓工具（Seq、ELK、雲端的 log 服務）搜尋和統計，一行一個 JSON 比較好。這也是 message template 真正有回報的地方。

需求：新增一個 File target jsonfile，檔名 logs/app-日期.json，用 JsonLayout，欄位：time、level、logger、url、message、exception，並且把 log 身上的屬性也放進去。* 那條 rule 的 writeTo 多加 jsonfile。

✅ 驗收：POST 一篇後，app-日期.json 裡那行有 "PostId" 和 "Title" 兩個欄位

參考答案（寫完再打開） 
<target xsi:type="File" name="jsonfile"
        fileName="${basedir}/logs/app-${shortdate}.json"
        maxArchiveFiles="7">
  <layout xsi:type="JsonLayout" includeEventProperties="true">
    <attribute name="time" layout="${longdate}" />
    <attribute name="level" layout="${level:uppercase=true}" />
    <attribute name="logger" layout="${logger}" />
    <attribute name="url" layout="${aspnet-request-method} ${aspnet-request-url:IncludePort=true}" />
    <attribute name="message" layout="${message}" />
    <attribute name="exception" layout="${exception:format=tostring}" />
  </layout>
</target>

<!-- rules -->
<logger name="*" minLevel="Info" writeTo="console,file,jsonfile" />

includeEventProperties="true" 就是「把 log 身上的屬性也放進 JSON」。結果：

症狀原因解法
啟動就炸：NLog.NLogConfigurationException: Failed loading NLog configuration. Unknown log level: Infomation (Parameter 'levelName') FilePath: …\nlog.config設定檔打錯字，而且 throwConfigExceptions="true"（實測）照訊息改。這是好的失敗，馬上知道

同一行在 Run 視窗印兩次忘了 ClearProviders()，內建 Console 和 NLog 的 console target 各印一次加上
Windows 上 bin 資料夾刪不掉、Clean 失敗File target 預設 keepFileOpen="true"，程式還在跑就鎖著 log 檔先停掉程式

log 檔越來越大、磁碟滿沒設 maxArchiveFiles；或把 Info 也寫進資料庫設上限；資料庫只收 Warn 以上

9. 延伸問題

  1. Serilog 和 NLog 怎麼選？兩個都是 Provider，概念一樣（Serilog 叫 sink 不叫 target，設定寫在程式碼裡多於設定檔）。公司用哪個就學哪個，換邊只是換名詞。
  2. 怎麼把同一個請求的所有 log 串起來？每個請求有一個 TraceId（${activityid}），放進 layout 就能用它過濾。第 5 課做錯誤處理時，回給前端的 ProblemDetails 也會帶 traceId，前端回報的 id 就能對回 log。
  3. 正式環境 log 放哪？放容器裡的 ${basedir}，容器刪掉就跟著消失，跟 00 課資料庫沒掛 volume 一樣。小專案掛 volume；多台機器就送到集中式服務（Seq、ELK、雲端的 Log Analytics），這時題 7 的 JSON 就派上用場。
  4. 想讓 appsettings 的 LogLevel 也生效？實驗 C 提到的 RemoveLoggerFactoryFilter 可以關掉，用法見 NLog.Web 的文件（這頁沒實測）。一般不建議兩邊都設門檻，會搞不清楚是誰擋的。
