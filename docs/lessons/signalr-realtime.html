1. 為什麼輪詢不夠

📋 情境：100 個人開著文章列表。主管發了一篇新文章，大家要馬上看到。

最直覺的做法是前端每 3 秒打一次 GET /api/posts，叫輪詢（polling）。100 個人就是每秒 33 個請求，99% 的回答是「沒有新文章」。真正要解的問題是：server 想講話的時候，沒有管道。HTTP 永遠是 client 先開口。

sequenceDiagram participant B as 瀏覽器 participant S as Server Note over B,S: 輪詢：client 一直問 B->>S: 有新文章嗎？ S-->>B: 沒有 B->>S: 有新文章嗎？ S-->>B: 沒有 B->>S: 有新文章嗎？ S-->>B: 有，文章 5 Note over B,S: WebSocket：握手一次，之後雙向 B->>S: 升級成 WebSocket S-->>B: 101 Switching Protocols S->>B: 文章 5 建立了 S->>B: 文章 5 更新了 B->>S: 我只想看文章 6
輪詢是 client 問、server 答；WebSocket 握手之後線一直接著，誰想講都可以講
方法怎麼做代價
輪詢固定間隔一直問浪費請求、延遲等於間隔
Long polling問了之後 server 先不答，有事才答，答完 client 馬上再問每次都是一個完整的 HTTP 請求，連線數多
Server-Sent Events（SSE）一個不關的 HTTP 回應，server 一直往裡面寫只能 server 到 client 單向
WebSocketHTTP 握手後升級成雙向的長連線要自己定義訊息格式、處理斷線、重連

SignalR 是 ASP.NET Core 內建的一層，把這些包起來：自動挑最好的傳輸（有 WebSocket 用 WebSocket，不行就退到 SSE 或 long polling）、幫你處理斷線重連、讓「server 呼叫 client 的方法」和「client 呼叫 server 的方法」寫起來像呼叫一般的函式、還有群組。你不用碰 WebSocket 的 API。

2. 原理：Hub、連線、群組、negotiate

名詞是什麼在 BlogApi 裡
Hubserver 端的一個類別。client 可以呼叫它的 public 方法；它可以透過 Clients 呼叫 client 的方法PostsHub，掛在 /hubs/posts
連線（connection）每個開著頁面的瀏覽器分頁是一條連線，有自己的 ConnectionId；分頁關掉連線就沒了開兩個分頁就是兩條
Clients.All / Group(…) / Caller要推給誰：所有連線、某個群組、呼叫我的那個人新文章推 All；文章更新只推 post-5 群組
群組（Group）連線的集合，名字自己取。加入、離開都是 server 做的（client 呼叫 Hub 方法請 server 幫它加）WatchPost(5) 把呼叫者加進 post-5
IHubContext<THub, TClient>在 Hub 類別外面（例如 Controller）推訊息用的。Controller 不是 Hub，拿不到 Clients，要靠它注入到 PostsController
強型別 Hub Hub<IPostsClient>用介面列出 client 有哪些方法，呼叫時編譯器檢查名稱和參數；不用強型別就是 SendAsync("方法名字串", …)，打錯字沒人知道（實驗 D）IPostsClient 有 PostCreated、PostUpdated

連線是怎麼建起來的：negotiate

client 的 start() 做兩件事：先 POST /hubs/posts/negotiate 問 server「你支援哪些傳輸、給我一個連線 id」，再用其中一種傳輸真正連上（通常是 WebSocket，Network 分頁會看到一個狀態 101 的請求）。negotiate 的回應長這樣：

{"negotiateVersion":1,"connectionId":"MGbguDIP_JfD-kRPT7ITaA","connectionToken":"ACO0ViIc-9n_27i9oD7vhw",
 "availableTransports":[{"transport":"WebSockets","transferFormats":["Text","Binary"]},
                        {"transport":"ServerSentEvents","transferFormats":["Text"]},
                        {"transport":"LongPolling","transferFormats":["Text","Binary"]}]}

這個端點是 MapHub 幫你掛的。它回 404 就代表 Hub 沒掛上（實驗 A）；它被 CORS 擋就代表頁面和 API 不同來源（實驗 B）。

送過去的 JSON 會變 camelCase

server 端的 PostCreatedNotification(int PostId, string Title, …)，到了 JavaScript 是 n.postId、n.title，跟 Web API 回 JSON 的規則一樣。C# 客戶端用自己的 record 接，名稱對得上就好。

BlogApi/Hubs/IPostsClient.cs

namespace BlogApi.Hubs;

// server 可以呼叫 client 的哪些方法。方法名稱就是 client 端 on("PostCreated") 要對上的字串
public interface IPostsClient
{
    Task PostCreated(PostCreatedNotification notification);

    Task PostUpdated(PostUpdatedNotification notification);
}

BlogApi/Hubs/PostsHub.cs

using Microsoft.AspNetCore.SignalR;

namespace BlogApi.Hubs;

// client 可以呼叫這裡的 public 方法；server 透過 Clients 呼叫 client 的方法
public class PostsHub(ILogger<PostsHub> logger) : Hub<IPostsClient>
{
    // client 呼叫 WatchPost(5)：加入群組 post-5，之後文章 5 的更新只推給這個群組
    public async Task<string> WatchPost(int postId)
    {
        await Groups.AddToGroupAsync(Context.ConnectionId, GroupName(postId));
        logger.LogInformation("{ConnectionId} 開始看文章 {PostId}", Context.ConnectionId, postId);
        return $"你正在看文章 {postId}";
    }

    public static string GroupName(int postId) => $"post-{postId}";

    public override Task OnConnectedAsync()
    {
        logger.LogInformation("連線：{ConnectionId}", Context.ConnectionId);
        return base.OnConnectedAsync();
    }

    public override Task OnDisconnectedAsync(Exception? exception)
    {
        logger.LogInformation("斷線：{ConnectionId}", Context.ConnectionId);
        return base.OnDisconnectedAsync(exception);
    }
}

  const statusEl = document.getElementById("status");
  const events = document.getElementById("events");

  function setStatus(text, cls) { statusEl.textContent = text; statusEl.className = cls; }
  function log(text) {
    const li = document.createElement("li");
    li.textContent = new Date().toLocaleTimeString() + "　" + text;

  // hub 的網址。頁面和 API 同一個站時用相對路徑就好

    .withAutomaticReconnect()

  // server 呼叫 client 的方法：名稱對應 IPostsClient 的方法；JSON 到了 JS 會變 camelCase
  connection.on("PostCreated", n => log(`新文章 #${n.postId}：${n.title}`));
  connection.on("PostUpdated", n => log(`文章 #${n.postId} 更新了：${n.title}`));

  connection.onreconnecting(err => setStatus("斷線，重連中… " + (err?.message ?? ""), "off"));

    .catch(err => { setStatus("連不上：" + err.message, "off"); console.error(err); });

void Log(string text) => Console.WriteLine($"{DateTime.Now:HH:mm:ss} {text}");

var connection = new HubConnectionBuilder()
    .WithUrl("http://localhost:5107/hubs/posts")
    .WithAutomaticReconnect()
    .Build();

// server 呼叫 client 的方法：名稱和 IPostsClient 的方法一樣，參數用自己的 record 接
connection.On<PostCreatedNotification>("PostCreated", n => Log($"PostCreated：#{n.PostId} {n.Title}"));
connection.On<PostUpdatedNotification>("PostUpdated", n => Log($"PostUpdated：#{n.PostId} {n.Title}"));

connection.Reconnecting += error => { Log($"斷線，重連中… {error?.Message}"); return Task.CompletedTask; };
connection.Reconnected += id => { Log($"重連成功：{id}"); return Task.CompletedTask; };
connection.Closed += error => { Log($"連線已關閉 {error?.Message}"); return Task.CompletedTask; };

try
{
    await connection.StartAsync();
    Log($"已連線：{connection.ConnectionId}");

    // client 呼叫 server 的 Hub 方法，拿回傳值

    Log(reply);
}
catch (Exception ex)
{
    Log($"連不上：{ex.GetType().Name}: {ex.Message}");
}

await Task.Delay(Timeout.Infinite);

5. 動手實驗：改一個地方，先猜會怎樣（四個）

每個先猜結果，再動手，最後打開答案。做完記得改回來。

實驗 A：忘了 MapHub

把 app.MapHub<PostsHub>("/hubs/posts"); 註解掉，重啟，開 posts.html，再跑一次 C# 客戶端。猜：各自看到什麼？

答案

negotiate 回 404。C# 客戶端：

17:43:56 連不上：HttpRequestException: Response status code does not indicate success: 404 (Not Found).

瀏覽器頁面會停在「連不上：」，F12 的 Network 看得到 negotiate 那個請求是 404。withAutomaticReconnect 不會重試第一次連線失敗，所以 start() 的 catch 一定要寫。

AddSignalR() 只是註冊服務，MapHub 才是把 /hubs/posts 這個路徑接上 Hub，少一個都不行。這和 01 課 AddControllers() 配 MapControllers() 是同一種對稱。

實驗 B：頁面和 API 不同來源：CORS

在 Rider 對 posts.html 按右鍵 Open in Browser。Rider 會用它內建的預覽伺服器開這個檔案，網址通常是 http://localhost:63342/…（port 以你看到的為準，下面的設定要跟著改），port 和 API 不一樣，瀏覽器視為不同來源。頁面的 withUrl("/hubs/posts") 要先改成完整網址 http://localhost:5107/hubs/posts。猜：連得上嗎？

答案

連不上，F12 的 Console 會有 CORS 的錯誤，negotiate 被瀏覽器擋住。用 curl 冒充瀏覽器送 preflight 看 API 回了什麼：

OPTIONS /hubs/posts/negotiate   Origin: http://localhost:63342
→ HTTP/1.1 405 Method Not Allowed（而且沒有任何 Access-Control-* 標頭）

瀏覽器的規矩：頁面的來源（http://localhost:63342）和 API 的來源（http://localhost:5107）不同時，瀏覽器先用 OPTIONS 問 API「這個來源可以嗎」，API 沒有用 Access-Control-Allow-Origin 回答，瀏覽器就不讓頁面送出真正的請求。API 本身沒有壞，curl 直接 POST negotiate 還是 200，只是瀏覽器不放行。

解法是 API 明確允許那個來源：

BlogApi/Program.cs（只列出改動）

builder.Services.AddCors(options => options.AddDefaultPolicy(policy =>
    policy.WithOrigins("http://localhost:63342")   // 只放行這個來源，不要 AllowAnyOrigin
          .AllowAnyHeader()
          .WithMethods("GET", "POST", "DELETE")      // long polling 要 DELETE 來關連線
          .AllowCredentials()));                      // SignalR 要求，沒登入也要
// …
app.UseStaticFiles();
app.UseCors();            // 一定要在 MapHub 前面
// …
app.MapHub<PostsHub>("/hubs/posts");

加上之後同一個 preflight：

→ HTTP/1.1 204 No Content
Access-Control-Allow-Credentials: true
Access-Control-Allow-Headers: x-signalr-user-agent,x-requested-with
Access-Control-Allow-Origin: http://localhost:63342

換一個來源（Origin: http://evil.example）送，回應裡就沒有這些標頭，瀏覽器照樣擋。AllowCredentials() 和 AllowAnyOrigin() 不能一起用，框架會直接拒絕，所以 SignalR 的 CORS 一定要列出確切的來源。

正式前端（Vue、React 開發伺服器跑在 5173 之類的 port）跟 API 幾乎一定不同來源，這個設定遲早要寫；這頁的題 2 把頁面放在 wwwroot 就是為了先避開它。做完把 withUrl 改回相對路徑。

實驗 C：API 停掉，client 會怎樣

頁面和 C# 客戶端都連著，停掉 API。猜：畫面變什麼？6 秒後再啟動 API，又變什麼？如果一直不啟動呢？

答案

C# 客戶端，API 停掉 6 秒後重啟：

17:42:36 已連線：PvHunTCq_pVPfQnp6PlGRg
17:42:39 斷線，重連中… The remote party closed the WebSocket connection without completing the close handshake.
17:42:47 重連成功：BC2O8efrXjuw7voDWkoNgw

一直不啟動：

18:49:01 斷線，重連中… The remote party closed the WebSocket connection without completing the close handshake.
18:49:59 連線已關閉 Reconnect retries have been exhausted after 4 failed attempts and 00:00:58.0424114 elapsed. Disconnecting.

三件事：

  • WithAutomaticReconnect() 不帶參數時，等 0、2、10、30 秒各試一次，四次都失敗就放棄，觸發 Closed（JS 是 onclose）。之後不會再試，要重新 start() 或請使用者重新整理
  • 重連成功後的 connectionId 是新的，server 把它當一條全新的連線，所以群組要重加（題 4）
  • 瀏覽器頁面對應的是 onreconnecting（狀態列變紅）、onreconnected（變綠並重加群組）、onclose

想改間隔：WithAutomaticReconnect(new[] { TimeSpan.Zero, TimeSpan.FromSeconds(2), TimeSpan.FromSeconds(10) })，JS 是 withAutomaticReconnect([0, 2000, 10000])。

實驗 D：用字串版推播，名字打錯

把 Controller 注入的型別暫時改成非強型別的 IHubContext<PostsHub>，用 SendAsync("PostCreatd", …)（少一個 e）推。POST 一篇。猜：會報錯嗎？

答案

POST 回 201、Run 視窗沒有任何錯誤或警告、client 什麼都沒收到。server 真的送出了一個叫 PostCreatd 的呼叫，client 沒有人註冊這個名字，就丟掉了。兩邊都認為自己沒錯。

強型別版本 IHubContext<PostsHub, IPostsClient> 根本沒有 SendAsync，只能呼叫 IPostsClient 裡有的方法，名字打錯是編譯錯誤。這就是題 1 用 Hub<IPostsClient> 的原因。client 那邊的 on("PostCreated") 還是字串，改介面的方法名時記得兩邊一起改。

6. 常見坑

症狀原因解法
重連之後收不到群組的訊息重連是新連線，群組沒了onreconnected 裡再呼叫一次 WatchPost（題 2 的頁面已經有）
在 Hub 類別裡放欄位記東西，下一次呼叫就不見Hub 每次呼叫都 new 一個，用完丟掉狀態放 singleton 服務或資料庫；Hub 只做轉發
上了兩台 server 之後，有些人收不到推播每台 server 只知道連到自己的連線加 backplane（Redis），讓每台都轉發給所有連線
推播沒反應也沒錯誤字串版方法名打錯（實驗 D）用強型別 Hub
頁面一開就「連不上」忘了 MapHub（實驗 A）或不同來源沒設 CORS（實驗 B）看 Network 分頁的 negotiate：404 是前者，被擋是後者
長時間開著的頁面突然收不到重連四次失敗後就放棄了（實驗 C）onclose 裡提示重新整理，或自己再 start()
想知道是誰的連線還沒登入，只有 ConnectionId第 5 課登入後用 Context.UserIdentifier，可以 Clients.User(userId) 推給某個人的所有分頁
每個推播都帶整個 Entity和 Web API 回傳一樣的問題（01 題 6）推 Notification record，只放畫面要的欄位

7. 延伸問題

  1. RabbitMQ 的 Worker 做完事，想通知瀏覽器？Worker 不是 Web 程式，沒有 SignalR 連線。兩條路：Worker 呼叫 API 的一個端點，由 API 用 IHubContext 推；或裝 Redis backplane，讓 Worker 也能透過 Redis 送訊息給 API 的連線。
  2. Blazor Server 跟這個有什麼關係？Blazor Server 的每個畫面更新都是走 SignalR 連線送 UI diff，你剛剛學的連線、重連、斷線就是它的底層。
  3. 不用 SignalR，直接用 WebSocket 可以嗎？可以，ASP.NET Core 有 app.UseWebSockets()。差別是訊息格式、重連、群組、傳輸降級都要自己寫。SignalR 幫你做的就是這些。
  4. 只要 server 單向推、不用 client 回話？SSE 更簡單，.NET 10 的 Minimal API 有 TypedResults.ServerSentEvents。但要群組、要重連、要 client 回話，還是 SignalR。
  5. 推播太多會不會塞爆？每條連線在 server 都占記憶體，幾千條沒問題，幾十萬條要分多台加 backplane，或改用 Azure SignalR Service 這種代管服務。
